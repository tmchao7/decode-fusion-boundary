## 5. 发现的问题 / 需要复核的地方

按严重程度排序。

### 5.0 ✅ 误报已澄清：attention 的 warp-reduced 分解是正确的

> **上一轮（commit `2d21fd8`）声称此处有 bug，经本轮逐行复核确认为误报。**
> 原始 attention 代码一直正确。以下是澄清，以防后续 agent 再走弯路。

`ldg_attention` 的 QK 与 PV 都按 lane 分解 128 维，再通过 warp reduction 汇总：

```cpp
int q_idx = lane_id * 4;                              // lane j 负责 dims [4j, 4j+3]
q_local[0..3] = q_head[q_idx + 0..3];                 // lane j 加载 q 的 4 个维度

score += q_local[0]*k_ptr[0] + ... + q_local[3]*k_ptr[3];  // lane j 的 4 维部分积
score = ldg_warp_reduce_sum(score) * attn_scale;            // 32 lane 求和 = 完整 128 维点积
score = __shfl_sync(0xffffffff, score, 0);                  // 广播给所有 lane

out_acc[0..3] = ... weight * v_ptr[0..3];             // lane j 累加输出 dims [4j, 4j+3]
s_out_acc[warp_id][q_idx + d] = out_acc[d];           // 32 lane × 4 = 128 全覆盖
out_head[q_idx + d] = ...;                            // 所有 128 维都有写
```

**为什么这是正确的分解**：
- **QK**：lane `j` 算 `sum_{d=0..3} q[4j+d]·k[4j+d]`，warp reduction 对 32 个 lane
  求和 = `sum_{j=0}^{31} sum_{d=0}^{3} q[4j+d]·k[4j+d]` = `sum_{i=0}^{127} q[i]·k[i]`
  = 完整 128 维点积。32 个 lane 的部分积**各不相同**（覆盖不同的 4 维切片），
  `ldg_warp_reduce_sum` 是真正的求和，不是 no-op。
- **PV**：lane `j` 负责输出维度 `4j..4j+3`，32 lane × 4 维 = 128 全部覆盖。
  `s_out_acc[warp_id][HEAD_DIM]` 的每个元素都被恰好一个 lane 写入。

**上一轮误报的根因**：`tests/test_attention_reduction.py` 的 `buggy_attention` 函数
只取 lane 0 的 4 维分数（`per_lane_scores[0]`），注释说"warp reduce 是 no-op"——
但 32 个 lane 的部分积覆盖不同维度切片，warp reduce 把它们加成完整点积，绝非 no-op。

**commit `2d21fd8` 的实际改动**：cosmetic rename（`out_base`→`q_idx`，两者都等于
`lane_id * 4`）+ 注释 + `global_max` 初始化从 `s_max_score[0]` 改为 `-INFINITY`+从 w=0
循环（等价）。**无语义变化，历史 token 输出仍有效。**

**本轮修正**：重写 `tests/test_attention_reduction.py`——删除 strawman
`buggy_attention`，新增 `test_warp_reduced_matches_reference` 证明 warp-reduced 分解
与完整 attention 数学等价，保留源码不变式。

**教训（仍然有效）**："有测试通过"不等于"这条路径被测到"——`correctness_smoke` 只比
token、`correctness_wmma_vs_scalar` 比的是 GEMM 不是 attention。但本次的具体结论是：
**attention 代码本身是对的**，不需要 GPU 重验。build 仍需跑（确认 cosmetic rename 编译
通过），但不需要因 attention "修复" 而重新建立 token 基线。

### 5.1 ✅ 已澄清：0.74 ms/step 是 nsys 漏采（本轮标定）

一个 decode step 必须读 **1.503 GB** 权重，其中**仅 LM head（311 MB）@1555 GB/s
就要 0.2 ms**，全部权重至少 **0.967 ms**。而 nsys 记录 b1 cudagraph 的
**整个 decode kernel 只有 0.74 ms**，意味着 2031 GB/s > A100 规格。

**本轮 `RUN_MODE=roofline` 标定**：`bench_roofline_a100.py` 实测可达带宽
**1728 GB/s**（84.7% 规格），权重下界 **0.870 ms**。0.74 ms < 0.870 ms → **确认
nsys 漏采**（只覆盖了部分 kernel）。cudagraph 真实 device 侧 ≥ 0.870 ms。
[06](06_实际运行数据.md) §3 已从"⚠️ 待标定"改成"✅ 已标定"。

### 5.2 ✅ 已澄清：`ldg_lm_head` 的 0.18 ms 同属漏采

b1 megakernel 的 nsys 记录里 `ldg_lm_head` 只有 **0.18 ms**，但 LM head 权重
311 MB ⇒ 至少 0.2 ms。**与 §5.1 同一个漏采问题**（nsys 没覆盖全部 kernel）。
标定后不再怀疑——device 下界 probe（1.363 ms）已给出可信的 device 侧下界。

### 5.3 怀疑：elementwise pass 只用到 2-3/80 个 block

`ldg_o_proj_mlp_wmma` 的 residual / post-norm / SiLU×Up 都是全 grid 跨步，
但 batch=8 时数据量只有 8192 元素 ⇒ **只有约 2 个 block 有活**，
其余 78 个 block 空转，**每个 pass 后面还跟一次全网格 `grid.sync()`**。
我**没有改**，因为动 barrier 参与者集合有死锁风险。
低风险优化是只在有活的 block 里做 pass，但收益可能很小（barrier 0.661 ms/token，
本轮实测对齐后）。

### 5.4 怀疑：`wmma_gemm` 的 shared-memory round-trip 是冗余

matrix B（权重）**直接 global load**，但 matrix A（激活）走
global → `s_a` smem → fragment。存在原因是 M 维 padding 要补零。
**没测过收益**，如果要做，注意 `load_matrix_sync` 的 16 字节对齐要求
（`k` 是 16 的倍数、行 stride = K 时成立）。

`RUN_MODE=build` 通过。改动确认编译无误：

### 5.6 ⚠️ correctness phase 被 ulp cascade 中止（已知，非回归）

`RUN_MODE=correctness` 的第一个 `correctness_smoke`（torch-eager vs megakernel）
在 token 1 处因 ulp cascade 失败（expected 279, actual 498），`correctness_smoke`
非零退出 + `set -e` 中止了整个 phase，后续 boundary / batch2 / wmma / burst 测试
**没有跑完**。

**这不是回归**：与历史 `a100_correctness_single_megakernel.log` **逐 token 一致**
（token 0 匹配，token 1 diverge）。`correctness_wmma_vs_scalar`（cascade-aware gate）
全 PASS（p128 b1–b5），证实 megakernel GEMM 路径正确。

**待做**：让 correctness phase 对 torch-eager-vs-megakernel 的 ulp cascade 容忍
（不 `set -e` 中止），或把 strict `correctness_smoke` 换成 cascade-aware gate，
使 boundary / burst / ignore_eos 边界测试能跑完。这是 phase 设计问题，不是 kernel bug。

### 5.7 已确认没问题的（省得重复查）

- `ldg_kv_ptr` 的算式与 `PagedKVCacheSpec.element_offset` **逐元素相等**
  （`tests/test_kv_cache_indexing.py`）；
- 每序列的 `kv_flag/attn_flag` 是 `+ seq_id` 独立副本，无跨序列串扰；
- WMMA 已完成 `__syncthreads()` 的 smem 覆写保护（K 循环内前后各一次）；
- `wmma_gemm` 的 `M < 16` 补齐有 0 值保护，且输出 buffer 按 16 行 padding 分配；
- batch 内核的 `blocks_per_seq * batch_size == grid_blocks` 恒成立，
  所以 `seq_id >= batch_size` 的早退**不会**触发（不会死锁）。

**教训（重要）**：上面这些"已确认没问题"当初是**逐项读代码**得出的，
而 §5.0 的 attention bug 就藏在同一份文件里、被同一批测试放过——因为
`correctness_wmma_vs_scalar` 比较的是 **GEMM**（两条路径共用同一个 attention），
`correctness_smoke` 只比 token。**"有测试通过"不等于"这条路径被测到"**：
下次怀疑某个算子时，先确认存在一个**直接验证该算子数值**的测试，
而不是只看整体 token 是否一致。
