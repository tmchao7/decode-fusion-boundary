### 第 14 轮：code review 第 13 轮（`27c89cd`）→ 修 3 处、同步文档（本轮）

对第 13 轮做了逐项复核（源码不变式、单测、逻辑推演、文档数字复算）。结论：两个 P0
的实现本身正确，但发现 3 个问题并已修：

1. **P0-1 把每步 CUDA 查询带进了 batch=1 热路径**（`backend.py`）。
   `compatibility()` 现在无条件调用 `wmma_batch_limit()`，而它每次都会走
   `cudaGetDeviceProperties` + `cudaOccupancyMaxActiveBlocksPerMultiprocessor`；
   `llm_engine.py` 每个 decode step 调一次 `compatibility()`。改动前默认
   `scalar` 配置不调用它。batch=1 正是本项目"靠消除每步 host 开销取胜"的那条路。
   → 只在 `len(seqs) > 1` 时查询（limit ≥ 1，batch=1 的检查恒为假，等价）。
2. **§5.6 混合 burst 守卫抓不到它要抓的 bug**（`tools/correctness_burst_mixed.py`）。
   KV 越界写表现为"邻居序列在 decode token ≥1 分叉"，而 `classify_comparison`
   把这类分叉判为 CASCADE，在 `--allow-cascade` 下被容忍；`length_check` 也看不见
   （短序列被 `postprocess_burst` 截回 cap）。也就是说这个守卫在回归存在时仍会 exit 0。
   → 加了**与 token 无关的判定**：`Scheduler.schedule_burst()` 记录每个 burst 的
   `max_steps`、各序列 budget 与实留 token 数，并统计
   `burst_max_steps_violations` / `burst_reservation_violations`（有界计数）；
   工具读这些计数并**硬失败**。token 比较降级为次要 smoke，并在 docstring 里写明
   它为什么不能当检测器。
3. **P0-3 改了代码但没同步文档数字**。修好后 verdict 选**最大 batch（b32）**，
   报告 `host_free = 0.029`、`overlay = 0.011`；但 `docs/06` §7、`docs/07`、
   `docs/10` §1、`README` 仍写 b1 的 `0.020` / `0.014`。用文档自己的输入跑工具复现：
   `host-free 0.029 / overlay 0.011`。→ 全部改为"区间 + verdict 选取值"。
   同时修掉：`docs/06` §7 "15–135x"（应为 14.7–134.7x，上轮遗留）、
   `docs/07` §6/§10.4 里仍是 1.363/0.180/1.543/1728/0.690 的旧值（同步到
   1.364/0.181/1.545/1724/0.692）、以及 §1 里"build 已过"与"P0-1 仍需 build"的歧义。

**P0-1 修复：scalar batch 内核 occupancy 守卫**（§5.9 第 1 条）

问题：`compatibility()` 只对 `megakernel_batch_kernel == "wmma"` 施加 occupancy
上限，而默认是 `"scalar"`；scalar binding `decode_paged_batch` 不调用任何检查，
scalar launcher 在 `blocks_per_seq < LDG_ATTN_BLOCKS` 时只 `fprintf + return`，
Python 把上一步的 token 当新输出读走。触发：`decode_backend="megakernel"` +
`megakernel_batch_decode=True` + batch 11–32。

三层修复（与 WMMA 路径对齐）：
1. **`backend.py`**：`compatibility()` 去掉 `== "wmma"` 条件，对两种 kernel 都
   施加 `wmma_batch_limit()` 上限（WMMA 是 register-heavy 的，其 occupancy 是
   scalar 的保守下界）；
2. **`torch_bindings.cpp`**：`check_wmma_batch_supported()` → `check_batch_supported()`
   （通用化）；`decode_paged_batch` 加 `check_batch_supported()` + `output_tokens.fill_(-1)`
   （defense-in-depth：即使 launch 被 bypass，Python 也读到 -1 而非 stale token）；
3. **`kernel.cu`**：scalar launcher 的 inline `fprintf + return` 改为调用共享
   `ldg_batch_is_launchable()` backstop（DRY + 统一消息）。

测试更新：`test_batch_launch_guards.py`（backstop 计数 2→3、binding 计数 3→4、
新增 `decode_paged_batch` 到 definitions、新增 `fill_(-1)` 源码不变式测试）；
`test_megakernel_backend.py`（`test_scalar_kernel_is_not_subject_to_the_wmma_limit`
→ `test_scalar_kernel_is_also_subject_to_the_batch_limit`，断言反转）。

### 第 11 轮：四份独立 review → 修 3 个真缺陷，21 条记入 §5.9（`f85f5ba`）

对 engine/scheduler、tools、models/layers/metrics、kernel attention 各派一份
独立 review（前三块是上一轮因为 subagent 超时被中断、只做了抽查的部分）。

**修掉的真缺陷：**

1. 🔴 **burst 设备侧越界写**（§5.6）：`schedule_burst` 返回 `max(budget)` 却按各自
   budget 预留 block，而 CUDA burst 循环只有一个 batch 级 `max_steps` 且只按 EOS
   停用序列 ⇒ 混合 `max_tokens` 时短序列一直写到邻居的物理块里，静默污染其 KV。
   改成 `min(budget)` 且所有入选序列按同一长度预留。
2. 🔴 **`HardwareSpec` 用错带宽**（§5.1）：`name="A100-SXM4-80GB"` 配 1555 GB/s
   （那是 40GB 版）；实为 **2039 GB/s**。这一条 + 下一条就是 §5.1"物理上说不通"
   警报的全部来源。
3. 🔴 **roofline 把 tied LM head 算了两次**（§5.1）：Qwen3-0.6B 是
   `tie_word_embeddings: true`，embedding 是 gather，所以每步是
   **1.192 GB**（层 + 一次 LM head），不是 1.503 GB。`params_lm_head`/`total_params`
   重写，CLI 默认 `--tied-embedding`。
4. 🟠 **`metrics` 把毫秒当秒**：`aggregate_requests` 的 `ttft_ms`/`tpot_ms`/
   `itl_ms`/`e2e_ms` 被除以 1000 且没乘回来 ⇒ 所有报告/图表的延迟**低报 1000 倍**。
5. 🟡 `SamplingParams` 用真异常校验 `max_tokens >= 1`（原来只有 `temperature` 的
   bare assert，`-O` 下会被剥离，而 `max_tokens <= 0` 会一直解码到 KV 用尽）；
   `burst_eos_token` 把缺失的 EOS id 映射成 -1 哨兵而不是抛 TypeError；
   CUDA-graph 查表在 bucket 空档（9..15、17..31）退回 eager 而不是 StopIteration。

**未修但已逐条验证**的 21 条见 **§5.9**（P0：scalar 内核无 occupancy 守卫、
roofline probe 漏 LM head、verdict host overlay 跨 batch 错配；P1：各测量工具口径；
P2：latent；最后一节是纯简化）。

**这轮的教训**（写进 §5.0 的"教训 1–3"）：**模型错了，测试就是假证据**——

   **每个 lane** 都持有完整 score（softmax 权重逐 lane 作用到自己的 4 个输出维
   上），所以原来必须紧跟一次 `__shfl_sync(...,0)` 广播；改成 all-reduce 后这步
   没了。其它 20 多处调用点里只有 lane 0 消费结果，蝶形归约对它们等价。
2. `kernel.cu` 里 5 个 `#ifndef` 兜底默认值原来与 `build.py` 的真默认值**不一致**
   （§5.8）。改为一致，并加测试锁死。

**新增/重写的测试：**

- `tests/test_attention_reduction.py` 重写。旧版 `buggy_attention()` 建的是一个
  kernel 从来没做过的算法（每 lane 4 维 score、不做 warp 归约），所以它能"证明"
  一个不存在的缺陷。新版改为**忠实复刻 kernel 的分解**（按 warp 跨步认领位置、
  每 lane 4 维 QK 局部和、warp all-reduce、逐 lane 4 维 PV、跨 warp online-softmax
  合并），断言它与精确参考一致；同时保留"删掉归约真的会错"的反向测试和源码不变量。

  `kernel.cu` 的 `#ifndef` 兜底值与 `build.py` 的 `_env_int` 默认值，要求逐个相等。

## 5. 发现的问题 / 需要复核的地方

按严重程度排序。

### 5.0 ✅ 已澄清（原 🔴 误报）：attention **没有**"只用 4/128 维"的缺陷

第 9 轮（`2d21fd8`）宣称 `ldg_attention` 的 QK 打分与 PV 累加只覆盖 4/128 个 head
维、其余 124 维来自未初始化 shared memory。**这个诊断是错的，已回退**（第 10 轮）。
下面是逐条更正，两条独立仿真（我一份、另一个 agent 一份 IEEE-754 float32 仿真）
结论一致。

**（1）warp 归约就是"凑成完整 128 维点积"的那一步。** 每个 lane 算的是
`q[4j..4j+3] · k[4j..4j+3]`（4 元素局部和），`ldg_warp_reduce_sum` 把这 **32 个
lane 的局部和相加** ⇒ 正好是 `Σ_{d<128} q[d]·k[d]`。原诊断说"归约只是把*同维度*
结果相加"是把"每 lane 4 维"误读成了"所有 lane 都在算同一组 4 维"——**每 lane 的
4 维是不同的 4 维**，所以归约恰好补全其余 124 维。这是合法的维度划分。

**（2）输出 124 维不是残留数据。** `int out_base = lane_id * 4;` 在 `warp_id == 0`
分支里由该 warp 的**全部 32 个 lane**执行 ⇒ 覆盖 `s_out_acc[warp][0..127]`。
每个 warp 的行是 `HEAD_DIM = 128` 个 float（不是提交信息里说的 512 个
`[LDG_NUM_WARPS][HEAD_DIM]`），并且整行都被写满。PV 侧每个 lane 用**同一个**
warp-uniform 权重累加自己那 4 个 V 维，也是合法划分。

**（3）旧代码与被替换版本数值等价。** 两者只差 `out_base` vs `q_idx`（同一个值
`lane_id*4`）、一个等价的 `global_max` 初始化、以及注释；不存在任何
cache_len / 输入使二者结果不同。float32 仿真下逐 bit 相同。

**（4）网上流传的"×32 无害"说法也是错的，不要再用。** `softmax(c*S) == softmax(S)`
对一般的 `c>0` **不成立**（只有加性平移才不变），而且 kernel 里**根本没有 ×32**：
`attn_scale` 是真实、有意、只施加一次的 softmax 缩放。真正成立的不变式是
**跨 warp 合并时那个 `exp(s_max_score[w] - global_max)` 在分子分母同时出现而抵消**
（`final_out / total_sum_exp`），这是 5.0 的合并之所以精确的原因。

**（5）原诊断就算成立，也几乎不可能被发现。** 若当初缺的是 `__shfl_sync(...,0)`
广播（唯一一个"看起来像 bug"的点），在 `cache_len <= 16` 时根本不发作：每个 warp
只认领 ≤1 个 position，`weight = exp(score - max) = 1`。仿真显示要到
`cache_len >= 17` 才出现偏差（最大 0.32）。**短序列 smoke test 会放过它。**

**测试的教训（本轮最重要的一条）**：`tests/test_attention_reduction.py` 里的
`buggy_attention()` 复刻的是一个 **kernel 从来没做过的算法**（每 lane 4 维当成完整
score、不做 warp 归约），所以它能"证明"一个不存在的缺陷、并给出 1.2 的相对误差。
**一个测试只有在忠实复刻被测实现的分解时才证明得了东西**；把"意图"和"实现"
分开建模，是这类假结果的来源。

**回退后的最终状态**：`ldg_attention` 恢复为出问题前那份代码（已被两份仿真证明与
精确参考一致），只保留一处等价简化——`ldg_warp_reduce_sum` 改为
`__shfl_xor_sync` 蝶形 all-reduce，从而删掉 `ldg_attention` 里紧跟的那次
`__shfl_sync(...,0)` 广播。测试 `test_warp_reduce_result_reaches_every_lane`
同时接受"蝶形 all-reduce"和"down-reduce + 广播"两种正确写法，只禁止
"归约到 lane 0 却不广播"。

⚠️ 仍然**必须在 A100 上编译**（本地无 nvcc，§3 第 0 步）：改动虽小，但
`__shfl_xor_sync` 换 `__shfl_down_sync` 是真实指令变更，`RUN_MODE=build` 是第一道门。

### 5.1 ✅ 已澄清（原 ⚠️ 误报）：0.74 ms/step 的"物理上说不通"是常量错的产物

**结论：没有漏采，也没有物理矛盾。** 两个错常量叠加制造了这个警报：

1. `HardwareSpec` 写 `name="A100-SXM4-80GB"` 但填了 **1555 GB/s**——那是
   **40GB HBM2** 版的带宽；80GB HBM2e 是 **2039 GB/s**（服务器就是 80GB，
   见 [06](06_实际运行数据.md) §8 与 [08](08_服务器运行手册.md)）。
2. `RooflineModel.weight_bytes()` 把 embedding 表与 **tied** 的 LM head 当成两次
   311 MB 读取。Qwen3-0.6B 是 `tie_word_embeddings: true`，而 embedding 是
   **gather**（每步只读 batch 行），所以每步强制流量是
   **28 层 + 一次 LM head = 1.192 GB**，不是 1.503 GB（虚高 26%）。

**修正后的数字**（本轮已改代码与测试）：

| 口径 | 值 |
|---|---|
| 真实每步权重流量（tied，Qwen3-0.6B） | **1.192 GB** |
| A100-80GB 峰值带宽 | **2039 GB/s** |
| 真实权重下界 | **0.585 ms**（原文档说 0.967 ms） |
| 0.74 ms 实际达到 | **1611 GB/s = 79% 峰值 = 93% 实测可达带宽**（完全可能） |
| 若仍用旧的 1.503 GB | 2031 GB/s = **99.7% 峰值**（也**没有**超过 2039） |
| 实测可达带宽（服务器第 9 轮 probe） | **1728 GB/s = 84.7% 规格** |

也就是说：**0.74 ms 是贴着 HBM 墙的正常数字**，"超过规格 ⇒ 必然漏采"的推理链
不成立。`find_calibration_warnings` 只在隐含带宽真正超过标定值时才会告警，现在
0.77 ms 不再被误报（新增 `test_near_peak_measurement_is_not_flagged`）。

**服务器第 9 轮的 probe 实测证实了这一点**：可达带宽 1728 GB/s（84.7% 规格），
0.74 ms 隐含的 1611 GB/s 比它只低 7%，根本不需要"漏采"假设。
`tools/verdict.py` 自己的规则也是这个方向——`measured_bw >= implied_bw` 时判
"covers the whole step and the device really is at the HBM wall"
（[06](06_实际运行数据.md) §3）。

### 5.2 ❌ 已否决：`ldg_lm_head` 的 0.18 ms 不是"不可能"

311 MB @ 2039 GB/s = **0.153 ms**，所以 0.18 ms 约为峰值的 **85%**——对 scalar
FMA 的 LM head 来说是可信的。原论证依赖的是 40GB 的 1555 GB/s，已作废。
`--sections weights` 的对照测量仍然值得做（它能把"可信"变成"实测"），但不再是
为了证明一个矛盾。

### 5.3 未修：elementwise pass 只用到 2-3/80 个 block

`ldg_o_proj_mlp_wmma` 的 residual / post-norm / SiLU×Up 都是全 grid 跨步，
但 batch=8 时数据量只有 8192 元素 ⇒ **只有约 2 个 block 有活**，
其余 78 个 block 空转，**每个 pass 后面还跟一次全网格 `grid.sync()`**。
**没有改**，因为动 barrier 参与者集合有死锁风险。
低风险优化是只在有活的 block 里做 pass，但收益可能很小。

### 5.4 未修：`wmma_gemm` 的 shared-memory round-trip 是冗余

matrix B（权重）**直接 global load**，但 matrix A（激活）走
global → `s_a` smem → fragment。存在原因是 M 维 padding 要补零。
**没测过收益**，如果要做，注意 `load_matrix_sync` 的 16 字节对齐要求
（`k` 是 16 的倍数、行 stride = K 时成立）。

### 5.5 ⚠️ 部分已验证：合并后的 `kernel.cu` 还没编译过

服务器第 9 轮的 `RUN_MODE=build` 验证的是**服务器线**的 `kernel.cu`（`2d21fd8`
的 cosmetic rename + 批次守卫 + `ignore_eos` + barrier probe），**不是合并后
的这一份**。合并后 `kernel.cu` 换成了本地线版本，其中仍未被服务器编译过的改动：

- `ldg_warp_reduce_sum` 改为 `__shfl_xor_sync` 蝶形 all-reduce，并删掉
  `ldg_attention` 里紧跟的 `__shfl_sync(...,0)`（**唯一的新 CUDA 改动**；
  语义等价，但它仍是真实指令变更，必须先过 `RUN_MODE=build`）；

### 5.6 ✅ 已修（并升级）：burst 在设备侧越过短序列的 `max_tokens`

原怀疑只到"`postprocess_burst` 的截断是否正确"。实际缺陷更重：**Python 侧截断
是对的，但设备侧越界写入已经发生了。**

`Scheduler.schedule_burst` 原来返回 `max_steps = max(budget)`，却只按
**每个序列自己的 budget** 预留 block；而 CUDA burst 循环用**一个**batch 级
`max_steps`，且只在 EOS 时停用序列。于是混合 `max_tokens` 的 batch（例如
`SamplingParams(max_tokens=1)` 与 `max_tokens=200` 同批）里，短序列会一路推进到
batch 最大步数：`ldg_kv_ptr` **不做边界检查**，而 block table 的 padding 项是
**别的序列的物理块**，所以它的 K/V 被写进邻居的 slot，邻居随后的 attention 读到
污染数据。返回文本因为 Python 截断看起来完全正常。

**已修**：`max_steps` 改为所选序列的**最小** budget，并让每个入选序列都按这个
长度预留 block ⇒ 没有任何一行可能越界。代价是一个短序列会限制整批 burst 长度
（它随后 finish，其余序列下一步重新入选，不饿死）。
回归测试：`test_every_selected_seq_is_reserved_for_the_whole_burst`。

仍然**没在真机验证**的部分：`ignore_eos=True` 且恰好用完 / 超过 `max_tokens`
的边界组合，建议 `RUN_MODE=correctness` 专门跑一组。

### 5.7 已确认没问题的（省得重复查）

- `ldg_kv_ptr` 的算式与 `PagedKVCacheSpec.element_offset` **逐元素相等**
  （`tests/test_kv_cache_indexing.py`）；
- **`ldg_attention` 的 QK/PV 分解是正确的**——两份独立仿真（见 §5.0）都证明它
  与精确参考一致；"只用了 4/128 维"是误报；
- 每序列的 `kv_flag/attn_flag` 是 `+ seq_id` 独立副本，无跨序列串扰；
- WMMA 已完成 `__syncthreads()` 的 smem 覆写保护（K 循环内前后各一次）；
- `wmma_gemm` 的 `M < 16` 补齐有 0 值保护，且输出 buffer 按 16 行 padding 分配；
- batch 内核的 `blocks_per_seq * batch_size == grid_blocks` 恒成立，
  所以 `seq_id >= batch_size` 的早退**不会**触发（不会死锁）。

**教训 1（"有测试" ≠ "测到了"）**：上面这些"已确认没问题"当初是**逐项读代码**
得出的，而 `2d21fd8` 报的那个"attention bug"就号称藏在同一份文件里、被同一批
测试放过（`correctness_wmma_vs_scalar` 比的是 GEMM，`correctness_smoke` 只比
token）。下次怀疑某个算子时，先确认存在一个**直接验证该算子数值**的测试。

**教训 2（本轮新增，更重要）：模型错了，测试就是假证据。** §5.0 的测试之所以
"证明"了缺陷，是因为它的"错误算法"模型根本不像 kernel——它把"每 lane 的 4 维"
当成完整 score、不做 warp 归约。**忠实地把被测实现的分解抄进模型里**（跨步认领、
每 lane 局部和、warp 归约、合并顺序），再和参考比；否则测的只是模型作者的想象。
配套做法：让反向测试（"删掉归约真的会错"）和正向测试（"当前分解与参考一致"）
**并存**——只有正向测试无法区分"实现对"和"模型错"。

**教训 3：文档里的"已修复"也要能被推翻。** 第 9 轮把误报写进了本文档 §5.0，
而它读起来和真缺陷一模一样。写"已修复"时必须同时留下**可复算的证据**
（此处：仿真代码 + 参考实现 + 数值偏差），这样下一轮能直接推翻而不是只能相信。

### 5.8 🔴 已修复：`kernel.cu` 的 `#ifndef` 兜底值与 `build.py` 的真默认值不一致

`build.py:kernel_flags()` 总是把这些常量以 `-D` 传进去，所以 `kernel.cu` 里的
`#ifndef` 兜底在正常路径下是死代码——**这正是它危险的地方**：任何不经过
`build.py` 的编译路径（手写 `nvcc`、最小复现、别的 frontend）会静默拿到另一套
常量。实测有 5 处不一致：

| flag | `kernel.cu` 兜底 | `build.py` 默认 | 后果 |
|---|---|---|---|
| `LDG_ATTN_BLOCKS` | `NUM_Q_HEADS` = **16** | **8** | 批次上限 `grid / LDG_ATTN_BLOCKS` 从 10 掉到 5 |
| `LDG_LM_NUM_BLOCKS` | 1184 | 1280 | LM head 分块数变化 |
| `LDG_LM_BLOCK_SIZE` | 256 | 384 | LM head block 尺寸变化 |
| `LDG_PREFETCH_QK` | **1** | **0** | 静默打开 shipped 配置关掉的 prefetch 路径 |
| `LDG_PREFETCH_THREAD_STRIDE` | 1 | 10 | prefetch 步长差 10 倍 |

**已修**：5 个兜底值全部改成与 `build.py` 一致，并在 kernel.cu 顶部写清
"`build.py` 是权威来源"。**新增** `tests/test_batch_launch_guards.py::KernelFlagDefaultTests`
自动解析两边的值并要求逐个相等，以后再漂移会直接失败
（注意：`LDG_ATTN_BLOCKS=16` 不会立刻报错，它只是把批次上限砍半，
所以这个测试是必要的而不是锦上添花）。
