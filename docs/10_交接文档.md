## 5. 发现的问题 / 需要复核的地方

按严重程度排序。

### 5.0 ✅ 已澄清（原 🔴 误报）：attention **没有**"只用 4/128 维"的缺陷

第 9 轮（`2d21fd8`）宣称 `ldg_attention` 的 QK 打分与 PV 累加只覆盖 4/128 个 head
维、其余 124 维来自未初始化 shared memory。**这个诊断是错的，已回退**（第 10 轮）。
下面是逐条更正，两条独立仿真（我一份、另一个 agent 一份 IEEE-754 float32 仿真）
结论一致。

**（1）warp 归约就是"凑成完整 128 维点积"的那一步。** 每个 lane 算的是
`q[4j..4j+3] · k[4j..4j+3]`（4 元素局部和），`ldg_warp_reduce_sum` 把这 **32 个
lane 的局部和相加** ⇒ 正好是 `Σ_{d<128} q[d]·k[d]`。原诊断说"归约只是把*同维度*
结果相加"是把"每 lane 4 维"误读成了"所有 lane 都在算同一组 4 维"——**每 lane 的
4 维是不同的 4 维**，所以归约恰好补全其余 124 维。这是合法的维度划分。

**（2）输出 124 维不是残留数据。** `int out_base = lane_id * 4;` 在 `warp_id == 0`
分支里由该 warp 的**全部 32 个 lane**执行 ⇒ 覆盖 `s_out_acc[warp][0..127]`。
每个 warp 的行是 `HEAD_DIM = 128` 个 float（不是提交信息里说的 512 个
`[LDG_NUM_WARPS][HEAD_DIM]`），并且整行都被写满。PV 侧每个 lane 用**同一个**
warp-uniform 权重累加自己那 4 个 V 维，也是合法划分。

**（3）旧代码与被替换版本数值等价。** 两者只差 `out_base` vs `q_idx`（同一个值
`lane_id*4`）、一个等价的 `global_max` 初始化、以及注释；不存在任何
cache_len / 输入使二者结果不同。float32 仿真下逐 bit 相同。

**（4）网上流传的"×32 无害"说法也是错的，不要再用。** `softmax(c*S) == softmax(S)`
对一般的 `c>0` **不成立**（只有加性平移才不变），而且 kernel 里**根本没有 ×32**：
`attn_scale` 是真实、有意、只施加一次的 softmax 缩放。真正成立的不变式是
**跨 warp 合并时那个 `exp(s_max_score[w] - global_max)` 在分子分母同时出现而抵消**
（`final_out / total_sum_exp`），这是 5.0 的合并之所以精确的原因。

**（5）原诊断就算成立，也几乎不可能被发现。** 若当初缺的是 `__shfl_sync(...,0)`
广播（唯一一个"看起来像 bug"的点），在 `cache_len <= 16` 时根本不发作：每个 warp
只认领 ≤1 个 position，`weight = exp(score - max) = 1`。仿真显示要到
`cache_len >= 17` 才出现偏差（最大 0.32）。**短序列 smoke test 会放过它。**

**测试的教训（本轮最重要的一条）**：`tests/test_attention_reduction.py` 里的
`buggy_attention()` 复刻的是一个 **kernel 从来没做过的算法**（每 lane 4 维当成完整
score、不做 warp 归约），所以它能"证明"一个不存在的缺陷、并给出 1.2 的相对误差。
**一个测试只有在忠实复刻被测实现的分解时才证明得了东西**；把"意图"和"实现"
分开建模，是这类假结果的来源。

**回退后的最终状态**：`ldg_attention` 恢复为出问题前那份代码（已被两份仿真证明与
精确参考一致），只保留一处等价简化——`ldg_warp_reduce_sum` 改为
`__shfl_xor_sync` 蝶形 all-reduce，从而删掉 `ldg_attention` 里紧跟的那次
`__shfl_sync(...,0)` 广播。测试 `test_warp_reduce_result_reaches_every_lane`
同时接受"蝶形 all-reduce"和"down-reduce + 广播"两种正确写法，只禁止
"归约到 lane 0 却不广播"。

⚠️ 仍然**必须在 A100 上编译**（本地无 nvcc，§3 第 0 步）：改动虽小，但
`__shfl_xor_sync` 换 `__shfl_down_sync` 是真实指令变更，`RUN_MODE=build` 是第一道门。

### 5.1 ⚠️ 已实测的 0.74 ms/step 物理上说不通（最高优先）

一个 decode step 必须读 **1.503 GB** 权重，其中**仅 LM head（311 MB）@1555 GB/s
就要 0.2 ms**，全部权重至少 **0.967 ms**。而 nsys 记录 b1 cudagraph 的
**整个 decode kernel 只有 0.74 ms**，意味着 2031 GB/s > A100 规格。

**怀疑**：那次的 nsys 统计**只覆盖了部分 kernel**（漏采），或者 `--decode-steps`
用的是错的步数。**在 [09](06_实际运行数据.md) §3 的标定完成前，第 3、4 节的
device 侧结论都只能算强假设。**

### 5.2 怀疑：`ldg_lm_head` 的 0.18 ms 同样不可能

b1 megakernel 的 nsys 记录里 `ldg_lm_head` 只有 **0.18 ms**，但 LM head 权重
311 MB ⇒ 至少 0.2 ms，且它是 scalar FMA（无张量核）——实际只会更慢。
**同一个漏采怀疑**。建议用 `tools/bench_roofline_a100.py --sections weights`
单独测一次 LM head 权重流式读作为对照。

### 5.3 怀疑：elementwise pass 只用到 2-3/80 个 block

`ldg_o_proj_mlp_wmma` 的 residual / post-norm / SiLU×Up 都是全 grid 跨步，
但 batch=8 时数据量只有 8192 元素 ⇒ **只有约 2 个 block 有活**，
其余 78 个 block 空转，**每个 pass 后面还跟一次全网格 `grid.sync()`**。
我**没有改**，因为动 barrier 参与者集合有死锁风险。
低风险优化是只在有活的 block 里做 pass，但收益可能很小（barrier 0.55 ms/token）。

### 5.4 怀疑：`wmma_gemm` 的 shared-memory round-trip 是冗余

matrix B（权重）**直接 global load**，但 matrix A（激活）走
global → `s_a` smem → fragment。存在原因是 M 维 padding 要补零。
**没测过收益**，如果要做，注意 `load_matrix_sync` 的 16 字节对齐要求
（`k` 是 16 的倍数、行 stride = K 时成立）。

### 5.5 未验证：最近几轮的 CUDA 改动都没编译过

见 §3 第 0 步。改动集中在：

- `ldg_warp_reduce_sum` 改为 `__shfl_xor_sync` 蝶形 all-reduce，并删掉
  `ldg_attention` 里紧跟的 `__shfl_sync(...,0)`（**本轮唯一的新 CUDA 改动**；
  语义等价，但它仍是真实指令变更，必须先过 `RUN_MODE=build`）；
- `ldg_wmma_max_supported_batch` / `ldg_batch_is_launchable`（批次上限守卫）；
- `ldg_update_step_batch` 的 `eos_token >= 0` 判断（ignore_eos 支持）；
- `barrier_probe` 的 `__launch_bounds__(512,1)`。

本地只能做静态检查：brace/paren 配平、`compileall`、源码不变式测试。
**没有 nvcc，无法编译**。`RUN_MODE=build` 是第一道门。

### 5.6 怀疑：`_should_burst` 放行 ignore_eos 后的交互

我只是让 `eos_token=-1` 表示"永不停止"，但**没有在真机上验证**：
burst 跑满 `max_steps` 后 `postprocess_burst` 的截断是否仍然正确
（`seq.max_tokens` 边界）、以及 `ignore_eos=True` 时 LM head 的 argmax
是否会取到某个特殊 id 导致长度不符。建议 `RUN_MODE=correctness` 时
专门跑一组 `ignore_eos=True` + `max_tokens` 边界（恰好用完 / 超过）。

### 5.7 已确认没问题的（省得重复查）

- `ldg_kv_ptr` 的算式与 `PagedKVCacheSpec.element_offset` **逐元素相等**
  （`tests/test_kv_cache_indexing.py`）；
- **`ldg_attention` 的 QK/PV 分解是正确的**——两份独立仿真（见 §5.0）都证明它
  与精确参考一致；"只用了 4/128 维"是误报；
- 每序列的 `kv_flag/attn_flag` 是 `+ seq_id` 独立副本，无跨序列串扰；
- WMMA 已完成 `__syncthreads()` 的 smem 覆写保护（K 循环内前后各一次）；
- `wmma_gemm` 的 `M < 16` 补齐有 0 值保护，且输出 buffer 按 16 行 padding 分配；
- batch 内核的 `blocks_per_seq * batch_size == grid_blocks` 恒成立，
  所以 `seq_id >= batch_size` 的早退**不会**触发（不会死锁）。

**教训 1（"有测试" ≠ "测到了"）**：上面这些"已确认没问题"当初是**逐项读代码**
得出的，而 `2d21fd8` 报的那个"attention bug"就号称藏在同一份文件里、被同一批
测试放过（`correctness_wmma_vs_scalar` 比的是 GEMM，`correctness_smoke` 只比
token）。下次怀疑某个算子时，先确认存在一个**直接验证该算子数值**的测试。

**教训 2（本轮新增，更重要）：模型错了，测试就是假证据。** §5.0 的测试之所以
"证明"了缺陷，是因为它的"错误算法"模型根本不像 kernel——它把"每 lane 的 4 维"
当成完整 score、不做 warp 归约。**忠实地把被测实现的分解抄进模型里**（跨步认领、
每 lane 局部和、warp 归约、合并顺序），再和参考比；否则测的只是模型作者的想象。
配套做法：让反向测试（"删掉归约真的会错"）和正向测试（"当前分解与参考一致"）
**并存**——只有正向测试无法区分"实现对"和"模型错"。

**教训 3：文档里的"已修复"也要能被推翻。** 第 9 轮把误报写进了本文档 §5.0，
而它读起来和真缺陷一模一样。写"已修复"时必须同时留下**可复算的证据**
（此处：仿真代码 + 参考实现 + 数值偏差），这样下一轮能直接推翻而不是只能相信。

### 5.8 🔴 已修复：`kernel.cu` 的 `#ifndef` 兜底值与 `build.py` 的真默认值不一致

`build.py:kernel_flags()` 总是把这些常量以 `-D` 传进去，所以 `kernel.cu` 里的
`#ifndef` 兜底在正常路径下是死代码——**这正是它危险的地方**：任何不经过
`build.py` 的编译路径（手写 `nvcc`、最小复现、别的 frontend）会静默拿到另一套
常量。实测有 5 处不一致：

| flag | `kernel.cu` 兜底 | `build.py` 默认 | 后果 |
|---|---|---|---|
| `LDG_ATTN_BLOCKS` | `NUM_Q_HEADS` = **16** | **8** | 批次上限 `grid / LDG_ATTN_BLOCKS` 从 10 掉到 5 |
| `LDG_LM_NUM_BLOCKS` | 1184 | 1280 | LM head 分块数变化 |
| `LDG_LM_BLOCK_SIZE` | 256 | 384 | LM head block 尺寸变化 |
| `LDG_PREFETCH_QK` | **1** | **0** | 静默打开 shipped 配置关掉的 prefetch 路径 |
| `LDG_PREFETCH_THREAD_STRIDE` | 1 | 10 | prefetch 步长差 10 倍 |

**已修**：5 个兜底值全部改成与 `build.py` 一致，并在 kernel.cu 顶部写清
"`build.py` 是权威来源"。**新增** `tests/test_batch_launch_guards.py::KernelFlagDefaultTests`
自动解析两边的值并要求逐个相等，以后再漂移会直接失败
（注意：`LDG_ATTN_BLOCKS=16` 不会立刻报错，它只是把批次上限砍半，
所以这个测试是必要的而不是锦上添花）。
