**做了什么**（`docs/13 §5` 阶段 0.1–0.4）：

1. **新 backend `decode_backend="megakernel-tg"`**（`config.py` 的
   `VALID_DECODE_BACKENDS`）：`backends/megakernel/taskgraph.py` 里的
   `TaskGraphDecoder` 持有 weights / schedule 缓存（BS 1/2/4/8）/ scratch / bars，
   `decode_rows()` 一步一 launch 调 `tg_zero_regions` + `tg_decode_step`。
   它与冻结的 `Decoder` 同接口（`step` / `step_batch` / `decode_rows`），
   所以 `MegakernelBackend` 不需要在每个调用点分支。
2. **两处按 backend 字符串分流的门改为共享谓词 `is_megakernel_backend()`**
   （`model_runner.py`：是否 capture CUDA graph、是否建 megakernel）。
   原来是内联 `!= "megakernel"`——**加一个 backend 就会静默走 torch**，
   而 benchmark 会把它报成 megakernel 结果。
   burst 是另一个问题，走 `supports_no_sync_burst()`（只有冻结的 `megakernel`
   有设备侧连跑 N 步的 burst）；`run_burst()` 在 try 之前短路，否则它返回的
   fallback 哨兵会被 `except` 误判成"kernel 已跑过"而毒化 CUDA。
3. **`last_backend_used` 报具体 backend 名**，`compare.py` 用
   `MEGAKERNEL_FAMILY` 集合判定 correctness/fallback 门（`docs/05 §6` 红线：
   fallback 行不算 megakernel 结果）。
4. **`benchmarks/compare.py`**：`BACKEND_CONFIGS` 加 `megakernel-tg`；
   默认 `--backends` 收窄为 `torch-eager,torch-cudagraph,megakernel-tg`
   （旧 `megakernel` / `-wmma` / `-burst` 移出默认但保留可用）；
   新增 `--grid --grid-lengths`，能真正表达 `docs/13 §1.3` 的
   batch × context 网格（原来只有两个固定形状）。
5. **`SERVER_COMMANDS.txt`**：新增 `RUN_MODE=taskgraph-baseline`
   （correctness → 主表 → `tools/account_decode` 四口径账）；
   修掉 `run_taskgraph_perf` 里 `--context-len 1,128,512,2048` 传给
   `type=int` 的崩溃；`MODEL` 同时导出 `NANOVLLM_MODEL_PATH` 与
   `QWEN3_MODEL_PATH`（两套变量名原本会有一个落回旧默认值）。
6. **`tools/bench_taskgraph.py`**：`--context-len` 改为接受列表并跑
   batch × context 全交叉，JSON 里带上 `context_len`。

### 第 16 轮：收尾——清掉 6 个运行时会踩的问题 + 冻结已知限制

项目在此冻结。本轮只改"会让用户踩坑"的代码，其余 P1/P2 明确冻结（§5.9 开头）。
所有改动都带测试；**没有 CUDA 改动，不需要重新 build**，但服务器上需要重跑
单测（`test_burst` / `test_config` 在本地因缺 numpy/transformers 无法运行）。

**修的 6 项（详见 §5.9 对应条目）**：

1. **#13 burst 零进展死循环**（`llm_engine.py`）：`token_logs` 全 -1 时
   `total_new == 0`、没有序列完成、`_should_burst` 仍为真 ⇒ `while not
   is_finished()` 永远不会结束。现在检测到零进展就 `_burst_disabled=True` +
   `RuntimeWarning` + 把该步交给 `_step_normal`（`postprocess_burst` 已
   `trim_burst`，回退安全）。
2. **#12 burst 选择没有尊重内核批次上限**（`burst_policy.py` + `llm_engine.py`）：
   `megakernel_burst_batch` 高于 `wmma_batch_limit` 时，burst binding 的
   `TORCH_CHECK` 会在 `run_burst` 里抛异常并把 `_cuda_poisoned=True`，**杀死引擎**
   而不是回退。新增 torch-free 的 `clamp_burst_batch()`，
   `LLMEngine._burst_batch_limit()` 每进程只查一次并缓存（避免把 CUDA 驱动查询
   带回每步热路径），`_step_burst` 用它钳制 `schedule_burst(max_batch=...)`。
3. **#8 正确性门在序列数不等时静默 PASS**（`tools/correctness_wmma_vs_scalar.py`）：
   `zip(scalar, wmma)` 会丢掉多出来的请求。现在先比请求数，不等直接 FAIL。
4. **#9 "回退 cudagraph" 表述不准**：`decode_backend="megakernel"` 时
   `use_cudagraph=False`，同引擎回退实际是 **eager**。改准了 `compatibility()` /
   `burst_policy` 的 reason 字符串与 docs/01 §0/§1、docs/07 §7.4/§10.4。
5. **#17 `max_model_len` 冲突静默整体回退**：`Config` 默认 4096，megakernel 契约
   要求 2048，只写 `decode_backend="megakernel"` 会**每个请求都回退**。现在
   `LLMEngine.__init__` 发 `RuntimeWarning` 明说。
6. **#15/#16 RoPE 解析分叉 + 未实现的 `rope_type` 被静默忽略**：新增 torch-free 的
   `src/nanovllm/rope_config.py`，`models/qwen3.py` 与
   `backends/megakernel/model.py` 共用 `resolve_rope_theta()`

   里"Qwen3-0.6B 把 theta 放在 `rope_scaling`"的错误说法（实际是顶层
   `rope_theta` + `rope_scaling: null`）。

**新增测试 24 个**：`tests/test_rope_config.py`(13，含"两条路径必须共用同一个

## 5. 发现的问题 / 需要复核的地方

按严重程度排序。

### 5.0 ✅ 已澄清（原 🔴 误报）：attention **没有**"只用 4/128 维"的缺陷

第 9 轮（`2d21fd8`）宣称 `ldg_attention` 的 QK 打分与 PV 累加只覆盖 4/128 个 head
维、其余 124 维来自未初始化 shared memory。**这个诊断是错的，已回退**（第 10 轮）。
下面是逐条更正，两条独立仿真（我一份、另一个 agent 一份 IEEE-754 float32 仿真）
结论一致。

**（1）warp 归约就是"凑成完整 128 维点积"的那一步。** 每个 lane 算的是
`q[4j..4j+3] · k[4j..4j+3]`（4 元素局部和），`ldg_warp_reduce_sum` 把这 **32 个
lane 的局部和相加** ⇒ 正好是 `Σ_{d<128} q[d]·k[d]`。原诊断说"归约只是把*同维度*
结果相加"是把"每 lane 4 维"误读成了"所有 lane 都在算同一组 4 维"——**每 lane 的
4 维是不同的 4 维**，所以归约恰好补全其余 124 维。这是合法的维度划分。

**（2）输出 124 维不是残留数据。** `int out_base = lane_id * 4;` 在 `warp_id == 0`
分支里由该 warp 的**全部 32 个 lane**执行 ⇒ 覆盖 `s_out_acc[warp][0..127]`。
每个 warp 的行是 `HEAD_DIM = 128` 个 float（不是提交信息里说的 512 个
`[LDG_NUM_WARPS][HEAD_DIM]`），并且整行都被写满。PV 侧每个 lane 用**同一个**
warp-uniform 权重累加自己那 4 个 V 维，也是合法划分。

**（3）旧代码与被替换版本数值等价。** 两者只差 `out_base` vs `q_idx`（同一个值
`lane_id*4`）、一个等价的 `global_max` 初始化、以及注释；不存在任何
cache_len / 输入使二者结果不同。float32 仿真下逐 bit 相同。

**（4）网上流传的"×32 无害"说法也是错的，不要再用。** `softmax(c*S) == softmax(S)`
对一般的 `c>0` **不成立**（只有加性平移才不变），而且 kernel 里**根本没有 ×32**：
`attn_scale` 是真实、有意、只施加一次的 softmax 缩放。真正成立的不变式是
**跨 warp 合并时那个 `exp(s_max_score[w] - global_max)` 在分子分母同时出现而抵消**
（`final_out / total_sum_exp`），这是 5.0 的合并之所以精确的原因。

**（5）原诊断就算成立，也几乎不可能被发现。** 若当初缺的是 `__shfl_sync(...,0)`
广播（唯一一个"看起来像 bug"的点），在 `cache_len <= 16` 时根本不发作：每个 warp
只认领 ≤1 个 position，`weight = exp(score - max) = 1`。仿真显示要到
`cache_len >= 17` 才出现偏差（最大 0.32）。**短序列 smoke test 会放过它。**

**测试的教训（本轮最重要的一条）**：`tests/test_attention_reduction.py` 里的
`buggy_attention()` 复刻的是一个 **kernel 从来没做过的算法**（每 lane 4 维当成完整
score、不做 warp 归约），所以它能"证明"一个不存在的缺陷、并给出 1.2 的相对误差。
**一个测试只有在忠实复刻被测实现的分解时才证明得了东西**；把"意图"和"实现"
分开建模，是这类假结果的来源。

**回退后的最终状态**：`ldg_attention` 恢复为出问题前那份代码（已被两份仿真证明与
精确参考一致），只保留一处等价简化——`ldg_warp_reduce_sum` 改为
`__shfl_xor_sync` 蝶形 all-reduce，从而删掉 `ldg_attention` 里紧跟的那次
`__shfl_sync(...,0)` 广播。测试 `test_warp_reduce_result_reaches_every_lane`
同时接受"蝶形 all-reduce"和"down-reduce + 广播"两种正确写法，只禁止
"归约到 lane 0 却不广播"。

⚠️ 仍然**必须在 A100 上编译**（本地无 nvcc，§3 第 0 步）：改动虽小，但
`__shfl_xor_sync` 换 `__shfl_down_sync` 是真实指令变更，`RUN_MODE=build` 是第一道门。

### 5.1 ✅ 已澄清（原 ⚠️ 误报）：0.74 ms/step 的"物理上说不通"是常量错的产物

**结论：没有漏采，也没有物理矛盾。** 两个错常量叠加制造了这个警报：

1. `HardwareSpec` 写 `name="A100-SXM4-80GB"` 但填了 **1555 GB/s**——那是
   **40GB HBM2** 版的带宽；80GB HBM2e 是 **2039 GB/s**（服务器就是 80GB，
   见 [06](06_实际运行数据.md) §8 与 [08](08_服务器运行手册.md)）。
2. `RooflineModel.weight_bytes()` 把 embedding 表与 **tied** 的 LM head 当成两次
   311 MB 读取。Qwen3-0.6B 是 `tie_word_embeddings: true`，而 embedding 是
   **gather**（每步只读 batch 行），所以每步强制流量是
   **28 层 + 一次 LM head = 1.192 GB**，不是 1.503 GB（虚高 26%）。

**修正后的数字**（本轮已改代码与测试）：

| 口径 | 值 |
|---|---|
| 真实每步权重流量（tied，Qwen3-0.6B） | **1.192 GB** |
| A100-80GB 峰值带宽 | **2039 GB/s** |
| 真实权重下界 | **0.585 ms**（原文档说 0.967 ms） |
| 0.74 ms 实际达到 | **1611 GB/s = 79% 峰值 = 95% 实测可达带宽**（完全可能） |
| 若仍用旧的 1.503 GB | 2031 GB/s = **99.7% 峰值**（也**没有**超过 2039） |
| 实测可达带宽（第 9 轮 1728，第 14 轮重跑 **1699 GB/s = 83.3% 规格**） | **1699 GB/s** |

也就是说：**0.74 ms 是贴着 HBM 墙的正常数字**，"超过规格 ⇒ 必然漏采"的推理链
不成立。`find_calibration_warnings` 只在隐含带宽真正超过标定值时才会告警，现在
0.77 ms 不再被误报（新增 `test_near_peak_measurement_is_not_flagged`）。

**probe 实测证实了这一点**：第 14 轮重跑的可达带宽 1699 GB/s（83.3% 规格），
0.74 ms 隐含的 1611 GB/s 比它低 5%，根本不需要"漏采"假设。
`tools/verdict.py` 自己的规则也是这个方向——`measured_bw >= implied_bw` 时判
"covers the whole step and the device really is at the HBM wall"
（[06](06_实际运行数据.md) §3）。

### 5.2 ❌ 已否决：`ldg_lm_head` 的 0.18 ms 不是"不可能"

311 MB @ 2039 GB/s = **0.153 ms**，所以 0.18 ms 约为峰值的 **85%**——对 scalar
FMA 的 LM head 来说是可信的。原论证依赖的是 40GB 的 1555 GB/s，已作废。
`--sections weights` 的对照测量仍然值得做（它能把"可信"变成"实测"），但不再是
为了证明一个矛盾。

### 5.3 未修：elementwise pass 只用到 2-3/80 个 block

`ldg_o_proj_mlp_wmma` 的 residual / post-norm / SiLU×Up 都是全 grid 跨步，
但 batch=8 时数据量只有 8192 元素 ⇒ **只有约 2 个 block 有活**，
其余 78 个 block 空转，**每个 pass 后面还跟一次全网格 `grid.sync()`**。
**没有改**，因为动 barrier 参与者集合有死锁风险。
低风险优化是只在有活的 block 里做 pass，但收益可能很小。

### 5.4 未修：`wmma_gemm` 的 shared-memory round-trip 是冗余

matrix B（权重）**直接 global load**，但 matrix A（激活）走
global → `s_a` smem → fragment。存在原因是 M 维 padding 要补零。
**没测过收益**，如果要做，注意 `load_matrix_sync` 的 16 字节对齐要求
（`k` 是 16 的倍数、行 stride = K 时成立）。

### 5.6 ✅ 已修（并升级）→ 已在 A100 真机验证（第 15 轮 `735728b`）

原怀疑只到"`postprocess_burst` 的截断是否正确"。实际缺陷更重：**Python 侧截断
是对的，但设备侧越界写入已经发生了。**

`Scheduler.schedule_burst` 原来返回 `max_steps = max(budget)`，却只按
**每个序列自己的 budget** 预留 block；而 CUDA burst 循环用**一个**batch 级
`max_steps`，且只在 EOS 时停用序列。于是混合 `max_tokens` 的 batch（例如
`SamplingParams(max_tokens=1)` 与 `max_tokens=200` 同批）里，短序列会一路推进到
batch 最大步数：`ldg_kv_ptr` **不做边界检查**，而 block table 的 padding 项是
**别的序列的物理块**，所以它的 K/V 被写进邻居的 slot，邻居随后的 attention 读到
污染数据。返回文本因为 Python 截断看起来完全正常。

**已修**：`max_steps` 改为所选序列的**最小** budget，并让每个入选序列都按这个
长度预留 block ⇒ 没有任何一行可能越界。代价是一个短序列会限制整批 burst 长度
（它随后 finish，其余序列下一步重新入选，不饿死）。
回归测试：`test_every_selected_seq_is_reserved_for_the_whole_burst`。

**GPU 验证（`tools/correctness_burst_mixed.py`）**：两道判定——
(1) `Scheduler.schedule_burst` 的 tripwire 计数（`max_steps == min(budget)`、
每个入选序列实留 token ≥ `max_steps`）；(2) token 比较（次要，因为越界污染与
已知 bf16 ulp 级联在 token 上不可区分）。

⚠️ **构造这个测试时 `--short-tokens` 必须 ≥ 2**：prefill 会产出第一个 completion
token，`max_tokens=1` 的序列在 prefill 就 FINISHED，永远不进 burst，于是
`min(budget) == max(budget)`、tripwire 结构上不可能触发——第 14 轮就是这样
"通过"的（报 `bursts_observed=4`/0 违规，其实全是均匀预算的 burst）。
现在工具要求 `mixed_budget_bursts >= 1`，否则硬失败。`--short-tokens 2`（prompt
250、cap 64）才是真正会越界的取值：`len(seq)=252` 只占 1 个 256 块，跑 64 步会
写到 padding 项。

**A100 真机验证（第 15 轮 `735728b`，单卡 A100，`--short-tokens 2`）**：✅ 通过。
`RUN_MODE=correctness` 全套件 46 PASS / 32 CASCADE / 0 FAIL。混合 burst 块
b2/b4/b5 每个 case 的 `megakernel-burst` 均 `bursts_observed=5`、
`mixed_budget_bursts=1`、`max_steps_violations=0`、`reservation_violations=0`
（原始数值见 §2 第 15 轮表格）。第一个 burst 是真混合预算（短序列剩余 budget=1 对长序列 budget=64），
`last_budgets=[6]` 是最后一个 burst（长序列 199 = 1（混合 burst）+ 64+64+64+6 的尾部）。两道硬门
同时成立，§5.6 标为**已在真机验证**。

### 5.7 已确认没问题的（省得重复查）

- `ldg_kv_ptr` 的算式与 `PagedKVCacheSpec.element_offset` **逐元素相等**
  （`tests/test_kv_cache_indexing.py`）；
- **`ldg_attention` 的 QK/PV 分解是正确的**——两份独立仿真（见 §5.0）都证明它
  与精确参考一致；"只用了 4/128 维"是误报；
- 每序列的 `kv_flag/attn_flag` 是 `+ seq_id` 独立副本，无跨序列串扰；
- WMMA 已完成 `__syncthreads()` 的 smem 覆写保护（K 循环内前后各一次）；
- `wmma_gemm` 的 `M < 16` 补齐有 0 值保护，且输出 buffer 按 16 行 padding 分配；
- batch 内核的 `blocks_per_seq * batch_size == grid_blocks` 恒成立，
  所以 `seq_id >= batch_size` 的早退**不会**触发（不会死锁）。

**教训 1（"有测试" ≠ "测到了"）**：上面这些"已确认没问题"当初是**逐项读代码**
得出的，而 `2d21fd8` 报的那个"attention bug"就号称藏在同一份文件里、被同一批
测试放过（`correctness_wmma_vs_scalar` 比的是 GEMM，`correctness_smoke` 只比
token）。下次怀疑某个算子时，先确认存在一个**直接验证该算子数值**的测试。

**教训 2（本轮新增，更重要）：模型错了，测试就是假证据。** §5.0 的测试之所以
"证明"了缺陷，是因为它的"错误算法"模型根本不像 kernel——它把"每 lane 的 4 维"
当成完整 score、不做 warp 归约。**忠实地把被测实现的分解抄进模型里**（跨步认领、
每 lane 局部和、warp 归约、合并顺序），再和参考比；否则测的只是模型作者的想象。
配套做法：让反向测试（"删掉归约真的会错"）和正向测试（"当前分解与参考一致"）
**并存**——只有正向测试无法区分"实现对"和"模型错"。

**教训 3：文档里的"已修复"也要能被推翻。** 第 9 轮把误报写进了本文档 §5.0，
而它读起来和真缺陷一模一样。写"已修复"时必须同时留下**可复算的证据**
（此处：仿真代码 + 参考实现 + 数值偏差），这样下一轮能直接推翻而不是只能相信。

### 5.8 🔴 已修复：`kernel.cu` 的 `#ifndef` 兜底值与 `build.py` 的真默认值不一致
