## 1. 当前状态（截至 commit `8110a2c`）

**项目最终形态已确定并落地**：

```text
batch == 1  ->  megakernel persistent/paged（一次 cooperative launch + 设备侧 EOS）
batch >= 2  ->  回退 torch-cudagraph（SM 用满 + tensor core + 无 padding）
```

**已完成且有证据**：

- batch=1 端到端超过 cudagraph **1.04–1.31x**（[09](06_实际运行数据.md) §2/§6）；
- batch>1 已加三层守卫，超限**显式回退**而不是静默错答（§2 第 4 轮）；
- KV cache 完全复用 nano-vLLM，索引算式与 `PagedKVCacheSpec` 有逐元素单测（[03](03_Megakernel设计说明.md) §4）；
- roofline / host-device 账本 / device 下界 probe / 二值判定工具链已就绪（[04](04_基准测试方法.md) §5）。

**未完成**：

- 🔜 **probe 从未在 A100 上跑过**——最关键的遗留项（§3 第 1 条）；
- ⚠️ 已实测数据里有一个**物理上说不通的数字**（0.74 ms/step ⇒ 2031 GB/s，超过
  A100 规格），必须先标定（§5 第 1 条）；
- ❌ attention 与 LM head 仍是 scalar，未上张量核（§3 第 4 条）。

**本地测试状态**：`PYTHONPATH=src python -m unittest discover -s tests` 共 194 个用例；
无 torch 环境下 4 个 error 属环境缺失（`torch`/`transformers`/`xxhash`），不是回归。

## 2. 最近做了什么

按时间倒序，每条都带 commit，便于 `git show` 追溯。

### 第 8 轮：KV 越界读 + 对比公平性（`8110a2c`）

**发现的真缺陷：**

1. **KV 越界读**：`ModelRunner.prepare_block_tables` 用 **-1** 右补齐短序列的
   block table，而 megakernel 直接消费该张量，`ldg_kv_ptr` 把 -1 当物理块号算出
   **负 offset，读到 KV cache 分配区之前**。torch 路径不受影响（flash-attn 用
   `cache_seqlens` 约束 + cudagraph 自带 buffer zero）。→ 改成 padding 用物理块 0；
   新增 `tests/test_kv_cache_indexing.py`（含从源码读 padding 值的回归锁）。
2. **主 A/B 表从未测到 burst**：`_should_burst` 见到任何 `ignore_eos=True` 就回退，
   而受控套件全用 `ignore_eos=True`，所以主表测的是 step-wise 路径。
   → 设备侧 EOS 现在把 `eos_token < 0` 视为"永不停止"；整批 ignore_eos 可走 burst
   （混合批仍回退）；策略抽到 torch-free 的 `engine/burst_policy.py`。

**已记录未修**：cudagraph 的 batch bucket padding（batch=10 多付 60%）；
attention/LM head 的硬件加速覆盖不对称。

### 第 7 轮：批次上限的静默错答（`507a6db`）

WMMA batch kernel 真实上限是 `grid/LDG_ATTN_BLOCKS = 80/8 = 10`，但代码里
`LDG_MAX_BATCH=32`、binding 的 `TORCH_CHECK`、`MAX_BATCH_SIZE` 全说 32。
超限时 launch 只打 stderr 就 `return`，void binding 仍报成功，Python 把**上一步的
token** 当新输出读走。
→ 三层守卫：`ldg_wmma_max_supported_batch()`（从真实 occupancy 推导）、
`check_wmma_batch_supported()`（launch 前 `TORCH_CHECK`）、
`backend.compatibility()`（回退 cudagraph 并给原因）；
`tests/test_batch_launch_guards.py` 用源码不变式锁住三处一致。

### 第 4–5 轮：二值判定 + 探针可测性（`22229df` / `b787d1a` / `b075754`）

- `tools/verdict.py`：读三个 probe JSON，输出**六种 verdict 枚举** + 证据 + 行动；
  含两个诚实护栏（`DEVICE_AT_FLOOR`、`DEVICE_BOUND_CUDA_GRAPH`）；
  18→24 个单测锁阈值。
- 两个 GPU 探针加了注入缝（`module` / `torch_module` / `weights`），
  用 fake 跑通编排逻辑；`tests/test_probe_orchestration.py` 还把 probe 输出喂给
  verdict，**提前抓住 schema 漂移**。
- cooperative preflight：编译前检查 grid 是否可 launch；barrier probe 补
  `__launch_bounds__(512,1)` 与生产一致。

### 第 3 轮：探针 barrier 与生产对齐（`aefeb09`）

探针 barrier 与 `AtomicGridSync` 语义不一致：用 `==` + 到达后读 generation
（ABA 风险）、用 `__threadfence()`（生产用 `fence.acq_rel.gpu`）。
→ 改成与生产同构；`tests/test_probe_fidelity.py` 直接 diff 两处源码防漂移。

### 第 1–2 轮：账本与工具（`fe052c8` … `7e8038d`）

- `src/nanovllm/roofline.py`：纯 Python roofline（1.503 GB/step、0.967 ms 下界、
  batch≈243 转 compute-bound），常量与 `kernel.cu` 做契约测试；
- `tools/account_decode.py`：每步墙钟/GPU/host 残差，吃 compare 与 crossover 两种 JSON；
- `tools/bench_roofline_a100.py` / `bench_burst_lower_bound.py`：带宽标定 +
  device 下界 probe + host-free replay；
- 文档补引 MPK(OSDI'26) / TaxBreak / Cohere / Ada-MK，并修正 megaQwen 的 owner
  （`Infatoshi`，不是 `NoneBone`）。

## 5. 发现的问题 / 需要复核的地方

按严重程度排序。

### 5.0 🔴 已修复：attention 只用了 128 维中的 4 维（本轮全量 review 发现）

`ldg_attention` 的 QK 打分与 PV 累加**只用到了 lane 自己的 4 个 head 维度**：

```cpp
int q_idx = lane_id * 4;
q_local[0..3] = q_head[q_idx + 0..3];
score += q_local[0] * k_ptr[0] + ... + q_local[3] * k_ptr[3];  // 只有 4 维
score = ldg_warp_reduce_sum(score) * attn_scale;               // 归约的是"同一 4 维"
...
out_acc[0..3] = ... weight * v_ptr[0..3];                      // PV 也只有 4 维
out_head[lane_id*4 + 0..3] = ...
```

**这不是"每 lane 算一部分、归约成全量"的正确分解**：每个 lane 算的是
`q[4j..4j+3] · k[4j..4j+3]`（4 元素点积），warp 归约只是把这 32 个 lane 的
*同维度* 结果相加，并不覆盖其余 124 维。后果：

1. 每个 position 的 score 只反映 **4/128** 的 query-key 相似度；
2. PV 只累加了 **v[0..3]**，其余 **124 个输出维度**（`out_head[4..127]`）来自
   未初始化的 shared memory（`s_out_acc` 是被写到 `[warp][lane_id*4]`，
   而每个 warp 只有 32 lane ⇒ 只有前 128 个元素被覆盖，**其余 124 个元素的
   来源是残留数据**）。

**为什么之前的测试没发现**：现有的两条正确性证据都测不到它——
`correctness_smoke` 只比 token，而 `correctness_wmma_vs_scalar` 是
**WMMA GEMM vs scalar GEMM**，两条路径共用同一个 `ldg_attention`
（`megakernel_batch_kernel` 只切换 GEMM），所以它验证的是 GEMM 一致，
不是 attention 正确。

**已修**（本轮）：score 改成 warp 归约的**完整 128 维点积**，PV 按 lane 自己的
4 维累加、跨 warp 用标准 online-softmax max/rescale 合并；`s_out_acc` 的写入
改成 `[q_idx + d]`，输出写回 `out_head[q_idx + d]`。

**新增回归测试** `tests/test_attention_reduction.py`：用纯 Python 复现"旧算法"
和"正确算法"并对比参考实现，证明旧算法差异 > 1e-3；外加源码不变式
（必须出现 `ldg_warp_reduce_sum(score)`、`s_out_acc[warp_id][q_idx + 0]`，
且输出不得用 `lane_id * 4` 直接索引）。

⚠️ **必须在 A100 上验证**：这次修改**没有经过 GPU 编译与运行**。
`RUN_MODE=build` 必须过，然后 `RUN_MODE=correctness` **必须重新确认 token 一致**
（修复前 attention 是坏的，修复后输出会变，历史 token 记录可能失效）。

### 5.1 ⚠️ 已实测的 0.74 ms/step 物理上说不通（最高优先）

一个 decode step 必须读 **1.503 GB** 权重，其中**仅 LM head（311 MB）@1555 GB/s
就要 0.2 ms**，全部权重至少 **0.967 ms**。而 nsys 记录 b1 cudagraph 的
**整个 decode kernel 只有 0.74 ms**，意味着 2031 GB/s > A100 规格。

**怀疑**：那次的 nsys 统计**只覆盖了部分 kernel**（漏采），或者 `--decode-steps`
用的是错的步数。**在 [09](06_实际运行数据.md) §3 的标定完成前，第 3、4 节的
device 侧结论都只能算强假设。**

### 5.2 怀疑：`ldg_lm_head` 的 0.18 ms 同样不可能

b1 megakernel 的 nsys 记录里 `ldg_lm_head` 只有 **0.18 ms**，但 LM head 权重
311 MB ⇒ 至少 0.2 ms，且它是 scalar FMA（无张量核）——实际只会更慢。
**同一个漏采怀疑**。建议用 `tools/bench_roofline_a100.py --sections weights`
单独测一次 LM head 权重流式读作为对照。

### 5.3 怀疑：elementwise pass 只用到 2-3/80 个 block

`ldg_o_proj_mlp_wmma` 的 residual / post-norm / SiLU×Up 都是全 grid 跨步，
但 batch=8 时数据量只有 8192 元素 ⇒ **只有约 2 个 block 有活**，
其余 78 个 block 空转，**每个 pass 后面还跟一次全网格 `grid.sync()`**。
我**没有改**，因为动 barrier 参与者集合有死锁风险。
低风险优化是只在有活的 block 里做 pass，但收益可能很小（barrier 0.55 ms/token）。

### 5.4 怀疑：`wmma_gemm` 的 shared-memory round-trip 是冗余

matrix B（权重）**直接 global load**，但 matrix A（激活）走
global → `s_a` smem → fragment。存在原因是 M 维 padding 要补零。
**没测过收益**，如果要做，注意 `load_matrix_sync` 的 16 字节对齐要求
（`k` 是 16 的倍数、行 stride = K 时成立）。

### 5.5 未验证：最近几轮的 CUDA 改动都没编译过

见 §3 第 0 步。改动集中在：

- §5.0 的 `ldg_attention` 重写（**风险最高**，整段 attention 主体被替换）；
- `ldg_wmma_max_supported_batch` / `ldg_batch_is_launchable`（批次上限守卫）；
- `ldg_update_step_batch` 的 `eos_token >= 0` 判断（ignore_eos 支持）；
- `barrier_probe` 的 `__launch_bounds__(512,1)`。

本地只能做静态检查：brace/paren 配平、`compileall`、源码不变式测试。
**没有 nvcc，无法编译**。`RUN_MODE=build` 是第一道门。

### 5.6 怀疑：`_should_burst` 放行 ignore_eos 后的交互

我只是让 `eos_token=-1` 表示"永不停止"，但**没有在真机上验证**：
burst 跑满 `max_steps` 后 `postprocess_burst` 的截断是否仍然正确
（`seq.max_tokens` 边界）、以及 `ignore_eos=True` 时 LM head 的 argmax
是否会取到某个特殊 id 导致长度不符。建议 `RUN_MODE=correctness` 时
专门跑一组 `ignore_eos=True` + `max_tokens` 边界（恰好用完 / 超过）。

### 5.7 已确认没问题的（省得重复查）

- `ldg_kv_ptr` 的算式与 `PagedKVCacheSpec.element_offset` **逐元素相等**
  （`tests/test_kv_cache_indexing.py`）；
- 每序列的 `kv_flag/attn_flag` 是 `+ seq_id` 独立副本，无跨序列串扰；
- WMMA 已完成 `__syncthreads()` 的 smem 覆写保护（K 循环内前后各一次）；
- `wmma_gemm` 的 `M < 16` 补齐有 0 值保护，且输出 buffer 按 16 行 padding 分配；
- batch 内核的 `blocks_per_seq * batch_size == grid_blocks` 恒成立，
  所以 `seq_id >= batch_size` 的早退**不会**触发（不会死锁）。

**教训（重要）**：上面这些"已确认没问题"当初是**逐项读代码**得出的，
而 §5.0 的 attention bug 就藏在同一份文件里、被同一批测试放过——因为
`correctness_wmma_vs_scalar` 比较的是 **GEMM**（两条路径共用同一个 attention），
`correctness_smoke` 只比 token。**"有测试通过"不等于"这条路径被测到"**：
下次怀疑某个算子时，先确认存在一个**直接验证该算子数值**的测试，
而不是只看整体 token 是否一致。
