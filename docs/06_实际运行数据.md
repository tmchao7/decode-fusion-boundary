## 1. 核心结论（一句话）

batch=1 megakernel 端到端 **1.04–1.31x** 超过 cudagraph；batch≥2 megakernel
device 侧落后 **~20x–50x**，因此默认回退 cudagraph。

## 2. ✅ 已实测：batch 扫描（crossover）

A100-SXM4-80GB / Qwen3-0.6B / prompt_len=32 / max_tokens=128 / greedy /
warmup=2 / runs=3 / 主指标 min-of-runs；工具 `tools/bench_burst_batch.py`，
复现：

```bash
python -m tools.bench_burst_batch --batch-sizes 1,2,3,4,5,6,7,8,10,16,32 \
  --max-tokens 128 --runs 3 --warmup 2 --json results/crossover_scan.json
```

| batch | cudagraph ms/tok | megakernel ms/tok | speedup | 判定 |
|------:|-----------------:|------------------:|--------:|:-----|
| 1 | 2.944 | **2.241** | **1.31x** | **megakernel 胜** |
| 2 | 1.634 | 11.352 | 0.14x | cudagraph 胜 |
| 3 | 1.120 | 8.236 | 0.14x | cudagraph 胜 |
| 4 | 0.840 | 6.631 | 0.13x | cudagraph 胜 |
| 5 | 0.680 | 5.902 | 0.12x | cudagraph 胜 |
| 6 | 0.566 | 5.621 | 0.10x | cudagraph 胜（megakernel 触底） |
| 7 | 0.487 | 5.979 | 0.08x | cudagraph 胜 |
| 8 | 0.429 | 6.495 | 0.07x | cudagraph 胜 |
| 10 | 0.347 | 7.478 | 0.05x | cudagraph 胜（serial×2） |
| 16 | 0.224 | 6.500 | 0.03x | cudagraph 胜（serial×2） |
| 32 | 0.111 | 6.496 | 0.02x | cudagraph 胜（serial×4） |

**读法（重要）**：

- 拐点在 **batch=1→2，悬崖式**，没有"打平区"；
- megakernel 在 b6 触底后**平台化于 ~6.5 ms/tok**：加 batch 不增加并行度，
  只增加等待时间；
- `serial×N` 表示 batch 超过 `megakernel_burst_batch=8` 后被拆成多次串行 burst，
  所以 b16/b32 的 ms/tok 是"每 step 处理 8 条序列"的成本，不能直接和
  cudagraph 的单次 replay 比并行度；
- **cudagraph 的 ms/tok 从 2.94 单调降到 0.11**，近似线性摊薄——这是"固定 host
  成本被摊薄"的表现，不是 GPU 变快（见 §3）。

## 3. ✅ 已标定：纯 GPU kernel 时间分解（nsys）+ 带宽标定

A100-SXM4-80GB / Qwen3-0.6B / prompt_len=32 / max_tokens=50 / greedy；
nsys `--trace=cuda --sample=none`；per-step = 纯 decode kernel ÷ 49 decode steps。

| 配置 | 纯 decode kernel ms/step | 主 kernel |
|------|------------------------:|-----------|
| b1 cudagraph | 0.74 | cuBLAS gemm + triton softmax/rmsnorm（33 种 kernel） |
| b1 megakernel | 1.89 | `ldg_decode_kernel_persistent_paged` 1.71 + `ldg_lm_head` 0.18 |
| b8 cudagraph | 0.77 | 同 b1 cuBLAS（batched gemm，时间几乎不变） |
| b8 megakernel | 101.8 | `ldg_decode_kernel_batch_wmma` 98.5 + `ldg_lm_head_batch` 3.38 |

**四个关键比值**：

1. b1 megakernel 纯 kernel 比 cudagraph **慢 2.6x**（1.89 vs 0.74 ms/step），
   但 E2E **反超 1.31x** —— 因为消除了 cudagraph 的 ~2.2 ms host/launch 开销。
   **batch=1 的胜利来自 launch 消除，不是算力更强。**
2. b8 megakernel 纯 kernel 比 cudagraph **慢 133x**（101.8 vs 0.77 ms/step）。
3. b8/b1 megakernel kernel 时间**增长 54x**（batch 只大 8x）→ 加 batch 不加并行度。
4. b8/b1 cudagraph kernel 时间**增长 1.04x**（几乎不变）→ batched GEMM 已吃满 SM。

### ✅ 标定结论（2026-09-13 `RUN_MODE=roofline` 实测 + HBM 常量修正）

`tools/bench_roofline_a100.py`（带宽标定）与 `tools/bench_burst_lower_bound.py`
（device 下界 probe）都已在 A100 上跑通，给出：

| 量 | 值 | 来源 |
|---|---:|---|
| A100-**SXM4-80GB** HBM2e 规格 | **2039 GB/s** | `nvidia-smi`（mem clock × bus width） |
| **可达带宽（实测）** | **1699 GB/s** | `a100_roofline_probe.json` → `bandwidth.best_gbps`（83.3% 规格） |
| 全权重下界 @ 规格带宽 | **0.585 ms/step** | 1.192 GB ÷ 2039 GB/s（`tied_embedding=True`） |
| 全权重下界 @ 实测可达带宽 | **0.701 ms/step** | 1.192 GB ÷ 1699 GB/s |
| per-layer 权重流（probe） | ~0.692 ms/step | probe 1.365 ms 含 barrier 0.673 ms（不含 lm_head） |

**0.74 ms/step 没有物理矛盾，不需要"nsys 漏采"假设**：
1.192 GB ÷ 0.74 ms = **1611 GB/s = 95% 的实测可达带宽（79% 规格）**，完全可达。
旧文档"0.74 ms 隐含 1.61 TB/s 超过 A100 规格 ⇒ 一定漏采"的结论建立在两个错常量上：

> **两处修正（本轮合并）**：
> 1. `HardwareSpec` 曾把 SXM4-**80GB** 写成 **1555 GB/s**——那是 40GB 版的规格，
>    已修为 **2039 GB/s**（本机 `nvidia-smi` 与 probe 都指向 2039）。
> 2. 每步权重流量曾是 1.503 GB（把 tied 的 LM head 与 embedding 各算一次）；
>    Qwen3-0.6B `tie_word_embeddings=True`，正确值 **1.192 GB**。
>    即便沿用旧的 1.503 GB，2031 GB/s 也只是 2039 的 99.7%，仍未超规格。

**结论**：cudagraph 的 b1 device 侧 0.74 ms 已经贴近权重墙（实测墙 0.701 ms =
1.06x；规格墙 0.585 ms），megakernel b1 离墙 2.7x（1.89 ms），b8 离墙 145x
（101.8 ms）。§4 的 host 残差可以直接用实测的 0.74 ms 反推。


## 4. ✅ 已实测：host / device 每步账本

用 §2 的墙钟 + §3 的 GPU 时间反推（每步墙钟 = ms/tok × batch）：

| batch | cg 每步墙钟 | cg 每步纯 GPU | host/launch 残差 | GPU 占比 |
|------:|-----------:|--------------:|-----------------:|--------:|
| 1 | 2.94 ms | 0.74 ms | **2.20 ms** | 25% |
| 8 | 3.43 ms | 0.77 ms | **2.66 ms** | 22% |
| 32 | 3.55 ms | 0.77 ms | **2.78 ms** | 22% |

**这是整个项目最重要的一张表**：cudagraph 的每步墙钟几乎不随 batch 变化，
GPU 只占 ~22%，**~2.5 ms/step 是 host 开销**。它的 tok/s 随 batch 涨，涨的是摊薄
host，不是 GPU 效率。推论：**高并发下唯一可赚的是 host 开销，而这部分两条路径
都在付**（详见 [07](07_架构结论_megakernel为何打不过cudagraph.md) §10）。

复现：

```bash
python -m tools.account_decode results/a100_account.json --seq-len 160
```

## 5. ✅ 已实测：barrier 成本

与 `AtomicGridSync` 同构的纯 barrier 微基准（grid=80、512 线程、cooperative、
`__launch_bounds__(512,1)` 与生产一致）：

```text
336 barriers = 28 层 × 12 次:  avg 0.673 ms/token -> 2.00 us/barrier
```

**纠正一个早前的误判**：barrier 原始成本**不是** 7–8 ms 量级，只有 ~0.67 ms/token。
真正的开销是它**强制层间全串行** + 每 GEMM 只有少数 block 干活导致的潜伏期累加。
（早前记录的 0.547 ms / 1.63 µs 是未对齐 `__launch_bounds__` 的旧值；对齐后
0.673 ms / 2.00 µs，与生产 occupancy 一致；上轮 0.661 ms / 1.96 µs 在 run-to-run
内一致。）
复现：`RUN_MODE=roofline`（报告里的 `barrier.ms_per_step_estimate`）。

## 7. ✅ probe + 二值判定已实测（2026-09-13 `RUN_MODE=roofline` 重跑）

按 [07](07_架构结论_megakernel为何打不过cudagraph.md) §10.4 的定义，
在 A100 上跑了 `RUN_MODE=roofline` + `RUN_MODE=account`（合并 ba1043d 后用修好的
`tools/verdict.py` 重跑，`--target-bytes 1.192e9`）：

| 实验 | 产物 | 实测值 | 判据与结论 |
|---|---|---:|---|
| B 可达带宽 | `a100_roofline_probe.json` → `bandwidth.best_gbps` | **1699 GB/s** | 83.3% 规格；§3 的 2031 GB/s "矛盾" 已由 HBM 常量修正澄清（不是漏采） |
| A device 下界 (probe) | `a100_lower_bound.json` → `lower_bound_probe.rows[*].ms_per_step_mean` | **1.365 ms/step** | probe 只流 per-layer 权重（跳过 lm_head） |
| LM head 修正 | 解析补充：0.311 GB / 1699 GB/s | **+0.183 ms/step** | probe 跳过 lm_head，`verdict.py` 用 `lm_head_stream_ms` 解析补回 |
| **完整 device 下界** | probe + lm_head 修正 = `full_device_floor_ms` | **1.548 ms/step** | **>1.5 ms → 实测 `DEVICE_BORDERLINE`** |

| 二值判定 | `a100_verdict.json` → `verdict` | ✅ **`DEVICE_BORDERLINE`** | 完整下界 1.548 ms 落在 1.5–3.0 ms 边际区间；`megakernel_could_win=false` |

> **1.548 vs 舍入复算**：`full_device_floor_ms` 取自 verdict JSON
> （1.548）。用上表三位小数的 probe 1.365 复算 1.365 + 0.183 = 1.548；
> **引用时以 JSON 字段为准**，不要用表里舍入后的数字相加。

> **第 14 轮服务器重跑已确认**：合并后的 `tools/verdict.py`（LM head 修正 +
> `tied_embedding=True` CLI）已在 A100 上重跑（`fe0d4f3`），verdict = **`DEVICE_BORDERLINE`**
> （`full_device_floor_ms = 1.548 ms`，probe 1.365 + lm_head 0.183）。
> 初版 verdict 报 `DEVICE_RECOVERABLE`，因为 probe 1.363 ms ≤ 1.5 ms 且没补 lm_head；
> 补回后 >1.5 ms → 升级为 `BORDERLINE`。本轮实测的带宽 1699 GB/s、
> barrier 0.673 ms 与第 13 轮标定（1724 GB/s / 0.673 ms）在 ~1.5% run-to-run 内一致，
> 结论不变。`tied_embedding=True`（Qwen3-0.6B），权重 1.192 GB（非 1.503 GB）。

### device 下界 probe 细节

| batch | ms/step | weight_stream_gbps | verdict 字段 |
|------:|--------:|-------------------:|:-------------|
| 1 | 1.365 | 643 | borderline (probe only) |
| 8 | 1.368 | 641 | borderline (probe only) |
| 32 | 1.367 | 642 | borderline (probe only) |

batch 无关（权重共享）；1.365 ms = per-layer 权重流 0.692 ms + barrier 0.673 ms
（0.692 ms 是该差值，不是独立实测值；probe 少 lm_head）。
完整下界 = 1.365 + 0.183（lm_head 修正）= **1.548 ms**。

### host overlay（实验 C）

| batch | host-inclusive ms/step | host-free ms/step | host overlay ms/step |
|------:|-----------------------:|------------------:|---------------------:|
| 1 | 0.034 | 0.020 | 0.014 |
| 8 | 0.046 | 0.032 | 0.014 |
| 32 | 0.043 | 0.029 | 0.014 |

**host overlay 仅 0.014 ms/step（b1/b8/b32 三行一致，均 <0.5 ms 门槛）→ 不构成可回收成本。**
`tools/verdict.py` 从**同一行**取值且选**最大 batch**，所以 verdict JSON 里
`measured_host_ms_per_step` = b32 的 **0.014**（`host_free` = 0.029）。注意这是
**同一行相减**的结果（0.043 − 0.029）；第 13 轮那次 b32 是 0.040/0.029 →
0.011，差异来自 run-to-run，不是口径。

### 实测 batch>1 device 时间（`RUN_MODE=account`）

| batch | cudagraph ms/step | megakernel-burst ms/step | 倍数 | megakernel vs 完整下界 1.548 ms |
|------:|------------------:|-------------------------:|-----:|-------------------------------:|
| 1 | 2.944 | **2.241** | **1.31x 胜** | 1.45x |
| 2 | 3.268 | 22.704 | 0.14x | 14.7x |
| 8 | 3.433 | 51.958 | 0.07x | 33.6x |
| 10 | 3.467 | 74.778 | 0.05x | 48.3x |
| 32 | 3.541 | 207.885 | 0.02x | 134.3x |

**关键差距**：完整下界 1.548 ms，但实测 megakernel-burst batch=10 为 74.8 ms
（**48.3x 下界**），batch=1 为 1.45x。上表是纯 burst 路径；`tools/verdict.py`
会在 `megakernel-burst` 行里选 **batch 最大**的那一行（batch=32，207.885 ms
= 134.3x 完整下界）作为"device 侧还有多少 gap"的证据。

### 判定解读

- **完整 device 下界 1.548 ms 刚过 1.5 ms 门槛 → 实测 `DEVICE_BORDERLINE`**：
  probe 1.365 ms 单看 ≤1.5 ms，但补回 LM head 0.183 ms 后 = 1.548 ms；
- **`megakernel_could_win=false`**：cudagraph 的 host-free replay 0.029 ms（b32，
  verdict 选取的行；b1 为 0.020），远低于 1.548 ms 的完整 device 下界，
  megakernel 没有 device 侧空间可赢；
- **实测 batch>1 device 时间是完整下界的 14.7–134.3x**：当前实现的算术 + 调度
  开销远超理论下界，R3 重构要填的 gap 极大；
- **host overlay 0.014 ms（b32）不可回收**：不是 host 问题。

> [10](10_交接文档.md) 第 9 轮的结论。
