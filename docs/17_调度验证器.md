# 调度验证器（离线静态验证）

> **状态**：现行 —— `schedule.py` 改动的前置门禁；纯 CPU，不需要 GPU。

## 1. 为什么需要它

cooperative launch 的正确性依赖一条 CUDA 编译器**无法检查**的不变量：
每个消费者的 wait 必须由某个生产者在它卡住之前满足。`schedule.py` 发出的指令流
有 bug 时：

- 在 A100 上的表现是**整卡挂死**（cooperative grid 卡在 `tg_wait`，`nvidia-smi` 也会被阻塞）；
- 一次会话就没了，而且**看不出是哪条指令**。

所以任何改动 `schedule.py` / 融合分段 / `attn_splits` 的提交，都必须先在这里通过。
实现：`src/nanovllm/backends/megakernel/verifier.py`；CLI：`tools/verify_schedule.py`。

## 2. 两个检测器 + 一个定位器

| 检查 | 能力 | 依据 |
|---|---|---|
| `execution` | **检测器** | 贪婪最大化执行。bar 计数器单调（执行一条指令不会让别的 wait 失效），所以"扫到没有 SM 能推进"就是真正死锁，不是模拟假象 |
| `arrivals` | **检测器** | 每个 bar 的生产数必须**等于**最大等待阈值。多到达 = 有人重复到达（内核的单调计数器会把它掩盖掉）；少到达 = 死锁 |
| `wait_graph` | **定位器** | 依赖图（wait `bar X >= t` 依赖 X 的前 t 个到达者）成环时**指名道姓**给出环，而不是只说"SMs 卡住了" |

**如实说明**：定位器**不是独立检测器**。环必然导致死锁，所以 `execution` 一定会同时失败 ——
在本仓库测过的 1438 个抽样变异里，`wait_graph` 的贡献是 **0** 次拒绝。
它当前的价值是诊断（报出环的成员），不是覆盖率。判断哪道检查在起作用，看
`AdversarialReport.rejected_checks` 的实际计数，不要假设三道都"在扛"。

（历史：这道检查的第一版只加"生产者位置更靠后"的边，而这样的路径位置严格递增、
永远闭不成环 —— 它是结构性空洞，从未触发过。现版本改为基于"第 t 个到达者"的依赖图，
并有平衡但成环的用例锁定。）

## 3. 对抗性变异

变异器从真实调度派生**必须被拒**的近似错误调度，再统计验证器**误接受**了多少：

| 变异 | 语义 |
|---|---|
| `drop_arrival` | 生产者的到达被抹掉 |
| `double_arrival` | 到达计数翻倍 |
| `shift_bar` | 到达写到了相邻的 bar 槽位 |
| `raise_threshold` | 等待阈值 +1，永远无法满足 |
| `truncate_stream` | 某个 SM 的指令流被截断 |

- **只生成"真的改变了缓冲区"的变异**：没有计数字段的 opcode 谈不上"计数翻倍"，
  这种空变异什么也证明不了（第一版会生成它们，并把"被正确接受"误记成误接受）。
- **抽样是按变异类别分层的**：`truncate_stream` 的候选全部排在列表末尾，
  均匀定步长抽样会**整类丢掉**，那样"每类都被验证过"就是假的。现在每类至少取一个，
  类内用固定步长 → 可复现。
- 抽样只影响运行时间，不影响结论：种群规模（`candidate_total`）同时报出。

## 4. 可引用的结果（2026-09-28，开发机 CPU）

```bash
python -m tools.verify_schedule --batch-sizes 1,8 --num-sms 1,108,170 \
  --fusion-groups 1,2,4,7,14,28 --attn-splits 1,2 --sample 120 \
  --json results/schedule_verification.json
```

| 指标 | 数值 |
|---|---|
| 调度通过 | **72/72**（BS ∈ {1,8} × SM ∈ {1,108,170} × attn_splits ∈ {1,2} × g ∈ {1,2,4,7,14,28}） |
| 有效参考流被接受 | **12/12** |
| 抽样变异被拒 | **1438/1438** |
| 变异种群 | **282,720** |
| **误接受** | **0** |
| 拒绝来源 | deadlock 1160、arrival accounting 278、wait_graph **0** |

顺带确立的两条结论（此前只在文档里存疑或靠模拟）：

1. **`attn_splits=2` 在调度层无死锁**：SM ∈ {1,4,108,170} 全部通过，
   指令数 4970（vs `attn_splits=1` 的 4522，差额是 split/combine 的额外到达）。
   文档里"attn_splits=2 会死锁"的旧记录就此关闭（GPU 数值比对仍需上机）。
2. **分段融合的指令守恒**：g ∈ {1,2,4,7,14,28} 的总指令数恒为 4522（BS=1），
   而**后段单独验证必然失败**（它等的是前段产生的 `bar_layer[first]`）——
   这正是"分段必须携带计数器"的机器可验证证据。

## 5. 局限（不要过度声称）

- 这是**静态论证**：证明指令流不会死锁，**不**证明数值正确、不覆盖数据竞争
  （`verifier.py` 不做内存冲突分析）、不覆盖 `row_active` 的非活跃行路径。
- 它替代不了服务器上的 `RUN_MODE=correctness`（PASS/CASCADE/FAIL）与
  compute-sanitizer（racecheck/memcheck）复跑；它只是把**能在本地抓到的那一类**拦在最前面。
- 贪婪执行对**单调计数器**是完备的；若将来引入非单调同步原语（例如无界重试、
  取消语义），这个论证需要重新审。

锁定测试：`tests/test_schedule_verifier.py`（28 项，含 opcode 字段布局、
两个检测器、平衡环定位、变异器不产生空变异、抽样分层、零误接受）。
