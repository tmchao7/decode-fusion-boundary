# 推理指标说明

> **状态**：现行 —— 指标定义 + 统计口径（所有数字的解释依据）。

本文档定义本项目在 A100/V100 服务器上的推理评估指标。所有结果都应同时记录模型、GPU、CUDA、PyTorch、git commit 和实际执行 backend。

## 请求级指标

### TTFT

`TTFT（Time To First Token）` 表示请求进入 `LLM.generate_with_metrics()` 后，到第一个输出 token 被 engine 记录之间的时间：

```text
TTFT = first_token_time - arrival_time
```

它主要反映 prompt prefill、首轮调度和首次执行开销。当前实现是在 scheduler 完成一次 step 后记录 token 时间，因此它是 engine-level TTFT，不是网络服务端的 streaming TTFT。

### ITL

`ITL（Inter-Token Latency）` 是连续输出 token 时间戳之间的间隔：

```text
ITL[i] = token_time[i] - token_time[i - 1]
```

ITL 主要反映 decode 阶段每一步的稳定延迟。报告至少包含 mean、p50、p95、p99。

### TPOT

`TPOT（Time Per Output Token）` 排除第一个输出 token 的时间：

```text
TPOT = (E2E - TTFT) / (output_tokens - 1)
```

当请求只生成一个 token 时，TPOT 为 `null`，不能填 0 或制造 NaN。

### E2E Latency

```text
E2E = last_token_time - arrival_time
```

当前是从请求到最后一个输出 token 的 engine-level 完成时间，不包含额外网络传输时间。

## 吞吐指标

- `prefill_tok_s`：prompt token 数除以 prefill 执行时间；
- `decode_tok_s`：输出 token 数除以 decode 执行时间；
- `output_tok_s`：输出 token 数除以整体测量 wall time。

性能 workload 使用 `temperature=0.0` 和 `ignore_eos=True`，尽量固定输出长度，避免提前 EOS 让吞吐比较失真。自然语言 correctness workload 保留 EOS 行为。

## GPU 与执行指标

代码内记录：

- CUDA Event 测量的 prefill/decode GPU 时间；
- Python host step 时间；
- peak allocated/reserved CUDA memory；
- 可选 NVML：GPU 利用率、显存利用率、功耗、温度。

Nsight 单独采集：

- kernel launches/token；
- memcpy operations/token 和 bytes/token；
- kernel GPU time/token；
- DRAM/L2 throughput；
- SM throughput；
- achieved occupancy。

普通 latency benchmark 不应和 Nsight profiling 混用，否则 profiler 开销会污染 TTFT、TPOT 和 ITL。

## 正确性与可比性

每个 Megakernel 结果必须记录：

```text
backend_requested
backend_actual
fallback_reason
correctness.passed
```

只有满足以下条件时才计算 Megakernel speedup：

1. `backend_actual` 中包含 `megakernel`；
2. greedy token 与 `torch-eager` reference 完全一致；
3. baseline 和 optimized 使用相同 prompt、seed、输出长度和硬件。

否则 speedup、improvement 和 latency 对比必须为 `null` 或 `not_applicable`。

## 统计口径（2026-09-28 起）

**为什么要写这一节**：一个 speedup 旁边没有离散度，就无法回答面试官/评审的第一个追问
——"这个 1.31x 显著吗？"。

### 单次聚合（`metrics.summarize`）

对**合并后的样本**（默认把每次 run 的 token 都并进同一个分布）报告：

```text
count  mean  stddev  cov  min  max  p5  p50  p95  p99
```

- `stddev` 是**样本**标准差（n < 2 时为 `null`，不给 0 以免被误读成"很稳"）；
- `cov` = stddev / |mean|（变异系数），**被问"稳不稳"时引这个数**；
- `mean` 与绝对量（ms/tok、ms/step）必须与 speedup 同时出现，不能只给比值。

### 跨 run 离散度（`metrics.summarize_runs`）

`compare.py` 每次 `run_case` 还会保留**每次 run 的标量**
（`wall_ms_per_token` / `tpot_ms` / `decode_tok_s`），并给出：

```text
mean  stddev  cov  min  max  ci95_low  ci95_high  ci95_half_width  resamples
```

- 置信区间是**确定性 percentile bootstrap**（10,000 次重采样，固定 seed），
  因为 run 数很少、不能假设正态（Hoefler & Belli #5/#6）；
- 固定 seed 保证同一份数据每次生成报告得到同一个区间；
- 输出位置：`compare.py` JSON 的 `runs_per_config` 与 `run_spread`。

### 复现协议

- 计时的模式统一 `--runs 5`（`SERVER_COMMANDS.txt`），warmup 保持 2；
- 报告里必须同时给出 `count` 与 `cov`。`cov > 5%` 的对比要么加 run，要么明确标注
  "差异落在噪声内"；
- **历史数据不可混口径**：`docs/06` / `docs/07` 的表来自已归档的
  `tools/bench_burst_batch.py`，用的是 `runs=3` + min-of-runs，只在那两张表内部可比。
