# 简历版一页小结：MegaKernel vs CUDA Graph 混合 decode 架构

> 一页 explainer，供直接引用。完整证据见 [docs/07](07_多batch为何打不过cudagraph.md)。

## 问题

LLM autoregressive decode 中，**Kernel Fusion（把整个 Transformer 融进单个 CUDA
cooperative kernel）与 CUDA Graph 谁更优？收益随 batch size 如何变化？MegaKernel
的最优适用区间在哪里？**

## 方法

在 nano-vLLM 推理引擎上为 Qwen3-0.6B（28 层, BF16）实现：
- **单序列 persistent megakernel**：整个 Transformer decode 融进一个 cooperative
  kernel，设备侧 EOS + N 步 back-to-back 排队，零每-token 主机同步；
- **WMMA tensor-core batch 路径**：QKV/O/Gate/Up/Down 全部 FC GEMM 上 m16n16k16
  WMMA，batch 维进 GEMM 的 M 侧；
- **直接复用 nano-vLLM paged KV cache + scheduler block table**，不建第二套 cache。

验证手段：crossover 扫描（b1–b32 双轨 ms/tok + tok/s）、nsys GPU kernel 时间分解
（4 组配置 b1/b8 × mega/cg）、纯 barrier 微基准、67 unittest + compute-sanitizer。

## 数据（A100-SXM4-80GB 实测）

| batch | cudagraph ms/tok | megakernel ms/tok | speedup | 判定 |
|------:|-----------------:|------------------:|--------:|:-----|
| 1 | 2.94 | **2.24** | **1.31x** | **megakernel 胜** |
| 2 | 1.63 | 11.35 | 0.14x | cudagraph 胜 |
| 8 | 0.43 | 6.50 | 0.07x | cudagraph 胜 |
| 32 | 0.11 | 6.50 | 0.02x | cudagraph 胜 |

**crossover 拐点在 batch=1→2，悬崖式（无打平区）。**

nsys 纯 GPU kernel 分解（坐实根因）：
- b1 megakernel 纯 kernel 比 cudagraph **慢 2.6x**（1.89 vs 0.74 ms/step），但 E2E
  **反超**——因为消除了 cudagraph 的 2.2ms host/launch 开销。**赢点 = launch 消除，
  不是算力更强。**
- b8 megakernel 纯 kernel 比 cudagraph **慢 133x**（101.8 vs 0.77 ms/step），
  host 消除的 2.2ms 完全无法补偿。
- b8/b1 megakernel kernel 时间增长 **54x**（batch 只大 8x）→ SM 空转 + barrier 串行；
  cudagraph 增长 **1.04x**（几乎不变）→ batched GEMM 用满 108 SM。

**host/device 账本（roofline 模型，`src/nanovllm/roofline.py`）**：
- 每步必须流 **1.503 GB** bf16 权重（28 层 0.881 + LM head 0.311 + embed 0.311 GB），
  HBM 墙 = **0.97 ms/step**（1555 GB/s）；**batch≈243 之前都是权重带宽 bound**。
- cudagraph 每步墙钟 = **2.94（b1）/ 3.43（b8）/ 3.55 ms（b32）**，其中纯 GPU 只占
  **25% / 22% / 22%** → **每步 host 残差 2.2-2.8 ms**，且几乎不随 batch 变化。
- 推论：cudagraph 的 tok/s 随 batch 提升来自**摊薄固定 host 成本**，不是 GPU 变快；
  **device 侧两者共享同一堵 0.97 ms 的墙，cuBLAS 已贴上，没有翻盘余量**。

## 结论

**根因是资源使用模型不对称，不是张量核覆盖**（FC GEMM 已全 WMMA 仍输）：
- megakernel 固定 80-block cooperative grid 按序列切分 + 每层全网格 barrier 强制
  层间串行 + 每 GEMM 仅 4–12/80 block 干活、其余 SM 空转；
- cudagraph 的 cuBLAS batched GEMM 用满 108 SM、张量核全开、无 padding、每 GEMM
  独立不被 barrier 串行，**且已经贴着 0.97 ms/step 的 HBM 墙**。

**高并发下的可赢空间只有一处**：消灭每步 ~2.5 ms 的 host 开销。这需要 megakernel
先把 batch>1 的 device 侧从 **98.5 ms 拉回 ~1 ms**（跨过逐层 grid.sync 的坎），
而不是去超过 cuBLAS——后者数学上没有余量。是否值得投入，由 docs/07 §10.4 的三个
便宜实验（device 下界 probe / 可达带宽标定 / host 消除上界）判定。

**混合架构（✅ 已落地）**：batch=1 走 megakernel persistent（消除 launch 间隙，
1.31x 微胜）；batch>1 回退 cudagraph（SM 用满 + 张量核全开）。`megakernel_batch_decode`
开关保留 megakernel batch 路径供正确性研究。

## 定位与外部印证

- 与 megaQwen（[Infatoshi/MegaQwen](https://github.com/Infatoshi/MegaQwen)，开源 Qwen3-0.6B megakernel）结论吻合：
  batch=1/short-context/static 窄场景优化，530 tok/s 自认是架构天花板，140+ grid.sync/token，
  带宽仅 ~5%；
- 与 Ada-MK（[arXiv:2605.11581](https://arxiv.org/abs/2605.11581)，已上线广告系统）方向一致：launch 开销占 E2E 14.6%
  （即可回收天花板），**single-batch** 比 TRT-LLM 高 23.6%，已转向 hybrid；
- 与 MPK（[arXiv:2512.22219](https://arxiv.org/abs/2512.22219)，[OSDI'26](https://www.usenix.org/conference/osdi26/presentation/cheng)）方向一致：用 SM 级图 + 去中心化调度做跨算子
  软件流水（低 1.7x），是"去掉逐层 grid.sync"方向的最强公开证据（但无 CUDA Graph 对照）；
- vLLM CUDA Graph（CudagraphDispatcher + BatchDescriptor + 多 shape 预捕获）天生
  搭配 batched kernel 用于 decode。

## 技术栈与工程量

CUDA cooperative kernel + WMMA tensor-core（~2500 行 C++/CUDA）、nano-vLLM backend
集成（scheduler/model_runner/engine 三方契约）、crossover benchmark + nsys profiling
工具链、paged KV cache 直连 + 64 位 offset + RoPE theta 事故修复、roofline/host-device
账本模型（纯 Python + 单测，锁定与 kernel 的常量契约）。

> **数据边界**：上表 device/host 分解来自既有 A100 实测（docs/07 §3.5/§9.6）+ 本次
> roofline 核算。其中"cudagraph 已贴带宽墙"是强假设而非已证事实——0.74 ms/step 流
> 1.503 GB 意味着 2.03 TB/s，超过 A100 HBM2e 的 1.555 TB/s 规格，需由
> `tools/bench_roofline_a100.py` 标定后确认（docs/07 §10.4）。**device 下界 probe
> 与高并发二值判定尚未在 A100 上跑过，本页不承诺任何高并发 speedup。**
