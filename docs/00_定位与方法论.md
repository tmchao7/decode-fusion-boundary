# 00 定位与方法论

> 本文是本仓库的**定位单一来源**。README 是入口，`docs/README.md` 是索引，
> 而"我们到底在问什么、用什么方法答、结论的效力边界在哪"由本文定义。

---

## 1. 项目定位

**一句话**：测量 **batch 增大时，megakernel（整前向融合）相对 CUDA Graph 的收益边界在哪，以及机制是什么**，并且把**为得出这个结论所用的 profiling 方法**本身作为可复用的产物。

这个定位有三个刻意的选择：

| 选择 | 为什么 |
|---|---|
| 问的是**边界**，不是"更快" | 融合的收益是**条件性的**。声称"更快"会被一个 batch 扫描推翻；给出边界则不会被推翻，只会被细化 |
| 对照臂是 **CUDA Graph**，不是 eager | Graph 才是强基线。对比 eager 得到的加速比没有意义 |
| **profiling 方法是产物之一** | 结论可能被硬件更新取代，方法不会。且"能诊断为什么慢"是岗位硬要求 |

**明确不做**：不追求在任意 batch 上更快；不做超过 8 的 batch；不做训练；不声称生产可用。

---

## 2. 结论（截至 2026-10）

**边界形状：`B=1` 融合占优，`B≥2` CUDA Graph 占优，且 device 侧融合恒慢。**

### 2.1 A100-SXM4-80GB

| 量 | 结果 |
|---|---|
| batch 1 | 融合**赢 1.31×**，赢点**不在算力**：省掉 ~2.2 ms/step 的 host 工作 |
| device 侧 | 融合**恒慢 2.6×** |
| batch ≥ 2 | device 差距主导，融合最多**输 133×** |

### 2.2 RTX 5090（当前主线测量）

| 量 | 结果 |
|---|---|
| host 残差 | **0.3%**（wall 624.1 / host 603.4 / device 601.7 ms，128 token） |
| 判读 | **CUDA Graph 已经把融合赖以立论的 host 边界消掉了** → 融合失去收益来源 |
| device @ ctx=1（**完全无 attention**） | 4.180 ms vs 权重地板 0.719 ms = **5.81× 离墙**，达成率 **17.2%** |
| 瓶颈归因 | **依赖/同步链，不是 HBM**（见 §3.4） |

### 2.3 外部独立复现

AutoMegaKernel（[arXiv:2606.09682](https://arxiv.org/abs/2606.09682)）把整个 Llama 前向编译成单个持久化 cooperative kernel，**自报**在 L4/L40S/A10G/RTX 5090 上赢 CUDA-graphed cuBLAS 1.08–1.33×，但在**训练级高带宽的 A100/H100 上输**，并把原因定位到 **cross-SM sync**。与本仓库在 A100 上的结论**方向一致**。

> ⚠️ 该对比是**精度不对称**的（W8A16 megakernel vs bf16 cuBLAS，decode 位置 0，最大 checkpoint TinyLlama-1.1B），且未经同行评审。引用时必须带上这句限定。

## 3. 方法论（本文的核心交付）

### 3.1 分母必须是本机实测可达带宽，且它是**尺寸敏感**的

roofline 的分母不能用规格值，也不能从别的机器继承。本机实测（RTX 5090）：

| buffer 尺寸 | 可达带宽 |
|---:|---:|
| 0.3 GB | 1,477 GB/s |
| 1.2 GB | 1,600 GB/s |
| 3.0 GB | 1,648 GB/s |
| 4.0 GB | **1,683 GB/s** |

对 `time_ms = a + bytes/B` 拟合得**截距 −3.9 µs**（即**无**固定 per-call 开销），说明差异来自"小 buffer 的单遍扫描没跑满"，不是摊不开开销。

**纪律**：任何"离墙多远"的数字必须声明用的是哪一行分母。

### 3.2 先 nsys 定位"时间花在哪"，再 ncu 问"为什么慢"

顺序不能反。nsys 给端到端 timeline（kernel 占比、memcpy、launch 间隙），ncu 给单 kernel 的计数器（occupancy、DRAM/L2 throughput、warp stall）。

### 3.3 ⚠️ `ncu` **不能** profile cooperative kernel

这是本项目踩到的真实坑，也是最有移植价值的结论之一：

> `ncu` 的 kernel-replay 机制与 `cudaLaunchCooperativeKernel` 冲突，实测后果是
> **GPU driver hang**——不只是 ncu 失败，`nvidia-smi` 也一起阻塞。

因此本仓库的 profiling 故事是 **nsys 驱动**的。遇到 cooperative kernel 时不要试图用 ncu。

### 3.4 SM 数扫描：判断"在等待"还是"在干活"

把 grid 从 1 扫到 SM 数上限，观察**单条指令耗时**随 SM 数的变化：

| num_sms | ms/step | 每 SM 指令数 | **每条指令耗时** |
|---:|---:|---:|---:|
| 1 | 74.655 | 4522 | 16.5 µs |
| 16 | 6.252 | 283 | 22.1 µs |
| 64 | 4.116 | 70 | 58.8 µs |
| 170 | 4.181 | 27 | **154.9 µs** |

从 16 到 170：每 SM 的工作量减少 **10.5×**，总时间只降 **1.5×**，而**单条指令耗时反涨 7×**。

> **判读规则**：若加 SM 使单条指令变慢，时间就花在**等依赖**，不在算力，也不在带宽。

### 3.5 结论必须有配对正确性

**没有配对 correctness 结果的延迟数字不写出来。** 门是 PASS / CASCADE / `DEVICE_ERROR`（硬失败，不可降级），并叠加严格 logit 对拍（`LOGIT_ATOL=1.0`）。

调度侧另有**对抗性验证器**：192/192 调度通过、变异体拒绝 640/640（抽样）、**误接受 0**。

## 4. 结论的效力边界（不得外推的部分）

- 绑定具体 GPU（A100-SXM4-80GB / RTX 5090）、模型（Qwen3-0.6B）、bf16、greedy、decode-only
- batch 上限 8（`TG_MAX_BATCH`）
- 单卡 tensor parallelism
- A100 与 5090 的结论**分别成立**，不是同一测量的两个点
- 未测：MoE、长 context 的最优配置、其他架构

---

## 5. 若继续推进，最有价值的方向

1. **窄波切宽**：`ADD_RMSNORM` 每层仅 1 条指令、`ATTN_DECODE` 仅 8 条，28 层串行穿过 → 可并发指令约 55（vs 170 SM），与 64 SM 饱和拐点一致
2. **attention 重写**：纯标量实现，实测 4.82 µs/位置；且 GQA 下同一份 K/V 被按 q-head **重复读两遍**
3. **不做**：加 `TG_B_STAGES`（`static_assert` 封死在 8，cp.async commit-group 硬件上限）、加 SM（170 实测比 64 更差）、用规格带宽当分母
