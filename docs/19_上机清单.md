## 2. 为什么剩下的必须上机

| 类别 | 具体项 | 离线为什么做不了 |
|---|---|---|
| **只有真机能测的量** | device ms/step、可达带宽、nsys 纯 kernel 拆解、E2E/ITL/TTFT | 需要真实时钟与带宽；开发机无 CUDA |
| **只有真机能验的正确性** | PASS/CASCADE/FAIL 门、`attn_splits=2` 的数值对拍、GPU 级 scheduler 行为（prefix 命中/chunked prefill/preemption）、compute-sanitizer 复跑 | 需要真权重与真内核执行 |
| **只有真机会暴露的失败模式** | cooperative 死锁（已离线拦）、扩展编译失败、`ncu` 卡死（已知，改用 nsys） | 平台相关 |

## 3. 执行顺序（建议一次会话内按此顺序）

| # | 命令 | 产物 | 通过判据 |
|---|---|---|---|
| 0 | `RUN_MODE=bandwidth bash SERVER_COMMANDS.txt` | `results/bandwidth.json` | 拿到本机可达带宽；**不要沿用 A100 的 1699 GB/s** |
| 1 | `RUN_MODE=taskgraph-baseline bash SERVER_COMMANDS.txt` | `taskgraph_baseline_correctness.{json,log}`、`taskgraph_attn_correctness.{json,log}`、`taskgraph_baseline.{json,md}`、`taskgraph_baseline_breakdown.{json,md}` | correctness 全 PASS 或 CASCADE；`g=1` 主表数值与既有记录一致（交叉校验） |
| 2 | `RUN_MODE=taskgraph-fusion bash SERVER_COMMANDS.txt` | `results/fusion_granularity.json` | 每行过 correctness 门；≥5 个粒度点；`g=1` 与步骤 1 一致 |
| 3 | `RUN_MODE=taskgraph bash SERVER_COMMANDS.txt`（含 7 个 GPU 验证模块） | `taskgraph_gpu_tests.log`、`tg_*.log`、`results/schedule_verification.json/.log` | 全绿；顺序上它排在 1/2 之前也可以（先验内核再做性能） |
| 4 | （仅 5090）cluster/PDL 臂 | — | 见 [14](14_融合粒度实验.md) §2.4 |

> `run_build` 会**自动**先跑 `tools/verify_schedule`：调度不可执行就直接停，不进付费会话。

## 4. 数据回来后的决策门（阈值已预先写死）

| 观测 | 触发结论 |
|---|---|
| taskgraph 主表 device ≥ 2x cudagraph 且无 E2E 增益 | 把 taskgraph 定位为 **IR + 粒度实验平台**，不再作为加速路径 |
| `g=28` 的 device 变化 **> 15.7%** | 推翻"边界成本可用 launch/sync 界定"的模型（[18](18_成本模型.md) §4.1） |
| 粒度曲线出现**谷底** | 推翻"bar 已把同样的边界串行化"，转 per-segment re-tiling |
| `attn_splits=2` 的时间与 `=1` 显著不同 | 修正 ATTN/combine 波的成本项（现按 1/0 K 步近似） |
| BS 1→8 的 device 时间显著变化 | 模型越界：它只适用于 BS=1 的波串行区间（[18](18_成本模型.md) §4.2） |
| `bandwidth.json` 的可达带宽明显低于 1699 GB/s | roofline 分母与所有 headroom 数字需按新值重算 |

## 5. 明确的 out of scope（A100 上不做）

cluster / DSMEM 融合、PDL 对照、TMA 权重预取（需 sm_90+）；FP8/NVFP4（A100 无 FP8 张量核，
量化走 W4A16/W8A16）；多卡 EP / all-to-all（无 NVLink 且需集群）；
Qwen3-30B-A3B bf16 及更大的 MoE（显存）。
