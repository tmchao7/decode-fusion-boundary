## 2b. 离线新增门禁（2026-09-30）

在接触 RTX 5090 之前，除了调度死锁/到达计数验证，还要运行 taskgraph ownership/geometry audit：

```bash
PYTHONPATH=src python -m unittest tests.test_taskgraph_audit tests.test_schedule_verifier
python -m tools.verify_schedule --batch-sizes 1,2,4,8 \
  --num-sms 1,4,108,170 --attn-splits 1,2 --sample 200
```

该门禁检查 packed GEMM/QKV 的 tile range、QKV pack 不跨 KV-head bar owner、attention split 索引、以及不同 SM 对输出 tile 的重复 ownership。它是 CPU-side safety net，不能替代 5090 上的实际执行、compute-sanitizer 或 `sms=1/4` 隔离矩阵。

correctness 产物现在区分：

- `PASS / CASCADE / FAIL`：输出对拍结果；
- `DEVICE_ERROR`：CUDA illegal access、launch failure、device assert 等设备故障，**不可降级为 CASCADE**；correctness 工具会先写出包含错误详情的 JSON，再以非零退出码结束。
- `requested_attn_splits` 与 `effective_attn_splits`：前者是命令行请求，后者来自 backend/metrics；如果实际 fallback 到 torch，effective 值记录为 1；旧 engine 没有回传字段时会额外标记为未确认。

## 3c. 2026-09-30 首次真机运行：两个只有 sm_120 才会暴露的 bug

这一节记录**已经发生过的**故障，不是预测。第一台 5090 上按 §3b 流程走时，两个 bug
连续打死了第一次运行；两个都已修复并加了守卫。

### 3c.1 `SERVER_COMMANDS.txt` 强制 `sm_80`（已修，`aec8723`）

`nvcc -arch=sm_XX` 只生成该架构的 SASS、不含 PTX，所以 `sm_80` 的扩展在 sm_120 上
launch 时报 `no kernel image is available for execution on the device`——看起来像内核
bug，其实是构建架构写死。现在改为**自动探测可见设备**，`verify_server_env` 的架构不匹配
是**硬失败**并说明后果。

### 3c.2 `s_norm` 的 dynamic smem 按 `TG_WMMA_TILE(16)` 而不是按 `BS` 开（已修）

| 项 | 值（RTX 5090 实测） |
|---|---|
| 内核 static smem | 37072 B |
| 旧请求 dynamic smem | `TG_WMMA_TILE * hidden * 4` = 65536 B |
| 两者之和 | **102608 B** |
| per-SM shared memory 上限 | **102400 B** |
| 结果 | `cudaFuncSetAttribute(...) failed: invalid argument` |

`tg_launch_decode` 现在按 `desc->BS * desc->hidden * 4` 申请（BS=8 → 32 KB，
static+dynamic = 69840 B < 102400 B），并且失败信息会打印 **static / dynamic / 上限**
三个数，而不是一句 `invalid argument`。

同一台机器上的**决定性对照实验**（`/tmp/mk_smem_bisect.cu`，用相同 static 开销的
dummy kernel）：

| kernel | static | 请求 65536 B | 请求 101376 B |
|---|---|---|---|
| 有 ~37 KB static | 37072 B | **REJECTED** | — |
| 无 static | 0 B | OK | OK |

→ 结论：`cudaFuncSetAttribute` 拒绝的不是"64 KB"本身，而是 **static + dynamic 超过
per-SM 预算**。这也是为什么它在 A100（上限 163 KB）上从未出现。

### 3c.3 仍未解决：grid > 1 时 illegal memory access

单 SM 能跑（7/7 CASCADE，`used_megakernel=True`），**grid=4 起在 sm_120 上崩溃**，
且是硬崩——容器连同 SSH 一起挂掉（`Connection refused` 直到平台重启），**不要在没有
救援手段的会话里盲试大 grid**。启动前先把 `TG_NUM_SMS=1` 当作安全档。

排障顺序（每条都要单独一个会话，崩溃后平台要重启）：

```bash
# 先在 nsys 下跑（ncu 不能用于 cooperative kernel，会把 driver 挂死）
nsys profile --trace=cuda,nvtx -o /tmp/mk_sms4 \
  env TG_NUM_SMS=4 python -m tools.correctness_smoke ... --batch-sizes 1
# 再用 compute-sanitizer 抓非法访问（cooperative + sanitizer 可能也不稳）
compute-sanitizer --tool memcheck --launch-timeout 120 python -m ...
```

已排除的方向：调度本身（`verify_schedule` 在 1/4/108/170 SM 上 192/192 PASS，且
sm_120 与 sm_80 的 `num_sms` 语义相同，`resolve_num_sms` 不依赖架构）。

**§3c.4 的越界写是最强嫌疑，但不能声称已定位**：`num_sms` 取 1/4/170 时，
`FFN_UPGATE_ACT` 的 784 个 pack 里都有 **756 个**会读 `inst[16]`——也就是说
grid=1（已知能过）同样在越界写。所以它单独**不能**解释 grid>1 崩溃；合理的说法是：
每个 CTA 都往 `silu_out` 之后约 1 MB 处乱写，grid=1 时那些地址恰好落在"写坏了也没人读"
的地方，而 grid>1 并发 CTA 更多、打到别的 CTA 正在使用的缓冲区上才致命。
这是**假设**，验证方法：重跑隔离矩阵（`sms=1 bs=1` → `sms=1 bs=8` → `sms=4`），
如果 grid=4 现在能过，说明这个修复就是根因；如果仍然崩，继续按下面的流程抓。

**32 GB 显存对本项目是过剩的**：0.6B 权重 1.19 GB，每 KV block 28 MiB，2048 上下文 × 8
序列只占 1.75 GB。显存只在 MoE 臂才成为约束（OLMoE-1B-7B bf16 13.8 GB ✓；
DeepSeek-V2-Lite 31.4 GB 需量化；Qwen3-30B-A3B 61 GB ✗）。

### 3c.4 第二个真机 bug：SiLU 阶段一直在重复激活 tile 0（已修，本机离线可证）

`tg_ffn_upgate_op` 的 SiLU 循环读的是 `inst[10 + t]`（旧的 per-tile 列表），
但 `f3d8114` 已经把 `inst[11..15]` 改成了**范围**编码：只写 `inst[9]=count` 和
`inst[10]=第一个 tile_n`，`inst[11..15]` 恒为 0。

op body 里的 `inst` 是 **`inst_shared`（`__shared__ int[TG_INST_WIDTH]` 的本地副本）**，
不是全局 `inst_buf` 的指针——`tg_dispatch(inst_shared, ...)`，op body 从不 rebase。
所以 `inst[10 + t]` 索引的是一个 **16 元素数组**，而 pack 上限是 7：

| t | 实际读到的 | 后果 |
|---|---|---|
| 0 | `inst[10]` = `tile_n0` | 只有 28 个 pack **起点**被执行 |
| 1..5 | `inst[11..15]` = 0（重构后清空） | tile 0 被**重复 Silu 3836 次** |
| 6 | `inst[16]` **越过 `inst_shared` 数组末端** | 落到相邻的 `__shared__ s_a`，即 GEMM 自己的 bf16 A 分片比特被当成 tile id |

离线对真实调度实测（不需要 GPU）：

| 量 | 值 |
|---|---|
| `FFN_UPGATE_ACT` 指令数（BS=1） | 784 |
| 内核实际 SiLU 到的不同 tile 数 | **28 / 192** |
| 从未被激活的 tile | **164（85.4%）**——保留 RAW gate 投影 |
| tile 0 被重复 Silu | 3836 次 |
| `inst[16]` 越界读 | **每步 756 次** |

`inst[16]` 读到什么**由编译器布局决定，没有保证**：它是 `inst_shared` 之后那块
`__shared__` 对象的内容。实测里相邻的 `s_a` 存着 GEMM 自己的 bf16 A 分片，
`bf16 1.0 = 0x3F80` 被当成 tile id 就是 16256，于是
`idx = 16256*16 + 15 = 260111`，而 `silu_out` 只有 49152 个 float（192 KiB）
——**越过缓冲区约 1 MB 的未经检查的读-改-写**。数值是布局相关的，越界本身不是。

**为什么 6→7 把潜在问题变成越界**：pack 上限 6 时，`inst[10..15]` 正好 6 个字，
`inst[10+5]` 还落在数组内；提到 7 之后 `inst[10+6]` 就越界了。

**为什么之前没被发现**：token 0 走 torch prefill，内核只在 **token ≥ 1** 进入，
而 `classify_comparison` 恰好把"分歧从 token ≥ 1 开始"判为 **CASCADE（容忍）**。
一个完全算错的 FFN 因此稳定地报成 CASCADE，从不报 FAIL——**这个容忍规则掩盖了它**。

修复：`int tile_n = tile_n0 + t;`。守卫三条：

1. `test_kernel_never_indexes_instruction_words_past_the_row` —— 任何
   `inst[<变量>]` 形式的读取直接失败（先剥注释，修复说明里引用了旧写法）；
2. `test_silu_phase_covers_every_intermediate_tile_exactly_once` —— 用内核自己的
   表达式回放调度，断言 192 个 tile 每个**恰好一次**（BS=1/2/4/8 全跑）；
3. 该守卫在 CPU-only 检出上就能运行，**不需要 GPU**。
