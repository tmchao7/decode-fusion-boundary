# Megakernel 设计说明与最终形态

> 本文回答"这个项目最终是什么"。测量方法见 [04](04_基准测试方法.md)，
> 为什么高并发打不过的机制见 [06](07_架构结论_megakernel为何打不过cudagraph.md)，
> 实测数字见 [09](06_实际运行数据.md)。

## 0. 一句话

**在 nano-vLLM 上为 Qwen3-0.6B 的 decode 阶段做一个 Megakernel：把整层 Transformer
融进一个 cooperative kernel，batch=1 时走它（消除每步 host/launch 开销），
batch>1 时回退 CUDA Graph。**

```text
batch == 1  ->  megakernel persistent/paged 路径   （零每步主机同步）
batch >= 2  ->  torch-cudagraph（nano-vLLM 原生）  （SM 用满 + tensor core + 无 padding）
```

这不是"退让"，而是**实测数据支持的结论**：megakernel 的收益来自消除每步
host 开销，而这个收益是 batch=1 独占的；batch>1 时它的 device 侧落后两个数量级
（[06](07_架构结论_megakernel为何打不过cudagraph.md) §10）。

## 1. 项目定位（可写进简历/汇报）

- **解决的问题**：单请求（batch=1）在线推理的延迟。此时 GPU 远未饱和，
  主要矛盾是**每步的 host/launch 开销**（CPU 驱动、kernel launch、`.item()` 同步）。
- **做法**：把 28 层 Transformer 的 decode 融进**一个 cooperative kernel**，
  设备侧 EOS + 连续排队 N 步，**每 token 零主机同步**；直接复用 nano-vLLM 的
  paged KV cache 与 scheduler block table，不建第二套 cache。
- **结果**：batch=1 端到端 **1.04–1.31x** 超过 CUDA Graph（数字见
  [09](06_实际运行数据.md)）；batch>1 回退 cudagraph。
- **边界（必须一起说）**：只支持 Qwen3-0.6B / BF16 / greedy / decode-only；
  batch>1 不占优；不承诺通用加速。

## 2. 三层结构

### 2.1 与 nano-vLLM 的集成边界

```text
prefill          -> 保持 nano-vLLM 原生 torch 路径（megakernel 不参与）
decode batch==1  -> MegakernelBackend.decode() -> generate_paged（设备侧 EOS）
decode batch>=2  -> MegakernelBackend.compatibility() 返回 not supported
                    -> ModelRunner 回退 torch + cudagraph
不支持的请求      -> 回退标准后端，并在 benchmark 里标为 non-comparable
```

回退是**显式且可观测**的：`backend_actual` / `fallback_reason` 会写进 metrics，
`compatibility()` 的拒绝理由会说明是 batch 超限、非 greedy、还是结构不匹配。

### 2.2 代码布局

```text
src/nanovllm/backends/megakernel/
├── backend.py     兼容性判定、fallback、batch 上限查询（wmma_batch_limit）
├── build.py       CUDA extension 的 JIT build（含 -DLDG_* 编译期参数）
├── model.py       权重打包、Decoder、paged KV 直连、operator 调用
├── cache.py       paged KV cache 契约（PagedKVCacheSpec，含单测）
└── csrc/
    ├── kernel.cu              cooperative decode kernel + WMMA GEMM + LM head
    └── torch_bindings.cpp     算子注册与参数校验
```

### 2.3 数据流（batch=1 burst）

```text
Scheduler.schedule_burst()
  -> 预分配 burst 所需的全部 block（block table 在整段固定）
ModelRunner.run_burst()
  -> megakernel.generate_paged_batch()  = 一次 cooperative launch，排队 N 步
       每步：embedding -> 28×(RMSNorm/QKV/RoPE/attention/O/MLP) -> final norm
             -> LM head + argmax（设备侧）
             -> ldg_update_step：写 token、推进 position、遇 EOS 置 inactive
  -> 只在 burst 结束时做一次 .cpu().tolist()
Scheduler.postprocess_burst()  -> 在 EOS / max_tokens 处截断
```

**关键点：整段 burst 只有一次主机同步**。这是 batch=1 能赢 cudagraph 的唯一原因。

## 3. Baseline 定义（对照的是谁）

| baseline | 配置 | 用途 |
|---|---|---|
| `torch-eager` | `decode_backend="torch", enforce_eager=True` | 下界参照（host-bound） |
| **`torch-cudagraph`** | `decode_backend="torch", enforce_eager=False` | **主对照**：graph replay 已消除 host launch |
| HF/PyTorch reference | `benchmarks/megakernel_reference.py` | 仅辅助 token-level 正确性 |

选 `torch-cudagraph` 做主对照的理由：它代表 nano-vLLM 已有的 decode 优化路径，
graph replay 把 host launch 拿掉之后，剩下的差距只能来自 GPU 侧——这正是
megakernel 要竞争的东西。公平性细节（bucket padding、硬件加速覆盖不对称）
见 [09](06_实际运行数据.md)。

## 4. KV cache：完全复用 nano-vLLM（没有第二套）

**megakernel 不生成、不复制、不迁移 KV cache。** 它直接拿到 nano-vLLM
`ModelRunner.allocate_kv_cache` 分配的同一块显存视图：

```text
[2, num_layers, num_blocks, block_size, num_kv_heads, head_dim]   # 2 = K/V
```

对序列 `s`、逻辑位置 `p`：

```text
logical_block  = p // block_size
block_offset   = p % block_size
physical_block = block_tables[s, logical_block]
element_offset = layer*layer_stride + physical_block*block_stride
               + block_offset*token_stride + kv_head*head_dim + dim
```

该契约实现在 `cache.py` 的 `PagedKVCacheSpec.element_offset`，并且
`tests/test_kv_cache_indexing.py` 用 Python 镜像 `ldg_kv_ptr` 的算式、
**逐元素断言两者相等**（paged 与 contiguous 两条路径都覆盖）。

GQA 映射：Q head `qh` 对应的 KV head 是 `qh // (num_q_heads / num_kv_heads)`
（16 Q head / 8 KV head ⇒ 每 2 个 Q head 共享 1 个 KV head）。

### 4.1 两个已修复的 KV 契约坑

1. **`cache_len = position + 1`**：nano-vLLM 先写当前 K/V 再调
   `flash_attn_with_kvcache(cache_seqlens=len(seq))`，即 query 关注 `[0, position]`
   闭区间。megakernel 必须一致，否则逐 token 偏移一位。
2. **block table 的 padding 必须是合法物理块**：`prepare_block_tables` 会把短序列
   的表右补齐成矩形。**padding 用 -1 会让 `ldg_kv_ptr` 算出负 offset，读到 KV
   cache 之前的内存**（越界读）。已改为 padding 用物理块 0（每个序列都必然分配了
   block 0）。详见 [07](09_集成问题清单.md)。

## 5. 算子与硬件加速覆盖（诚实版）

| 算子 | cudagraph（torch） | megakernel |
|---|---|---|
| QKV / O / Gate / Up / Down | cuBLAS GEMM | **WMMA m16n16k16（tensor core）** |
| Attention QK + softmax + PV | **FlashAttention** | **scalar** |
| LM head（151936×1024） | **cuBLAS** | **scalar FMA + 融合 argmax** |
| RMSNorm / RoPE / SiLU | torch/Triton kernel | 融合进 kernel |
| 采样 argmax | torch | 融合进 LM head |

**结论：megakernel 是在"两个最大的算子仍是 scalar"的前提下和"全 tensor core"
比较**。这让"batch>1 打不过"的结论更保守，也说明如果目标是比 kernel 质量，
应先把 attention / LM head 上张量核（[07](09_集成问题清单.md) 的 P1 项）。

## 6. 已知边界与不做的事

- **只做 decode**：prefill 不融合（融合 prefill 是另一篇论文的工作量）。
- **只支持 greedy**：temperature>0 未接入设备侧采样。
- **单卡**：`tensor_parallel_size` 必须为 1。
- **Qwen3-0.6B 固定结构**：`backend.py` 的 `QWEN3_CONTRACT` 在加载时逐项校验。
- **batch>1 不承诺收益**：见 [06](07_架构结论_megakernel为何打不过cudagraph.md)。
- **不用 ncu 采 cooperative kernel**：会 hang GPU（见 [08](08_服务器运行手册.md) §4.2）。
