# Task-Graph Megakernel 性能诊断与优化计划

> **状态**：现行计划 —— 基线仍是优化前的 10.8 ms/step，待 `RUN_MODE=taskgraph-baseline` 刷新。

**日期**: 2026-09-23
**基线**: A100-SXM4-80GB (108 SM)，Qwen3-0.6B，`attn_splits=1`，BS=1 ctx=1 → **10.8 ms/step (111 GB/s)**
**理论下界**: 1.2 GB 权重 / 1.5 TB/s ≈ **0.8 ms/step** → 当前差 13x

---

## 1. 诊断：瓶颈不是"权重带宽"，是"每波一个 K 循环"

### 1.1 Amdahl 拟合服务器数据

| 数据 | 值 |
|---|---|
| `T(1 SM)` | 275 ms/step |
| `T(108 SM)` | 10.8 ms/step |
| 108 SM 加速比 | **25x**（不是 108x） |

拟合 `T(n) = S + P/n`：`S ≈ 8.3 ms`（**77% 串行**），`P ≈ 267 ms`。

### 1.2 串行分量 = 波数 × 每波 K 步数 × 每步耗时

> ⚠️ **本节的三处计数已被 [18 成本模型](18_成本模型.md) §2 修正**（197 波→170 波；LM_HEAD 13 轮被漏算；`FFN_DOWN` 的 K 是 3072/192 而不是 1024/64）。本节保留作历史推导，**现行口径以 18 为准**。


调度是 **7 波/层 × 28 层 + LM_HEAD = 197 个串行波**（`build_layer_waves`）。波与波之间只能串行：下一波要等上一波最后一条指令落地（`tg_wait` on bar）。而**一波的耗时 = 该波最慢的那条指令**，因为 `place_round_robin` 把一条指令放在一个 SM 上。

一条 GEMM 指令 = 一个 16×N×K 的 WMMA 调用，K 循环 `K/16 = 64` 步（QKV/O/FFN/LM_HEAD 的 K 都是 1024）：

```
197 波 × 64 K-steps = 12608 K-steps
10.8 ms / 12608      = 857 ns per K-step   ← 与单 SM 实测 875 ns 吻合
```

**模型验证通过。性能 = 波数 × K步数/波 × 每步耗时，三个乘数就是三个优化方向。**

### 1.3 每步 857 ns 为什么这么慢

单 SM 实测 4.4 GB/s，而 7 个 warp 的 cp.async 流水按 Little's law 应该有：

```
in-flight = (TG_B_STAGES - 1) × 7 warps × 512 B = 3 × 7 × 512 = 10.5 KB
上限 = 10.5 KB / 600 ns ≈ 17.5 GB/s
```

实测 4.4 GB/s 只有上限的 1/4，所以除了 in-flight 不足，还有**每 K 步的串行开销**在关键路径上：

| 开销 | 说明 |
|---|---|
| `cp.async.wait_group` | 流水只有 3 深，等待 ≈ latency/3 ≈ 200 ns |
| **A staging** | 每 warp 每 K 步 8 次**标量** global load + 转换 + smem store，且 load→store 依赖，延迟直接暴露 |
| `__syncwarp()` ×2 | 每 K 步 |
| `ldmatrix` bank conflict | `s_b` 16×16 bf16 行距 32 B → 4-way |
| occupancy | 1 CTA/SM = 8 warps（12.5%），延迟无处隐藏 |

### 1.4 一个被否掉的假设（记录下来免得再走弯路）

曾推断"把 tile 摊薄到更多 SM（减小 `max_per_inst`）能缩短波次"。**这是错的**：一条指令内的 tile 是跨 7 个 warp **并行**的，摊薄只会让部分 warp 空转。每 SM 的波次成本是

```
ceil(ceil(tiles / M) / num_sms) × ceil(M / 7) × (K/16) K-steps
```

`M=7` 和 `M=2` 代入结果**完全相同**（M 小 → warp 少 → 每 K 步流的字节也少）。真正决定波次的是 `(K/16) × k_step_time`，与 M 无关。已用测试 `test_wider_packing_never_lengthens_the_path` 锁死"更宽的打包永不更差"。

**结论：M 取 7（一个 warp 一个 tile）——饱和 warp、指令数最少。**

## 2. 本轮已做（本地可编译验证，无 GPU 数值验证）

### 2.1 打包上限 6 → 7，编码改为区间语义

内核只读 `inst[10]`（`tile_n0`）和 `inst[9]`（`num_tiles`），**`inst[11..15]` 的 tile 列表是死数据**（内核本来就把一个 pack 当成一个 N=num_tiles\*16 的 GEMM）。所以：

- `make_gemm` / `make_qkv_proj`：`extra_tiles=[...]` → `num_tiles=N`，只写 `inst[10] = 首个 tile_n`
- `_TILE_SLOTS_PER_INST = 7`：一个 warp 一个 tile，饱和 7 个 worker warp
- 顺带修了 packer 的 key 不含 `tile_m` 的潜在隐患（M 未分块，但加上更安全）

效果：指令数 **4916 → 4522**，108 SM 的 `max_inst` **46 → 42**。bar 记账**完全不变**（每条 GEMM 到达仍带 `num_tiles` 作为 `inc`），已用测试 `test_granularity_preserves_bar_accounting` 锁定（num_sms=1/4/108 的 814 个 bar 槽位计数逐位相同）。

### 2.2 `TG_B_STAGES` 4 → 8

cp.async 流水 3 深 → 7 深，`in-flight` 1.5 KB → 3.5 KB per warp。8 是 A100 commit-group 硬件上限，已 `static_assert` 锁住（prologue 提交 `STAGES-1` 个，每次 wait 前再提交 1 个 → 等待时恰好 8 个在飞）。

### 2.3 A staging 向量化

标量 8 载入 + 8 存储/ lane → **float4 2 载入 + uint2 2 存储**。地址全 16 字节对齐（已逐一核对所有 `H`：`s_norm` 共享内存或 torch 张量基址；`STRIDE_K ∈ {1024, 2048, 3072}` 和 `ki ∈ {0,4,8,12}` 都是 4 的倍数；`k+ki+3 ≤ K-1` 所以 guard 不会截断向量）。

### 2.4 A staging 移到 `cp.async.wait` 之前

原来 K 循环里是「先 `wait_group` 阻塞，再发 A staging 的 global load」——两段延迟**串行相加**。现在 A staging 在 `commit` 之后、`wait` 之前发出，其 load 与 cp.async 的在途请求**重叠**。A staging 只写本 warp 的 `s_a` 切片，与 B 流水无竞争；`__syncwarp()` 仍在 wait 之后，保证 `ldmatrix` 能看到本 warp 的 store。

**SASS 验证**（`nvdisasm -c`，sm_80）：

```
LDGSTS.E.BYPASS.128 ...        <- cp.async 权重载入
LDGDEPBAR                      <- commit_group
LDS.128 R24, [R32.X4+0x8da0]   <- A staging: 16B 共享载入（已向量化）
F2FP.BF16.PACK_AB R34, R25, R24
STS.64 [R16], R34              <- 8B 打包存储
DEPBAR.LE SB0, 0x7             <- cp.async.wait_group 7（8 stages 生效）
HMMA.16816.F32.BF16 ...
```

三件事同时确认：向量化（`LDS.128`/`STS.64` 取代 8+8 标量）、重排（A staging 在 `DEPBAR` 之前）、8 stages（`DEPBAR.LE SB0, 0x7`）。

**还有一个 SASS 才暴露的问题**：写成两迭代循环时，编译器复用载入寄存器，生成
`LDS.128 → F2FP → STS.64 → LDS.128`，把两次载入的延迟**串行化**了。改成显式
`row_lo` / `row_lo+8` 两次载入后，SASS 变成两次 `LDS.128` 连续发出、之后才转换存储：

```
@!P4 LDGSTS.E.BYPASS.128 [R51], [R12.64]  ; cp.async 权重
@!P6 LDS.128 R24, [R64+0x8000]            ; A 载入 #1  ┐ 连续发出
@!P5 LDS.128 R32, [R64]                   ; A 载入 #2  ┘ 寄存器不冲突
LDGDEPBAR                                 ; commit_group
F2FP.BF16.PACK_AB R27, R27, R26           ; 两次载入都发出后才转换
...
DEPBAR.LE SB0, 0x7                        ; cp.async.wait_group 7
```

lane → 元素的映射（`lane/4` 行、`k + 4*(lane%4)` 列，以及 +8 行的第二个载入）
已用 Python 复刻验证：与原来的两迭代循环逐 lane 等价，且恰好覆盖 16×16 的
256 个元素各一次，smem 索引全为 4 的倍数（8 字节对齐）。

### 2.5 编译与资源

```
nvcc 12.4 -O3 -arch=sm_80 (TG_BLOCK_SIZE=256 TG_B_STAGES=8)
  tg_decode_kernel: 104 registers, 0 spill stores, 0 spill loads
  static smem 35.4 KB + dynamic 64 KB = 99.4 KB  (A100 上限 163 KB，余 63.6 KB)
```

寄存器从 128 降到 104（向量化后编译器重新分配），无 spill。

### 2.6 预期收益（保守）

| 改动 | 对 k_step 的贡献 |
|---|---|
| stages 4→8 | 等待分量 200 ns → 86 ns |
| A staging 向量化 | issue 开销降 4x |
| A staging 重排到 wait 之前 | 把 A 的 load 延迟从「相加」变成「重叠」 |
| 打包 7 | 指令数 -8%（barrier 流量） |

**估计 1.5 ~ 2.3x：10.8 ms → 4.7 ~ 7 ms。** 注意 A staging 的 global load **延迟**仍未隐藏（见 §3.2），所以达不到纯 in-flight 模型的 2.3x。

## 3. 下一步

### 3.1 先定性：**nsys，不要用 ncu**（必须做，只有服务器能做）

> ⚠️ **禁止对 `tg_decode_kernel` 用 `ncu`。** 它是 `cudaLaunchCooperativeKernel`
> 启动的，ncu 的 kernel replay 与 cooperative launch 冲突，**会 hang GPU（连
> `nvidia-smi` 都阻塞）**。见 `docs/05 §6` / `docs/07` / `docs/10`。
> 需要 stall 分解时，唯一合规路径是 `docs/13 §7` 的 `TG_DEBUG_NONCOOP=1`
> 单 CTA（`num_sms=1`）调试启动。

```bash
# 安全：nsys 不 replay，对 cooperative kernel 无冲突
nsys profile --trace=cuda,nvtx --force-overwrite=true \
    --output=results/tg_nsys \
    python -m unittest tests.test_taskgraph_smoke -v
nsys stats --report cuda_gpu_kern_sum --format table results/tg_nsys.nsys-rep
```

**决策点**：857 ns/K-step 是
- **(a) 长记分牌/屏障主导**（in-flight 不足）→ 继续加深流水：T_w（warp tile 16×32/64）+ stages
- **(b) A staging 的 global load 延迟主导** → 见 §3.2

判据：用 `TG_B_STAGES=4` 重跑同一个内核微基准，与默认的 8 对比
（`TG_B_STAGES` 是 `build.py` 的 env flag，改它会触发重新编译）：

```bash
TG_B_STAGES=4 python -m tools.bench_taskgraph --model "$MODEL" \
    --batch-size 1,2,4,8 --context-len 1,128,512,2048 \
    --num-steps 50 --warmup 5 --json results/taskgraph_kernel_stages4.json
```

若 stages=8 明显快于 stages=4 → 是 (a)（cp.async 延迟受限）；两者相同 → 是 (b)。

### 3.2 把 A staging 提出 K 循环（若判定为 (b)）

A 数据对一条指令内所有 tile 相同，但现在 7 个 warp 各自重复 staging，且每个 K 步都要重来。方案：

1. **每条指令 staging 一次**：把 16×K 的 A 转成 bf16 放共享内存（K=1024 → 32 KB；K=3072 的 FFN_DOWN 分 2 块），K 循环只做 `ldmatrix`，无 global load / 转换。需要 K 循环前一次 worker barrier（每条指令一次，不是每 K 步）。
2. **寄存器预取 + 双缓冲**：第 ks+1 步的 A 载入提前到第 ks 步发出，store 推迟到 mma 之后，用 8 个寄存器换掉暴露的延迟。
3. **治本**：让 RMSNorm 直接产出 bf16 的 `x_attn`/`s_norm`，A staging 就退化成纯 cp.async（无转换），可完全异步。

### 3.3 split-K（第二大结构性杠杆）

一波的临界路径是 64 个 K 步，而 108 个 SM 里 QKV 波只用 56 个、O_PROJ/FFN_DOWN 只用 10 个。把 K 切成 `splits` 份，每份 64/splits 步，波次时间线性下降。

**必须确定性**：用 partial buffer + 归约指令，**不要 `atomicAdd`**（会重新引入服务器刚修好的非确定性）。`TgTiling.down_splits` / `oproj_splits` 的字段已经预留，`build_schedule` 现在对 `>1` 抛 `NotImplementedError`。

### 3.4 长 context

ctx=2048 时 25.8 ms（attention 从 0 涨到 15 ms）。attention 现在是 4 bf16/lane 的标量实现，向量化到 16 B/lane，或直接用 WMMA 做 QK^T / PV。

### 3.5 明确不值得做的

- **ring buffer dispatch**：`__syncthreads` 每条指令 2 次 × 42 条/SM ≈ 84 个 barrier ≈ 5 µs，占 10.8 ms 的 **0.05%**。服务器文档把它列为优化项，建议降级。
