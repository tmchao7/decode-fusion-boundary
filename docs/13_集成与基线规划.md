## 1. 基线选择（已定稿）

### 1.1 主表：2 + 1

| backend | 角色 | 进主表 |
|---|---|---|
| `torch-cudagraph` | **主对照**（`--baseline`） | ✅ |
| `torch-eager` | 下界 + host 开销标定（唯一能把 wall 拆成 GPU/host 的手段） | ✅ 标注为下界 |
| `megakernel-tg`（新） | 我们 | ✅ |
| `megakernel` / `-wmma` / `-burst` | 旧架构（`kernel.cu`） | ❌ 移出默认 `--backends` |

**为什么主对照必须是 `torch-cudagraph`**（`docs/05:20-24` 已定调）：
graph replay 已经消除了 host launch，残差**只能来自 GPU 侧** —— 这正是 megakernel 必须竞争的维度。
`torch-eager` 只作下界，不作竞争者。

**为什么不对比 vLLM / SGLang**：
不同引擎、不同调度器、不同 kernel 实现，比出来的是"哪个引擎好"，不是"megakernel 有没有用"。
且仓库内无可执行基线（`benchmarks/baseline.py` 里 vLLM 是注释掉的）。如需对外头条数字，另开附录，明确标注为跨引擎对比。

**为什么移出旧 megakernel**：
5 个 backend 里 3 个是旧架构，默认 batch `[1,8,32]` × 4 档 prompt × 10 runs ≈ 360 次 run，噪音过大。
"重写比旧的好 7x"这个论断**不需要重跑**：`docs/06` 已有旧 megakernel b8 device = **98.5 ms**，task-graph b8 = **13.6 ms**，引用即可。

### 1.2 重要区分：移出主表 ≠ 从代码里删掉

- `kernel.cu` **不能删**：它今天是 `backend.py` 的 batch=1 生产路径，且 `docs/11 §1.3` 明确保留为 A/B 与 correctness 参考。
- `BACKEND_CONFIGS` 里那 3 个 config **保留**，只是不进默认 `--backends`。
  需要时 `--backends torch-cudagraph,megakernel,megakernel-tg` 一条命令补跑。

### 1.3 workload 网格（收窄）

| 维度 | 取值 | 理由 |
|---|---|---|
| batch | **1, 2, 4, 8** | cudagraph 的桶边界；taskgraph 支持范围。16/32 仅在证明"不塌"时补跑 |
| prompt 长度 | **32, 512, 2048** | 短 / 中 / 长（2048 = `max_model_len`，暴露标量 attention） |
| max_tokens | 128 + `ignore_eos=True` | 固定 token 数，`decode_time_ms_total` 才可比 |
| warmup / runs | **2 / 3** | `docs/06` 就是 min-of-3 取数 |

→ 3 backend × 4 batch × 3 长度 ≈ **36 次 run**（原来约 360）。

### 1.4 必须继承的公平性红线（`docs/05`）

1. **batch 桶对齐**：cudagraph 只 capture `[1,2,4,8,16,32,...]`，b=10 会 replay 16（多算 60%）。比桶边界值，或把 padding 折进结论。
2. **burst vs step-wise 必须标注**：两张表的 megakernel 不是同一个东西。
3. **算子覆盖不对称要披露**：attention QK/PV 与 LM head 在旧 kernel 是标量，cudagraph 是 FlashAttention / cuBLAS。
4. **每个数字带四口径**：wall / 纯 GPU / host residual / GPU share（`account_decode`）。
5. **fallback 行不算 megakernel 结果**（`compare.py:370-378` 已编码）。
6. **不要用 token 全等做正确性门**：用 PASS / CASCADE / FAIL 分级（bf16 级联 ~1 ulp 是预期的）。

## 2. CUDA Graph 对比机制（机制上的坑）

**不能同进程切**：`model_runner.py:38-40` 写死

```python
use_cudagraph = not enforce_eager and config.decode_backend != "megakernel"
```

→ **选了 megakernel 就全局关掉 graph capture**，batch>1 的 fallback 是 eager 而不是 cudagraph。

**做法：扩 `benchmarks/compare.py`，不要新写脚本。**

- `compare.py` 已是"一个 case 一个 `LLM()`，串行跑，`finally: llm.exit()`"（`174-179, 270-274`）→ 天然支持两条路径各自建引擎
- `BACKEND_CONFIGS`（`32-50`）加 `megakernel-tg`
- 自动继承 §1.4 全部公平性规则与 correctness gate
- **废弃**原计划的 `tools/compare_tg_vs_cudagraph.py`（`docs/taskgraph_progress.md:104-109`）——避免第二套计时/公平性逻辑漂移

## 3. 单请求卖点的账（必须先算清，否则会翻车）

`docs/06` b1 账本：

| | wall/step | 纯 GPU | **host/launch residual** | GPU 占比 |
|---|---|---|---|---|
| cudagraph b1 | 2.94 ms | 0.74 ms | **2.20 ms** | 25% |

- 旧 megakernel 的 **1.31x 全部来自消掉那 2.20 ms host**，不是算得更快（它 device 侧 1.89 ms，比 cudagraph 0.74 ms 慢 2.6x）。
- `docs/07 §10` 判定 **`DEVICE_BORDERLINE` / `megakernel_could_win=false`**：权重墙 0.585~0.702 ms/step，cudagraph 已在 0.74~0.77，**b1 的 device 侧没有余量**。

**推论**：

1. 单请求卖点的数学上限 = 省掉 ~2.2 ms host，**前提是 device 时间 ≤ ~0.8 ms**。
2. task-graph 现在 **10.8 ms**（device）→ 比 cudagraph 慢 **14.6x**。**在此状态下集成，单请求一定输。**
3. **这就是"必须先追性能再谈集成"的硬理由**，不是偏好。
4. **batch>1 才是真机会**：旧 megakernel b8 device = **98.5 ms**，cudagraph = **0.77 ms**；task-graph b8 = **13.6 ms**（已比旧的好 7x），且 **BS 1→8 只涨 26%**（旧的是 54x 爆炸）。
   → 把 b1..b8 全压到 ~1 ms 附近，就能得到"**全 batch 区间不退化**"这个可写进结论的卖点。

## 4. 集成架构：方案 C（B 起步 → A 收尾）

| 方案 | 做法 | host 开销 | 复杂度 | 与 compare.py 公平性 |
|---|---|---|---|---|
| **B（轻量桥接）** | `MegakernelBackend` 持有 weights / schedule / scratch / bars 缓存；`decode_batch()` 调 `tg_zero_regions` + `tg_decode_step`；走 `ModelRunner.run` 既有 dispatch | 每步回 Python（~2.5 ms/step，单请求卖点打折） | 低 | ✅ 天然公平 |
| **A（`docs/11 §7` 原设计）** | C++ `DecodeService` + `session.py` 双 daemon 线程 + pause/resume 握手；decode 不回 Python | 最低 | 高（要写 `runtime.cu`） | 需额外注意 |
| **C（推荐）** | **B 起步拿证据 → A 收尾压 host** | 分阶段 | 中 | ✅ |

**推荐 C 的理由**：A 的 `DecodeService` 也要用同一套 scratch / schedule / slot 管理代码 ——
**B 是 A 的前置，不是浪费**；且 B 能最快拿到"batch 缩放修好了"这个核心证据，风险最低。

### 阶段 1：性能追平（主战场，可与阶段 2 并行）

| # | 项 | 目标 | 依据 |
|---|---|---|---|
| 1.1 | **split-K**（确定性归约，**不用 atomicAdd**） | 一波 64 K 步 → 64/splits；108 SM 现在只用 10~56 个 | `docs/12 §3.3` |
| 1.2 | **A staging 提出 K 循环** | A 的载入延迟现在是 `k_step` 主项 | `docs/12 §3.2` |

**验收**：b1 ctx=1 从 10.8 ms → ≤1.5 ms；b8 从 13.6 ms → ≤2 ms（用阶段 0 的表）。

### 阶段 2：连续批处理 + 调度器承接

引擎侧现状（**已核实**）：
- **连续批处理已有**：`scheduler.py:37-85` 每步 `schedule()`、`running` deque、`preempt()` 抢占；`block_manager` 有 refcount + 前缀缓存
- **chunked prefill 部分有**：`scheduler.py:54` 只有**批内第一个**序列能被切块（靠 `num_cached_tokens` 续跑）
- **prefill/decode 不混批**：`scheduler.py:66-67` 有 prefill 就早返回

task-graph 侧要补：
1. **slot 管理**：`row_active` 的写者 + `page_table` / `cache_seqlens` 上传
   （内核侧防呆已做：inactive 行不写 KV，避免页复用污染）
2. **几何切换**：BS ∈ {1,2,4,8} 的 schedule 预构建；切换时重装 live slot
3. **KV pressure**：`free_blocks` 低于阈值 → park → 让 Scheduler 抢占
4. **prefill/decode 交替**：prefill 走 torch（decode park），decode 走 task-graph —— 即 `docs/11 §7.6` 的设计

**验收**：`compare.py` 的 mixed_batch / realistic suite 跑通；正确性用 PASS/CASCADE/FAIL 三级门。

### 阶段 3：单请求卖点（host 开销消除）

- no-sync / burst 模式：N 步不回 host（device 侧 per-seq done flag + 动态 mask）
- 或方案 A 的 C++ `DecodeService`
- **验收**：`tools/bench_nosync.py` 口径下 b1 的 host residual 从 2.2 ms → ~0，E2E 超过 cudagraph

### 阶段 4：chunked prefill 的"现代语义"（最后做）

现在是"批内第一个能切块" + "prefill/decode 不混批"。
现代引擎（vLLM/SGLang）是 **mixed batch**：一个 step 内同时放 prefill chunk + decode。
需要改 `scheduler.py` + `model_runner`，且 task-graph 是 decode-only 后端 → 一个 step 里既要跑 torch prefill 又要跑 task-graph decode。
**收益主要在高并发 TTFT，阶段 2 的"交替"已能满足单/低并发**，故排最后。

## 6. 风险

1. **b1 device 侧可能追不平**：`docs/07` 判定 `DEVICE_BORDERLINE`，cudagraph 已在权重墙上（0.74 vs 墙 0.585~0.702）。task-graph 要赢 b1 必须打到 ~0.7 ms —— **14.6x 的差距**。
   **若追不平，结论应转向"batch>1 不退化"，而不是"单请求更快"。**
2. **每步一次 launch**：persistent kernel 仍需 cooperative launch，`docs/11 §10.5` 明确"每步 decode 都是一次 launch"（不像 burst 那样 N 步不回 host）。host 开销靠阶段 3 压低。
3. **公平性红线**：任何对比表都要带四口径 + fallback 标注 + 算子覆盖披露。否则与 `docs/05` 修过的那次"两张表的 megakernel 不是同一个东西"是同一类错误。

## 7. P0 修正：ncu 不能用于 cooperative kernel（**安全**）

`docs/05 §6` / `docs/07` / `docs/10` 三处都明文：

> **不要**用 `ncu` 采 cooperative kernel：kernel replay 与 `cudaLaunchCooperativeKernel` 冲突，**会 hang GPU（连 `nvidia-smi` 都阻塞）**。

而 `tg_decode_kernel` 正是 `cudaLaunchCooperativeKernel` 启动的（`taskgraph_kernel.cu:tg_launch_decode`）。

**需要修的（上一轮引入的错误）**：

| 位置 | 现状（危险） | 改为 |
|---|---|---|
| `SERVER_COMMANDS.txt` `RUN_MODE=taskgraph-perf` | `ncu --kernel-name tg_decode_kernel` | `nsys profile --trace=cuda,nvtx` |
| `docs/12 §3.1` | 建议 ncu 采 `tg_decode_kernel` 的 stall | nsys；若要 stall 分解，只能走下面的单 CTA 非 cooperative 路径 |

**若确实需要 stall 分解**（唯一合规路径）：
新增 `TG_DEBUG_NONCOOP=1` 调试开关 → `tg_launch_decode` 改用普通 `<<<>>>` 启动，**仅在 `num_sms=1` 下安全**（单 CTA 必然驻留，自旋不会死锁），此时 ncu 可采。
**硬性约束：该开关在 `num_sms > 1` 时必须拒绝启动**（否则必死锁）。且只用于内循环分析，不作性能结论。
