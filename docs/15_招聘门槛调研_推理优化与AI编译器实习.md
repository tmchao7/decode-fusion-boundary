## 0. 一句话结论（先看这个）

对这名候选人，**项目本身是强信号，但当前叙事方式是弱信号**：

1. **megakernel 方向被头部团队点名**。阿里星 2027 届实习 JD 里直接写了要把 `op fusion、meag kernel、auto-tuning&codegen、compute overlap` 推到关键链路上，并要求"能够独立在 infra 上验证 or 完成上线"（[nowcoder 446420](https://www.nowcoder.com/jobs/detail/446420)，[一手]）。这不是"民科方向"。
2. **但 megakernel 的通行读法是"batch=1、短 context、小模型"的窄域优化**。HN 上 Hazy Research megakernel 博客的评论区，评论者 `mmoskal` 直接说"1B 模型是极端例子，所以才 1.5x；常规模型和 batch size 下大概只值几个百分点"，`kcorbitt` 问"14–70B 才是大家实际部署的"（[HN 44111673](https://news.ycombinator.com/item?id=44111673)，[一手]）。这名候选人自己的 docs/07 已经用 A100 实测把这条批评**证实了**（b1 赢 1.31x，b≥2 输到 0.02x）——这是**加分项，不是减分项**，前提是把它写成"我划定了适用区间并证伪了自己"。
3. **nano-vllm 现在是简历上的通货，不是差异点**。社区已有面向面试的整套包装（20 课 + 60+ 八股 + STAR 模板 + 简历模板），明写目标是"获得一份可以直接用于简历的项目经验"（[learn-nano-vllm](https://github.com/bcefghj/learn-nano-vllm)，[一手]）。**必须把差异点从"读了 nano-vllm"移到"我改了它的哪一层、改完的账是什么"。**
4. **模型选择在面试官眼里是有信号的**：dense Qwen3-0.6B + 短 context 是最容易被归为"玩具"的组合；同时 ByteDance / NVIDIA / 阿里 / 昆仑芯的 JD 都在点名 **MoE**，HN 上也有人直接点名 **Qwen3-30B-A3B** 是 megakernel 真正有意思的目标。
5. **工具链 vs 方法论的权重，两个岗位族不同**（详见 §4）：推理优化岗把 **profiling 能力写成硬要求**（快手快Star："熟练使用 NSYS、NCU 等性能分析工具"，而 Cute/TileLang/Triton 只列为加分项）；AI 编译器岗则把 **MLIR/LLVM/TVM/IR/Pass 写成硬要求**，profiling 常只作加分。

**方法论层面的"公认标准"可以引用 Hoefler & Belli 的十二条规则**（ETH Zurich，SC'15 教程论文），这是 HPC 圈写性能报告的事实标准，逐条原文如下（我直接从 PDF 抽取，非转述）：

1. "When publishing parallel speedup, report if the base case is a single parallel process or best serial execution, as well as the **absolute execution performance of the base case**. …one should **never report ratios without absolute values**."
2. "Specify the reason for only reporting subsets of standard benchmarks or applications or not using all system resources. …a corollary of this rule is to **report all results, not just the best**."
3. "Use the **arithmetic mean only for summarizing costs. Use the harmonic mean for summarizing rates**."
4. "**Avoid summarizing ratios**; summarize the costs or rates that the ratios base on instead."
5. "**Report if the measurement values are deterministic.** For nondeterministic data, report **confidence intervals**."
6. "**Do not assume normality** of collected data… without diagnostic checking."
7. "Compare nondeterministic data in a statistically sound way, e.g., using **non-overlapping confidence intervals or ANOVA**."
8. "Carefully investigate if measures of central tendency such as mean or median are useful to report. Some problems, such as **worst-case latency, may require other percentiles**."
9. "**Document all varying factors and their levels as well as the complete experimental setup** (e.g., software, hardware, techniques) to facilitate reproducibility."
10. "For parallel time measurements, report **all measurement, (optional) synchronization, and summarization techniques**."
11. "**If possible, show upper performance bounds** to facilitate interpretability of the measured results."
12. "Plot as much information as needed to interpret the experimental results. Only connect measurements by lines if they indicate trends and the interpolation is valid."

来源：Hoefler & Belli, *Scientific Benchmarking of Parallel Computing Systems: Twelve ways to tell the masses when reporting performance results*, [PDF](http://spcl.inf.ethz.ch/Teaching/2024-dphpc/hoefler-scientific-benchmarking.pdf) [一手]

> **[推断] 本项目对照这 12 条的自评**：已经在做的是 #1（报告绝对 ms/tok 与 speedup 并列）、#2（报告全部 batch 点，包括输的）、#10（nsys 分纯 GPU 时间、host 残差、GPU 占比）、#11（HBM 墙 + 可达带宽标定作为上界）。**明显缺的是 #5/#6/#7（置信区间 / 正态性 / 统计显著性检验）**——docs/06 用的主指标是 "min-of-runs"（3 runs），这在 HPC 圈是常见做法但**不是** Hoefler 推荐的做法；面试官如果问"你的 1.31x 显著吗"，min-of-3 会被追问。这是**最值得补的一块**。

## 5. 模型选择到底有没有影响？

**有，而且比大多数人以为的大。** 三条独立证据：

2. **面试确实会问"你的项目里 dense 和 MoE 有什么区别"**。理想汽车大模型推理一面原题："**你的项目中Dense和Moe模型推理实现起来有什么区别？EP？**"；字节跳动 AI Infra 一面："在 **MoE 模型**（如 RL 场景中）的推理优化方面是否有实践经验？"、"是否遇到过 reward 导致 routing 退化…如何处理？"[nowcoder e7b2c02ffda1430fbe51020c42467627](https://www.nowcoder.com/feed/main/detail/e7b2c02ffda1430fbe51020c42467627)、[AIInfraGuide 字节](https://caomaolufei.github.io/AIInfraGuide/interview/%E5%AD%97%E8%8A%82%E8%B7%B3%E5%8A%A8-ai-infra-%E5%AE%9E%E4%B9%A0-%E4%B8%80%E9%9D%A2-1) [聚合]
3. **JD 层面 MoE 是高频关键词**：NVIDIA（CuTe DSL 轨明写 "GEMM, **MoE**, Attention and Convolution"）、阿里星（"对 **MOE**, FlashAttention 有比较深入了解和实际经验"）、昆仑芯（"面向大规模 **MoE** 架构，从服务调度、并行策略、KV Cache 管理维度优化"）、Intel（"**MoE 路由策略、专家并行**"）、智谱（手撕 MoE Dispatch）、月之暗面（"攻关 MLA、Linear Attention、VQ、**MoE** 等 SOTA 结构"）。[均为一手 JD，见 §1]

**反过来说，"Qwen3-0.6B 密集模型"这个选择的风险在于**：
- 它是 nano-vllm 教程的默认模型，也是 learn-nano-vllm 指南 demo 的模型 → **零差异化**；
- decode 场景下 0.6B dense 的算术强度极低（本项目自己算出 ~1.04 FLOP/byte），**几乎必然是 memory bound**，因此"融合省 launch"的收益才显得大——这恰好**放大了"窄域优化"的观感**；
- 它没有 expert routing / EP / all-to-all，因此**无法回答**上面那些 MoE 问题。

**[推断] 优先级建议**（如果只能改一件事）：**把主模型从 Qwen3-0.6B dense 换成一个小 MoE（Qwen3-30B-A3B 或 DeepSeek-V2-Lite 级别），或者至少把小 MoE 作为第二个 workload 加进 crossover 扫描**。原因：
- 单卡放不下 30B-A3B 全量在 A100 80GB（BF16 约 60GB，做得到但很紧），**DeepSeek-V2-Lite（~16B total / 2.4B active）更现实**；
- 更划算的中间路线：**在现有 0.6B dense 上把 story 改正确**（说清"我选它是因为它让 memory-bound 与 launch-bound 的边界最干净，可作为方法论标定"），**同时补一个 MoE 的最小实验**——例如把 nanovllm 的 MLP 换成 top-2 expert 的 mock MoE，测"expert routing + all-to-all 在 megakernel 里可行吗"。**这个实验本身就是 HN 上被点名的问题**，而且不需要真的跑 30B。
- **不做的代价**：面试官问"你做过 MoE 吗"，答案是"没有"，那前面所有 megakernel 的深度都会被归到"batch=1 小模型"这一档。

## 6. 怎么呈现这个项目

### 6.1 README / 报告结构（建议）

基于 MLSys / OSDI artifact 评审通行要求（见 §6.4）与本项目已有的文档结构，建议 README 顺序：

1. **一句话 + 一张图**：**把研究问题前置，不要以"nano-vLLM 的 backend"开头。** 例："In LLM decode, how do the returns from whole-model kernel fusion vs CUDA Graph vary with batch size? This repo answers it with a hand-written persistent task-graph megakernel on A100, and reports where the crossover is and why."
2. **Applicability boundary（适用区间）**：一句话给结论——"b1: 1.09–1.31x faster; b≥2: up to 50x slower; crossover is a cliff at b1→b2"。
3. **TL;DR results table**（batch × {eager, cudagraph, megakernel} × {ms/tok, 纯 kernel ms/step, host 残差, GPU 占比}）。
4. **Why**（机制，不是猜测）：每层 336 次 grid.sync、每个 batched GEMM 只有 4–12/80 block 干活、M=batch<16 时 WMMA tile padding 到 16。
5. **Roofline / 物理下界**：1.192 GB 权重/step、0.585 ms（规格）vs 0.702 ms（1699 GB/s 实测可达）、cudagraph 实测 0.74 ms = 1.06x 墙。
6. **Methodology**（独立小节，见 §6.2）。
7. **Threats to validity / what I did NOT test**（诚实清单：scalar attention、scalar LM head、无 MoE、单卡、max_model_len ≤ 2048、ncu 不可用于 cooperative kernel）。
8. **Reproduce**: 一条命令 + 环境（driver / CUDA / torch / 硬件 SXM4-80GB / 时钟状态）。
9. **Negative results & 被证伪的假设**（这是最稀缺、最加分的一节）：barrier 不是毫秒级（实测 0.547 ms/token，推翻了此前 7–8ms 的归因）；"没上张量核"不是根因（FC GEMM 全 WMMA 后仍然输）。
10. **Related work & 定位**：Hazy megakernel、Cohere megakernel、MPK、Ada-MK、vLLM CUDA Graph。

### 6.2 基准方法学清单（可直接抄进 README）

- **预热与重复**：本项目已用 warmup=2 / runs=3。**建议补**：报告每点的重复次数、**中位数 + 均值 + stddev + min/max + p5/p95 + 变异系数（CoV）**，并把 CoV 当噪声信号标出来。这是 `gpu_benchmarking_osx/METHODOLOGY.md` 的配方（"report median / mean / stddev / min / max / p5 / p95 and the coefficient of variation"），也是 Hoefler 规则 #5–#8 的要求。[METHODOLOGY.md](https://raw.githubusercontent.com/Novotarskyi/gpu_benchmarking_osx/refs/heads/main/METHODOLOGY.md) [一手]
- **对照正确性**：kernel 输出必须对 CPU/参考实现做数值比对，而不只是"能跑"。本项目已有 PASS/CASCADE/FAIL 三级判定——**要在 README 里解释为什么允许 CASCADE（BF16 归约顺序）**，否则评审会读成"结果不一致"。
- **不要只报 ratio**：Hoefler 规则 #1——所有 speedup 旁边必须给绝对数（ms/tok、tok/s）。
- **报上界，不只报实测**：规则 #11。本项目已有（HBM 墙 + 可达带宽标定），**把它提到 README 主表旁边**。
- **披露不对称**：本项目 docs/05 §2 已经明确"CUDA Graph 使用 FlashAttention/cuBLAS，而 task graph 的 attention/LM head 仍包含 scalar 部分，必须在报告中披露"。**这正是 HN 上 `ryao` 攻击的缺陷的反面**——把它写成显式的 fair-comparison section，把"对 megakernel 有利的解读"也一并写出（"它还没用满硬件"）。
- **CUDA Graph bucket padding**：本项目 docs/07 §10.6(b) 已识别 cudagraph 按桶（1/2/4/8/16…）向上取整会多算。**要么选桶大小做测试点，要么把 padding 折算进去**——面试官如果懂 vLLM，一定会问这个。

### 6.3 面试话术（[推断]）

准备三段，每段 ≤90 秒：

1. **"我做了什么"**：一次 cooperative launch 跑完 28 层 + 设备侧 EOS，task-graph ABI 把 host 端指令/barrier 构建与 device 执行解耦。
2. **"我怎么知道它有效/无效"**：nsys 拆纯 kernel 时间发现 b1 megakernel 纯 kernel 比 cudagraph **慢** 2.6x（1.89 vs 0.74 ms/step），E2E 却反超——所以赢点是**消除 2.2 ms 的 host 开销，不是算力**。紧接着给 crossover：b1 赢，b≥2 悬崖式输。
3. **"我从中学到/证伪了什么"**：先验假设"barrier 是主开销"被微基准推翻（336 次 = 0.547 ms）；先验假设"上张量核就能翻盘"被推翻（FC 全 WMMA 后 b8 仍 133x 慢）；最终结论是 device 侧没有翻盘空间，唯一可赚的是 host。**这三条比任何 speedup 都更能说明有判断力。**

**要主动交代的短板**（面试官一定会发现，不如自己先说）：attention 与 LM head 仍是 scalar；无 MoE；单卡无 NCCL；batch 上限 ≈10；ncu 用不了。
