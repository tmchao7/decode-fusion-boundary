# 高并发 Megakernel vs CUDA Graph：判定任务书（可直接执行）

> 目的：用**一天**的 A100 机时，把"高并发下 megakernel 能否打败 cudagraph"
> 变成二值判定，并且**在动 kernel 之前**决定要不要投入 R3（几百行 kernel 重构）。
>
> 背景与完整论证见 [docs/07](07_多batch为何打不过cudagraph.md) 第 6 版 §10。
> 本文只讲"跑什么、看什么、怎么判"。

## 0. 已经算出来的账（不需要 GPU）

| 量 | 值 | 来源 |
|---|---|---|
| 每步必须流的权重 | **1.503 GB**（28 层 0.881 + LM head 0.311 + embed 0.311） | `roofline.py`，与 `kernel.cu` 常量做契约测试 |
| HBM 权重下界 @1555 GB/s | **0.967 ms/step**，batch 无关 | 同上 |
| 转算力 bound 的 batch | **≈243**（按 312 TFLOP/s 峰值） | 同上 |
| cudagraph 每步墙钟（b1/8/32） | 2.94 / 3.43 / 3.55 ms | docs/07 §9.6 实测 |
| cudagraph 每步纯 GPU（b1/8） | 0.74 / 0.77 ms（nsys） | docs/07 §3.5 |
| **每步 host 残差** | **2.2 / 2.7 / 2.8 ms（GPU 只占 21-25%）** | `tools/account_decode.py` 复算 |
| megakernel 每步纯 GPU（b8） | **98.5 ms**（慢 128x） | docs/07 §3.5 |

**已给出的判语（待实验确认）**：device 侧两者共享同一堵 0.967 ms 的墙，cuBLAS 已贴上，
**device 侧没有翻盘余量**；高并发唯一可赚的是**每步 ~2.5 ms 的 host 开销**。
但这条判语有一个**必须先解决的矛盾**（见 §2 实验 B）。

## 2. 三个实验与判据

### 实验 B：可达带宽标定（先看这个）

`results/a100_roofline_probe.json` 的 `bandwidth.best_gbps`。

**为什么必须先看**：0.74 ms/step 流 1.503 GB 意味着 **2.03 TB/s**，超过 A100 HBM2e
的 1.555 TB/s 规格。所以要么 nsys 的 0.74 只覆盖了部分 kernel，要么这台机器实际
带宽高于规格。**在标定前，"cudagraph 已贴带宽墙"只是强假设。**

| 结果 | 含义 |
|---|---|
| `best_gbps` ≈ 1.5-1.8 TB/s | 规格可信 ⇒ 0.74 ms **物理上不可能覆盖整个 step** ⇒ nsys 那个数只算了部分 kernel，device 侧其实还有空间（但注意那是 **cudagraph 自己的空间**，不是 megakernel 独有） |
| `best_gbps` ≥ 2.0 TB/s | 这台机器带宽异常高 ⇒ 0.74 ms 合理 ⇒ cudagraph 确实贴墙 ⇒ 判语成立 |

### 实验 A：device 下界 probe（决定性）

`results/a100_lower_bound.json` → `lower_bound_probe.rows[*].verdict`。

这个 kernel **不做任何计算**，只把 28 层权重各流一遍 + 每层 12 次 barrier——
即"一个完美融合 kernel 的 device 侧物理下界"。

| `ms_per_step_mean` | 判定 | 行动 |
|---|---|---|
| **≤ 1.5 ms** | device 侧可回收 | 值得做 R3（去掉逐层 grid.sync，MPK 方向）；E2E 有望 3-7x |
| 1.5 - 3.0 ms | 边际 | 需要更强的理由（例如同时修 attention/LM head）才做 |
| **> 3.0 ms** | **高并发翻盘不可行** | **停止 kernel 重构**，把结论写死进 docs/07/08，精力转向 host 侧优化（对 megakernel 和 cudagraph 都有效） |

### 实验 C：host 消除上界

`results/a100_lower_bound.json` → `host_free_graph[*]`：cudagraph 单步捕获后连续
replay N 步（不插主机同步）的每步墙钟。

这是"把每步 host 压到 0 之后 cudagraph 能到多快"的**直接测量**，也是 megakernel
在高并发要打败的**真实对手**。同时它证明一件事：**CUDA Graph 无法把 N 步塞进一个
graph，所以 host 每步至少一次 round trip**（§9.8 象限 D 的答案）。

## 3. 结果怎么处理

把这两个文件的内容（或 `results/a100_roofline_probe.log` /
`a100_lower_bound.log` / `a100_account_breakdown.md`）贴回来即可，本会话会：

1. 用 `tools/account_decode.py` 复算 host/device 账本，交叉验证三项口径
   （nsys per-step vs `cuda_decode_time_ms_total/decode_steps` vs `tpot×batch`）；
2. 按实验 A/B/C 的数据给出**二值判定**；
3. 写入 `docs/07` 第 6 版的实测小节（替换 §10.4 的"待跑"）与 `docs/08` 的数据边界说明；
4. 若判定为"不可行"，把结论固化并停止 R3；若"可回收"，再评估 R3 的具体改造范围。

## 4. 不要先做的事

- **不要**在实验 A 出结果前动 `kernel.cu` 的 batch>1 路径。probe 若 >3 ms/step，
  这条路的几百行重构全部作废（详见 docs/07 §8）。
- **不要**用 `ncu` 采任何 cooperative kernel（driver hang，docs/07 §3.5 已记录）。
- **不要**把 `bench_burst_batch.py` 的 `serial xN` 行当成 batch=N 的并行度
  （`tools/account_decode.py` 会读成 `serial_chunks` 并标注）。
- **不要**在标定（实验 B）之前相信 `a100_account_breakdown.json` 里的 headroom
  数字；工具会打 `calibration_warnings`，那不是报错而是强制提示。
