# 对比基线与公平性说明

> 这份文档回答一个问题：**"megakernel 打不过 cudagraph"这个结论，是怎么测出来的，
> 测法是否公平？** 结论见 [07](07_架构结论_megakernel为何打不过cudagraph.md)，
> 数字见 [06](06_实际运行数据.md)。

## 1. 三条执行路径

| backend | 配置 | 每步做什么 |
|---|---|---|
| `torch-eager` | `decode_backend="torch", enforce_eager=True` | Python 逐算子 dispatch，host-bound |
| `torch-cudagraph` | `decode_backend="torch", enforce_eager=False` | 按 batch bucket（桶）capture 的 graph，`graph.replay()` |
| `megakernel` | `decode_backend="megakernel"` | 一次 cooperative launch，设备侧 EOS |
| `megakernel-burst` / `-wmma` | 额外 `megakernel_burst=True` / `megakernel_batch_decode=True` | 显式开启 burst 与 batch WMMA 路径 |

`megakernel-burst` 与 `megakernel-wmma` 是**研究用后端**：它们绕过 hybrid dispatch，
强制走 megakernel 的 batch 路径，用于正确性验证和 A/B。默认策略（`megakernel`）
对 batch>1 回退 cudagraph。

## 2. 主对照为什么是 cudagraph

`torch-cudagraph` 已经用 graph replay 消除了 host launch 开销，所以剩余差距
**只能来自 GPU 侧**（kernel 间间隙、访存流水线、并行度）。这正是 megakernel
要竞争的东西。`torch-eager` 只作下界参照，不作为结论依据。

## 3. 公平性审计：三个必须披露的点

### 3.1 主 A/B 表原先从未测到 burst 路径（已修）

`megakernel-burst` 配置了 `megakernel_burst=True`，但 `_should_burst` 原先
**只要有一条序列 `ignore_eos=True` 就回退**；而 `benchmarks/compare.py` 的
performance / realistic 套件都用 `ignore_eos=True`（为了固定生成长度）。
后果：主表里的 megakernel 走的是 **step-wise 路径（每步一次主机同步）**，
不是它最强的那条路；而 `tools/bench_burst_batch.py` 用 `ignore_eos=False`
测的是 burst 路径。**两张表里的 "megakernel" 不是同一个东西。**

**修复**（第 8 轮）：设备侧 EOS 现在把 `eos_token < 0` 当作"永不停止"，
`_should_burst` 允许**整批都 ignore_eos** 的批走 burst（混合批仍回退，因为
设备侧 EOS 标志是批级、无法表达逐序列语义），`run_burst` 在这种批上传 `-1`。
判定逻辑抽到 `src/nanovllm/engine/burst_policy.py`（torch-free，可单测）。

**复现口径**：现在 `benchmarks.compare --backends torch-cudagraph,megakernel-burst`
配 `ignore_eos=True` 也能触发 burst；若要看 burst 与 cudagraph 的对照，
必须用 `megakernel-burst` 而不是 `megakernel`。

### 3.2 cudagraph 的 batch padding

torch 路径按

```python
graph_bs = [1, 2, 4, 8] + list(range(16, max_bs + 1, 16))   # model_runner.capture_cudagraph
graph = self.graphs[next(x for x in self.graph_bs if x >= bs)]  # run_model
```

预捕获并就近 replay。所以**非桶大小的批要付 padding**：batch=10 replay graph 16，
计算量 +60%；batch=9..15 同理。

这是 vLLM 的标准做法、**合法**，但对比时必须说清：**megakernel 是精确 batch，
cudagraph 是向上取桶**。要干净的 batch 对比就用桶大小（1/2/4/8/16/32）做点，
或把 padding 折算进 cudagraph 的每 token 成本。

### 3.3 硬件加速资源覆盖不对称

| 算子 | cudagraph | megakernel |
|---|---|---|
| QKV/O/Gate/Up/Down | cuBLAS（tensor core） | WMMA（tensor core） |
| Attention QK/PV | **FlashAttention（tensor core）** | **scalar** |
| LM head | **cuBLAS（tensor core）** | **scalar FMA** |

即：megakernel 是在**两个最大的算子仍是 scalar** 的前提下和"全 tensor core +
FMHA"比较。这使"megakernel 打不过"的结论更保守（对 megakernel 有利的解读是
"它还没用满硬件"），但如果目标是**公平比较 kernel 质量**，应先把 attention 与
LM head 上张量核，再谈 batch>1 的架构问题。

## 4. 测量口径（每个数字都要标这四项）

1. **墙钟 / GPU / host 残差 / GPU 占比**：`tools/account_decode.py`。
   每步墙钟 = `tpot × batch`；GPU = `cuda_decode_time_ms_total / decode_steps`。
2. **纯 GPU kernel 时间**：nsys（`nsys profile --trace=cuda --sample=none`），
   用 `tools/parse_nsys_kernel.py --decode-steps N --roofline` 解析。
   **注意**：`--trace=cuda` 不采集 DRAM 计数器；缺表时工具报 UNAVAILABLE 而非 0。
3. **标定状态**：实测 per-step GPU 时间若低于权重下界（1.192 GB ÷ 2039 GB/s =
   0.585 ms；即隐含带宽超过标定值），工具会打 `calibration_warnings`——
   **该行的 headroom 在标定前不可信**。注意 0.74 ms（隐含 1611 GB/s）**不**触发：
   它低于 2039 规格、也低于 1728 实测可达带宽。
4. **是否 fallback**：`backend_actual` / `fallback_reason`；fallback 的行不能当
   megakernel 成绩。

## 6. 不要做的事（测量层面）

- **不要**用 `ncu` 采 cooperative kernel：kernel replay 与
  `cudaLaunchCooperativeKernel` 冲突，会 hang GPU（连 `nvidia-smi` 都阻塞）。
- **不要**把 `results/a100_nosync_compare.md` 的数字当 burst 性能：那走的是
  `ignore_eos=True` 的 step-wise 回退。
- **不要**用 token 全等做正确性门：WMMA batched 与 scalar 路径不是逐 bit 相等，
  用 `tools/correctness_wmma_vs_scalar.py` 的 PASS / CASCADE / FAIL 分级。
- **不要**在同一张表里混用 burst 与 step-wise 的 megakernel 数字而不标注。
