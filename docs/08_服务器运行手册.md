# 服务器运行手册（A100 / V100）

> 所有命令都在仓库根目录、通过 `SERVER_COMMANDS.txt` 执行。
> **规则（见 AGENTS.md）**：任何要在服务器上跑的命令都必须写进
> `SERVER_COMMANDS.txt`，不允许新建其它 `*_COMMANDS.txt`。

## 2. RUN_MODE 一览

| RUN_MODE | 做什么 | 需要模型 | 需要编译 |
|---|---|:---:|:---:|

| `verify` | 环境 + extension 导入检查 | ✅ | – |

| `account` | host/device 每步账本 + roofline 表 | ✅ | ✅ |

首次完整流程：

```bash

RUN_MODE=build       bash SERVER_COMMANDS.txt
RUN_MODE=correctness bash SERVER_COMMANDS.txt
RUN_MODE=roofline    bash SERVER_COMMANDS.txt   # 先做判定，再谈优化
RUN_MODE=account     bash SERVER_COMMANDS.txt
```

## 3. 先做哪一步

**`RUN_MODE=roofline` 优先于一切 kernel 改动。** 它回答两个决定性问题：

1. 这台机器的**可达带宽**是多少？——用来判定实测 kernel 时间是否可信，
   并解释 0.74 ms/step 是否真的超规格（实测 1728 GB/s：不超，见
   [06](06_实际运行数据.md) §3）；
2. 一个**不做任何计算**的 cooperative kernel 流一遍权重需要多久？——这是
   "把 batch>1 的 device 侧拉回 ~1 ms" 是否可能的物理下界。

`results/a100_verdict.json` 由 `tools/verdict.py` **机械给出判定**，
不要人工从日志里读结论（判据见 [07](07_架构结论_megakernel为何打不过cudagraph.md) §10.4）。

## 4. Profiling

### 4.1 nsys（安全）

```bash
nsys profile --trace=cuda,nvtx --sample=none \
  --output=results/a100_nsys \
  python -m benchmarks.compare "$MODEL" --suite performance --backends megakernel \
    --prompt-lengths 32 --max-tokens 32 --warmup 1 --runs 1

python -m tools.parse_nsys_kernel.py results/a100_nsys.sqlite \
  --decode-steps 49 --memory --roofline
```

- `--trace=cuda` **不采集 DRAM 计数器**；缺表时工具明确报 `UNAVAILABLE` 并给出
  替代方案（`tools.bench_roofline_a100.py --sections bandwidth`），**不会静默报 0**。
- `--roofline` 把每步 kernel 时间换算成"隐含权重带宽"，用来对照标定/规格带宽
  （实测用途见 [06](06_实际运行数据.md) §3）。

### 4.2 ncu（危险，不要用）

**不要**对任何 megakernel / cooperative kernel 使用 ncu（Nsight Compute）：
其 kernel-replay 机制与 `cudaLaunchCooperativeKernel` 冲突，会导致 GPU driver
hang——**连 `nvidia-smi` 都会被阻塞**，需要等 driver TDR 恢复。
采集 cooperative kernel 只能靠 nsys（只 trace 不 replay）或微基准。

### 4.3 compute-sanitizer

```bash
RUN_MODE=sanitize bash SERVER_COMMANDS.txt
```

用于越界 / 竞态排查。注意它会让 cooperative kernel 极慢，只跑最小 case。

## 6. 每次改动后的回归基线

```bash
PYTHONPATH=src python -m unittest discover -s tests -v
python -m compileall src/nanovllm benchmarks tools
RUN_MODE=correctness bash SERVER_COMMANDS.txt     # 含 --require-megakernel
```

本地（无 GPU）只能跑前两条；`tests/` 里需要 torch 的用例在无 torch 环境会报
`ModuleNotFoundError`，那是环境缺失而非失败。

## 7. 常见故障

| 症状 | 原因 / 处理 |
|---|---|
| `megakernel WMMA batch decode supports at most 10 sequences` | batch 超过真实上限（grid 80 ÷ `LDG_ATTN_BLOCKS=8` = 10，不是 `LDG_MAX_BATCH=32`）。现在会在 launch 前被 `TORCH_CHECK` 拒绝，并由 `backend.compatibility()` 回退 cudagraph，**不会**再静默返回上一步的 token |
| `cooperative preflight failed` | grid 超过设备 cooperative 上限，或设备不支持 cooperative launch；probe 在**编译前**报错并给出应改的 `--grid-blocks` |
| 偶发 token 翻转 / 量化不一致 | 见 AGENTS.md 的 ulp cascade 记录：WMMA 与 scalar 路径不是逐 bit 相等，用 `tools/correctness_wmma_vs_scalar.py` 的 PASS/CASCADE/FAIL 分级 |
| RoPE 相关数值错 | 先查 `rope_theta` 是否从 `rope_scaling` 取（Qwen3 放在那里，不是顶层字段） |
| GPU 卡死、`nvidia-smi` 阻塞 | 大概率是对 cooperative kernel 用了 ncu；等 TDR 恢复，之后只用 nsys |
| megakernel 数字和文档对不上 | 检查是 burst 还是 step-wise 路径：burst 需要 `ignore_eos=False` 或整批 `ignore_eos=True`（见 [05](05_对比基线与公平性.md) §3.1） |
