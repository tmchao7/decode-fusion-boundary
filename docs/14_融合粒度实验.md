## 1. 为什么做这个实验

仓库自己的实测把问题钉死了（[06](archive/06_实际运行数据.md) / [07](07_融合收益边界与根因.md)）：

```text
batch=1  megakernel E2E 2.241 ms/tok  vs  cudagraph 2.944 ms/tok   -> 1.31x 胜
batch=1  megakernel device 1.89 ms/step  vs  cudagraph 0.74 ms/step -> 慢 2.6x
cudagraph 0.74 ms/step = 1611 GB/s = 实测可达带宽(1699 GB/s) 的 95%
```

结论一：**batch=1 的胜利全部来自消除 host/launch（~2.2 ms/step），不是算得更快。**
结论二：**dense 小模型上 device 侧已经贴着权重墙，没有可赚的空间。**

所以"融合得更深"在 device 侧不可能赢；能赢的只有 host 边界。于是本实验问一个
可以证伪的问题：

> 把一次 decode step 切成 `g` 段、每段一次 cooperative launch，**融合粒度**对
> device 时间与端到端延迟各有什么影响？拐点在哪？

## 2. 设计

### 2.1 粒度定义

`Config.fusion_groups = g`：一个 step 的指令流被构建成 `g` 个**连续层段**，
每段一次 cooperative launch。`g=1` 就是当前的单 megakernel（零行为变化），
`g=28` = 每层一次 launch。

实现：`schedule.split_layers(28, g)` + `schedule.build_schedule(..., layer_range=...)`，
`TaskGraphDecoder` 按段缓存调度、每步按序发 `g` 次 `tg_decode_step`。
**scratch / bars / page_table / cache_seqlens / 最终 D2H 全部共用且只做一次** ——
唯一变化的变量就是段边界本身。

### 2.2 为什么按层切在语义上是免费的

1. bar 槽位是**全局层索引**的，两段永不共享槽位 → 每步开头 `tg_zero_regions`
   清一次仍然正确；
2. 唯一的跨段依赖是 `bar_layer` 的交接：段 k 最后一层的 ADD_RMSNORM 产出
   `bar_layer[boundary]`，段 k+1 首层 QKV 等待的正是**同一个槽位**、target `BS`；
3. kernel launch 本身就是隐式全屏障，所以这个等待在段开始时已经满足。

这三点都有测试锁定（见 §3），不靠推理。

### 2.3 四条臂（避免把"粒度"和"实现语言"混在一起）

| 臂 | 实现 | 隔离的变量 |
|---|---|---|
| A | torch-eager | host-bound 下界 |
| B | torch-cudagraph | 强基线（已贴墙） |
| **C** | 分段 megakernel（本实验，同一份 IR） | **融合粒度** |
| D | Triton 融合组 + CUDA Graph | 工具链 / 实现质量 |

**C 是 D 的对照**：如果 D 赢了，必须先用 C 回答"这是粒度的功劳还是实现的功劳"。
在 sm_80（无 TMA / 无 thread-block cluster / 无 wgmma）上，ClusterFusion++ 那类
cluster 级融合不可用，所以本实验的能量范围就是"跨段边界 + 并行分解"。

### 2.3b 第二条粒度轴：schedule 多态（RaMP 路线，Phase 1 可选扩展）

RaMP（[arXiv:2604.26039](https://arxiv.org/abs/2604.26039)）的实测结论是"只按 batch
size dispatch 会让 **10–70%** 的 kernel 吞吐量闲置"，改成从**运行时样本（专家直方图、
实际 batch/context）**里选 1/134–268 个 schedule 变体，换到 1.22x kernel、0.93% 平均
后悔值。对我们是**同一份 IR 的第二种粒度旋钮**，且不需要新 kernel：

- 现状：每个 batch bucket 一个 schedule，`fusion_groups` 再乘一层；
- 扩展：把"选哪个 (bucket, groups, attn_splits)"变成**从实测数据里选的策略**，
  并与静态 dispatch 对比 —— 这正是 AI compiler 岗要的"cost model + 调度决策"。

它和臂 C 的区别：C 隔离**融合粒度**；2.3b 隔离**调度决策**（同一粒度下选配置）。
两者都必须在同一 harness 上跑，否则又变成跨实现比较。

### 2.4 硬件靶与文献先验（2026-09-28 更新）

**A100 是"困难靶"，这不是我们的实现事故。** AutoMegaKernel
（[arXiv:2606.09682](https://arxiv.org/abs/2606.09682)）是唯一能找到的、能重定向到
sm_80 的全前向 persistent megakernel，它**在 A100/H100 上输给 CUDA-graphed cuBLAS**，
论文自述原因是 **cross-SM-sync 瓶颈**；而在 L4 1.33x / L40S 1.25–1.27x / A10G 1.08x /
**RTX 5090 1.19–1.23x** 上赢。注意它是带着 W8A16 量化优势仍然在 A100 上输。
详见 [07 §9.10](07_融合收益边界与根因.md)。

三个直接结论：

1. **A100 上的负结果 = 可发表的适用域结论**，不是"没调好"。面试叙事应主动给这条
   外部复现，而不是回避。
2. **要展示融合收益，租 inference-class 卡（RTX 5090 32G）**；A100 继续当 sm_80
   对照组。租金与卡型核对见 [16](archive/16_MoE_A100可行性调研.md) 与 `docs/archive/15`。
3. **sm_80 没有 FP8 张量核**（A100 whitepaper 的数据类型表里没有 FP8），所以 FP8
   checkpoint 只省存储、MMA 仍要反量化到 BF16；A100 上的量化路径用
   **Marlin W4A16/W8A16**，不要按 FP8 设计。

**novelty 定位（先说清楚，免得被当复现）**：公开工作里**没有** sm_80 的单卡 MoE decode
megakernel，也**没有**任何人在 A100 上发过"megakernel vs CUDA Graph"的对照。本实验的
对照口径是**这个空白区间**，而不是复现 Hazy/Cohere/MonoMoE。

## 3. CPU 侧已验证（`PYTHONPATH=src python -m unittest tests.test_taskgraph_abi`）

`FusionGranularityScheduleTests`：

- 段划分：`g ∈ {1,2,3,4,7,14,28}` 覆盖全部 28 层、连续、大小差 ≤ 1；
- `g=1` 的 `flat_inst_buf` / `num_inst_per_sm` / `max_inst` 与旧路径**逐字节相同**；
- 指令数守恒：各段 `total_instructions` 之和 == 全调度（实测 4522），LM head 只在
  拥有最后一层的那段出现；
- `bar_dims` 每段都是全尺寸（槽位全局索引、栏数组共享）；
- **跨段 `bar_layer` 交接槽位被直接锁定**（防未来改动导致"全调度仍通过、分段却死锁"）；
- 死锁模拟：`g ∈ {1,2,4,7,14,28}` × `num_sms ∈ {1,108}` × `BS ∈ {1,8}` ×
  `attn_splits ∈ {1,2}` 全部跑通（模拟器跨段携带 bar 状态，与真机 launch 语义一致）。

规模参考：`num_sms=108` 时全调度 4522 条指令 / `max_inst=42`；切成 4 段后指令总数
不变，但每段各自向上取整 `max_inst`，合计 44 —— 即分段会引入**约 2 条 padding
指令**的固定开销（用于解释后续实测的偏差）。

## 4. 服务器步骤

命令序列的唯一来源是 `SERVER_COMMANDS.txt`（见 [19](19_上机清单.md) §3 的执行顺序）：

```bash
# 一条命令：跑与主表相同的 (batch, context) 网格，一个 g 一行。
# 自 2026-10 起它**自带对照臂与 correctness 门**：
#   --reference-backends torch-eager,torch-cudagraph
#   --baseline-json results/taskgraph_baseline.json   （g=1 交叉校验）
#   --bandwidth-json results/bandwidth.json           （roofline 距离列）
RUN_MODE=taskgraph-fusion bash SERVER_COMMANDS.txt

# 自定义扫描点
FUSION_GROUPS=1,4,28 RUN_MODE=taskgraph-fusion bash SERVER_COMMANDS.txt
```

产物（需要回传）：

```text
results/fusion_granularity.json   每行 = (g, batch, prompt) + metrics + correctness
                                  + device_ms_per_step/implied_bandwidth_gbps/
                                    gap_to_core_floor_x
results/fusion_granularity.log    进度日志（含 g=1 与主表的对比）
```

判读时需要的列：`device_ms_per_step`（CUDA event，`cuda_decode_time_ms_total ÷
decode_steps`；与 cuBLAS 臂同口径同 harness）、`implied_bandwidth_gbps`、
`gap_to_core_floor_x`、E2E ITL mean/p50/p95/p99、TPOT。
需要**纯 kernel 拆解**时才上 nsys（`tools/parse_nsys_kernel.py`）；
**不要把 nsys 与延迟 benchmark 混跑**（[02](02_指标说明.md)）。

## 5. 判读规则（先写下先验，避免事后编故事）

> **量化先验见 [18 成本模型](18_成本模型.md) §4.1**：device 侧预测为「平坦到单调略差」，`g=28` 相对变化 +4.7%~+15.7%；**超过 15.7% 即证伪**「边界成本可用 launch/sync 界定」，出现谷底则证伪「bar 已把同样的边界串行化」。

- 若 device 时间随 `g` **单调变差**（预期最可能）：说明在带宽受限解码上粒度只
  通过 launch 开销起作用 → **结论是"部分融合在这个 workload/sm_80 上买不到
  东西"**，这本身是有价值的负结果，并据此把精力转向臂 D。
- 若出现**谷底**（某个 `g>1` 明显更好）：说明分段让某些段吃到了更好的并行分解 →
  下一步做 per-segment re-tiling（`num_sms` / tile 打包 / `attn_splits` 按段配置）。
- 若 `g` 曲线几乎平坦：说明 launch 开销在 0.74–2 ms/step 量级上可忽略 →
  粒度不是杠杆，直接记录并转臂 D。

## 6. 验收标准

1. 每一行都过 correctness gate（首 token 与 torch-eager 一致，bf16 用 PASS/CASCADE）。
   **工具强制**：对照臂由 `--reference-backends` 在同一次运行内跑出，整组交给
   `benchmarks.compare.mark_correctness`；任一行不过则 `RUN_MODE=taskgraph-fusion`
   非零退出（`--no-fail-on-correctness` 可记录而不失败，但那就不是结果）；
2. 至少 5 个粒度点，且 `g=1` 与既有 `taskgraph-baseline` 的主表数值一致（交叉校验）。
   **工具强制**：`--baseline-json` 在 |Δ| > `--cross-check-tolerance`（默认 5%）时报错；
3. 产出"粒度 vs device ms/step"与"粒度 vs ITL/TTFT"两张曲线，并附
   `implied_bandwidth_gbps` 与 `gap_to_core_floor_x`（离 weights roofline 的距离）；
4. 负结果照报（见 §5）。

> **口径提醒**：roofline 分母只能是**本机实测**可达带宽（`results/bandwidth.json`）。
> `--bandwidth-json` 缺失时工具**报错退出**，不会退回规格值 1792/2039 GB/s。
