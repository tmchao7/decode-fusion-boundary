# 融合粒度实验（Phase 1）

> 更新日期：2026-09-28
> 状态：**CPU 侧已验证，GPU 侧待跑**

## 1. 为什么做这个实验

仓库自己的实测把问题钉死了（[06](06_实际运行数据.md) / [07](07_架构结论_megakernel为何打不过cudagraph.md)）：

```text
batch=1  megakernel E2E 2.241 ms/tok  vs  cudagraph 2.944 ms/tok   -> 1.31x 胜
batch=1  megakernel device 1.89 ms/step  vs  cudagraph 0.74 ms/step -> 慢 2.6x
cudagraph 0.74 ms/step = 1611 GB/s = 实测可达带宽(1699 GB/s) 的 95%
```

结论一：**batch=1 的胜利全部来自消除 host/launch（~2.2 ms/step），不是算得更快。**
结论二：**dense 小模型上 device 侧已经贴着权重墙，没有可赚的空间。**

所以"融合得更深"在 device 侧不可能赢；能赢的只有 host 边界。于是本实验问一个
可以证伪的问题：

> 把一次 decode step 切成 `g` 段、每段一次 cooperative launch，**融合粒度**对
> device 时间与端到端延迟各有什么影响？拐点在哪？

## 2. 设计

### 2.1 粒度定义

`Config.fusion_groups = g`：一个 step 的指令流被构建成 `g` 个**连续层段**，
每段一次 cooperative launch。`g=1` 就是当前的单 megakernel（零行为变化），
`g=28` = 每层一次 launch。

实现：`schedule.split_layers(28, g)` + `schedule.build_schedule(..., layer_range=...)`，
`TaskGraphDecoder` 按段缓存调度、每步按序发 `g` 次 `tg_decode_step`。
**scratch / bars / page_table / cache_seqlens / 最终 D2H 全部共用且只做一次** ——
唯一变化的变量就是段边界本身。

### 2.2 为什么按层切在语义上是免费的

1. bar 槽位是**全局层索引**的，两段永不共享槽位 → 每步开头 `tg_zero_regions`
   清一次仍然正确；
2. 唯一的跨段依赖是 `bar_layer` 的交接：段 k 最后一层的 ADD_RMSNORM 产出
   `bar_layer[boundary]`，段 k+1 首层 QKV 等待的正是**同一个槽位**、target `BS`；
3. kernel launch 本身就是隐式全屏障，所以这个等待在段开始时已经满足。

这三点都有测试锁定（见 §3），不靠推理。

### 2.3 四条臂（避免把"粒度"和"实现语言"混在一起）

| 臂 | 实现 | 隔离的变量 |
|---|---|---|
| A | torch-eager | host-bound 下界 |
| B | torch-cudagraph | 强基线（已贴墙） |
| **C** | 分段 megakernel（本实验，同一份 IR） | **融合粒度** |
| D | Triton 融合组 + CUDA Graph | 工具链 / 实现质量 |

**C 是 D 的对照**：如果 D 赢了，必须先用 C 回答"这是粒度的功劳还是实现的功劳"。
在 sm_80（无 TMA / 无 thread-block cluster / 无 wgmma）上，ClusterFusion++ 那类
cluster 级融合不可用，所以本实验的能量范围就是"跨段边界 + 并行分解"。

## 3. CPU 侧已验证（`PYTHONPATH=src python -m unittest tests.test_taskgraph_abi`）

`FusionGranularityScheduleTests`：

- 段划分：`g ∈ {1,2,3,4,7,14,28}` 覆盖全部 28 层、连续、大小差 ≤ 1；
- `g=1` 的 `flat_inst_buf` / `num_inst_per_sm` / `max_inst` 与旧路径**逐字节相同**；
- 指令数守恒：各段 `total_instructions` 之和 == 全调度（实测 4522），LM head 只在
  拥有最后一层的那段出现；
- `bar_dims` 每段都是全尺寸（槽位全局索引、栏数组共享）；
- **跨段 `bar_layer` 交接槽位被直接锁定**（防未来改动导致"全调度仍通过、分段却死锁"）；
- 死锁模拟：`g ∈ {1,2,4,7,14,28}` × `num_sms ∈ {1,108}` × `BS ∈ {1,8}` ×
  `attn_splits ∈ {1,2}` 全部跑通（模拟器跨段携带 bar 状态，与真机 launch 语义一致）。

规模参考：`num_sms=108` 时全调度 4522 条指令 / `max_inst=42`；切成 4 段后指令总数
不变，但每段各自向上取整 `max_inst`，合计 44 —— 即分段会引入**约 2 条 padding
指令**的固定开销（用于解释后续实测的偏差）。

## 5. 判读规则（先写下先验，避免事后编故事）

- 若 device 时间随 `g` **单调变差**（预期最可能）：说明在带宽受限解码上粒度只
  通过 launch 开销起作用 → **结论是"部分融合在这个 workload/sm_80 上买不到
  东西"**，这本身是有价值的负结果，并据此把精力转向臂 D。
- 若出现**谷底**（某个 `g>1` 明显更好）：说明分段让某些段吃到了更好的并行分解 →
  下一步做 per-segment re-tiling（`num_sms` / tile 打包 / `attn_splits` 按段配置）。
- 若 `g` 曲线几乎平坦：说明 launch 开销在 0.74–2 ms/step 量级上可忽略 →
  粒度不是杠杆，直接记录并转臂 D。

## 6. 验收标准

1. 每一行都过 correctness gate（首 token 与 torch-eager 一致，bf16 用 PASS/CASCADE）；
2. 至少 5 个粒度点，且 `g=1` 与既有 `taskgraph-baseline` 的主表数值一致（交叉校验）；
3. 产出"粒度 vs device ms/step"与"粒度 vs ITL/TTFT"两张曲线；
4. 负结果照报（见 §5）。
