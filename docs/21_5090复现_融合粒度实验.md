## 1. 这次要回答什么

> 融合/CUDA Graph 的**收益边界**是否随架构移动？

`docs/14` §1 记录了 A100 上的结论（**归档 `kernel.cu` 线**）：

```text
batch=1  megakernel E2E     2.241 ms/tok  vs cudagraph 2.944 ms/tok   -> 1.31x 胜
batch=1  megakernel device  1.89  ms/step vs cudagraph 0.74  ms/step  -> 慢 2.6x
cudagraph 0.74 ms/step = 1611 GB/s = 实测可达带宽(1699 GB/s) 的 95%
```

外部独立实现 AutoMegaKernel 在 **5090** 上自报：同精度 bf16 **输给** cuBLAS 1.24×，
只有 int8（fewer bytes）赢 1.19–1.23×（[20](20_方向重构_从dense到MoE融合kernel.md) §1.2）。
所以 5090 上"融合是否翻盘"不能靠转述外部数字回答，要么自己测，要么不写。

## 4. 预注册假设（取数之前写下）

### H-5090：5090 的 device 侧地板**更高**，因此融合的 device 劣势应收窄

- **推断**：5090 的权重墙是 **0.7645 ms/step**，A100 实测墙是 **0.702 ms/step**。
  5090 的规格带宽（1792）虽高于 A100（2039 的 83% 实测），但**实测可达带宽反而更低**
  （1559.2 < 1699）。所以在同一个 1.192 GB/step 的模型上，cuBLAS + CUDA Graph 的
  device 时间**不可能优于** A100 的 0.74 ms/step。
- **推论（可证伪）**：如果 megakernel 的 device 时间里有相当一部分是**与带宽无关的
  固定 per-step 成本**（launch 边界、barrier、drain），那么它在 0.7645 ms 的地板上
  占比更小 → `megakernel ÷ cudagraph` 的 device 倍数**应比 A100 归档线的 2.6× 更小**。
- **反证信号**：
  1. 实测 cudagraph 的 device ms/step **< 0.7645 ms** → 上述字节账/带宽账在 5090 上
     不成立。这是 **calibration finding**（`calibration_needed`），**不是 kernel 赢了**，
     必须先修模型（KV 读放大、权重字节口径）再谈结论；
  2. 实测 device 倍数 **≥ 2.6×** → 固定成本随 grid 变大而变大（170 SM vs 108 SM），
     "固定成本被高地板摊薄"这条机制被推翻，`docs/18` §4.1 的 launch/sync 界定也需要重标定。

### 沿用 `docs/18` §4.1 的粒度预测（不重新发明）

- `g ∈ {1,2,4,7,14,28}` 的指令数/层级/K 步**完全相同**（验证器已证）；
- 预测：device 侧「平坦到单调略差」，`g=28` 相对变化 **+4.7% ~ +15.7%**；
- **证伪阈值 15.7%**：超过即"边界成本可用 launch/sync 界定"被推翻；
  出现**谷底**则"bar 已把同样的边界串行化"被推翻。

> ⚠️ **基线的来源必须标出来**：`tools.bench_fusion_granularity` 的
> `--base-device-ms` 默认是**归档 A100 的 1.89 ms/step**（`docs/14` §1），
> **不是** 5090 的数字。它只决定预测表的绝对毫秒列；`g=28` 的相对阈值随基线缩放
> （1.89 → +15.7%，10.8 → +2.75%）。取数后必须按实测 `g=1` 重算这张表，
> 并把 `--base-device-ms-source` 写成实测来源。

### 5.5 已测：带宽、以及"为什么 dense 在 5090 上不快"

**这一节的每个数字都是本机实测**（`results/bandwidth.json`，RTX 5090，commit `e2b7e21`）。

**5.5.1 可达带宽**（探针 `--bytes 1.2e9 --iterations 20 --warmup 5`）

| 量 | 本仓实测 | 引用值 | 备注 |
|---|---|---|---|
| 只读可达带宽 GB/s | **1658.08**（stddev 5.30，CoV 0.32%） | 1559.2 | 高 6.3%，按本仓为准 |
| 规格 GB/s（NVML） | 1766.528 | 1792 | 达成 **93.9%** |

⚠️ 可达带宽**不是唯一值**：同一探针换 buffer 尺寸从 1,477（0.3 GB）到 1,683（4 GB）单调上升，
对 `time_ms = a + bytes/B` 的拟合**截距 −3.9 µs**（即**无**固定 per-call 开销）。
所以差异是"小 buffer 的单遍扫描没跑满"，不是摊不开开销。**任何 roofline 分母必须声明用的是哪个数。**

**5.5.2 dense 权重地板 vs 实测**（`[W] = 1.1921 GB`，bf16）

| 臂 | device ms/step | 等效带宽 | 占可达 | 离地板 |
|---|---:|---:|---:|---:|
| megakernel `g=1` @ ctx=1 | **4.180** | 285 GB/s | **17.2%** | **5.81×** |
| megakernel `g=1` @ ctx=32 | 4.318 | 276 GB/s | 16.6% | 6.00× |
| megakernel `g=1` @ ctx=1920 | 13.397 | 89 GB/s | 5.4% | 18.6× |
| floor（1.1921 GB ÷ 1658.08 GB/s） | **0.7190** | 1658 GB/s | 100% | 1.00× |

**5.5.3 两个瓶颈是分开的，且都不是"带宽不够"**

**(a) attention 成本严格线性**：ctx 从 1→1920，增量 13.397−4.180 = 9.217 ms 对应 1919 个
KV 位置，即 **4.82 µs/位置**；在 ctx=512/1024 两点独立复核为 4.83 / 4.82 µs/位置（一致到 0.2%）。

**(b) 基础 GEMM 流水在 ctx=1 就已经 5.81× 离墙**，此时**完全没有 attention**。
所以 (b) 不是 attention 引起的，是主因。

**(c) 网格扩展性在 64 SM 饱和，且"加 SM 反而更慢"**（ctx=1，b=1）：

| num_sms | ms/step | 等效 GB/s | 每 SM 指令数 | **每条指令耗时** |
|---:|---:|---:|---:|---:|
| 1 | 74.655 | 16 | 4522 | 16.5 µs |
| 4 | 20.206 | 59 | 1131 | 17.9 µs |
| 16 | 6.252 | 192 | 283 | 22.1 µs |
| 32 | 4.616 | 260 | 141 | 32.7 µs |
| 64 | 4.116 | 292 | 70 | 58.8 µs |
| 108 | 4.125 | 291 | 42 | 98.2 µs |
| 170 | 4.181 | 287 | 27 | **154.9 µs** |

把 SM 从 16 加到 170：每 SM 的活减少 **10.5×**，而总时间只降 1.5×（6.252→4.181），
**单条指令耗时反而涨 7×**（22.1→154.9 µs）。

> **判读**：时间不在"干活"，在**等依赖**。**280 GB/s 是同步/依赖链的上限，不是 HBM 的上限。**
> 佐证：`[W]=1.192 GB` 在 170 个 SM 上要跑到 1658 GB/s，每 SM 只需 9.75 GB/s；
> 而单 SM 独跑（num_sms=1）就有 16 GB/s。**单 SM 能力足够，合起来反而慢。**

结构原因（`build_layer_waves`，BS=1）：每层 7 波的指令数是
`QKV 56 / ATTN 8 / COMBINE 0 / O_PROJ 10 / FFN_UP 28 / FFN_DOWN 10 / RMSNORM 1`。
其中 **`ADD_RMSNORM` 每层只有 1 条指令、`ATTN_DECODE` 只有 8 条**，
而 28 层必须**串行穿过**这些窄波；`LM_HEAD` 虽有 1333 条（占调度 29%），
但它依赖最后一层的 RMSNORM，只能在**末尾单独跑**。调度总指令 4522、每 SM 27 条、
串行层级 82 —— 每层平均可并发指令仅 **≈55 条**，远低于 170。
> 这正是"64 SM 饱和"的来源：**可并发的指令数 ≈55，与 16→64 SM 的测量拐点一致。**

**5.5.4 host 残差已归零（这否证了 dense 融合的前提）**

`perf_grid.json`（24 行，`runs=5`）：p32 b1 megakernel `wall 624.1 / host decode 603.4 /
device 601.7 ms`（128 token）。**host ≈ device，差 0.3%**；cudagraph 差 0.8%。
[14](14_融合粒度实验.md) 那条 ~2.2 ms/step 的 host 残差在 5090 上**不存在**。

**结论（对交付的影响）**：dense 融合在 5090 上**没有可赚的东西** —— 它赚的是"少一次
host 边界"，而该机制在此机器上已归零；device 侧又受同步链限制（17% 可达带宽）。
因此 **本页的"5090 赢"假设被否证**，A100/5090 双机对比不成立，
`docs.md`[20](20_方向重构_从dense到MoE融合kernel.md) 的转向理由由此**从推测变为实测**。

> **口径声明**：以上 device 数字只用了 **b=1**。`torch-cudagraph` 在 b≥2 时 8 个网格点
> 只有 2 个过 correctness 门，`attn_splits=2` 臂另有未修 bug（见 [22](22_小batch_MoE架构设计.md) §8）。
> 按本仓硬规则，这些臂在过门之前不出延迟表。

## 6. 判读规则（先写下，避免事后编故事）

> **本页只回答 dense 的融合粒度问题。** MoE 的架构决议（小 batch 的字节账、四层架构、
> 新 opcode 契约、b=1 → b>1 路径）见 [22 小 batch MoE 架构设计](22_小batch_MoE架构设计.md)。

沿用 [14](14_融合粒度实验.md) §5：

- device 随 `g` **单调变差** → 粒度只通过 launch 开销起作用；
- 出现**谷底** → 分段拿到了更好的并行分解，下一步做 per-segment re-tiling；
- 曲线**几乎平坦** → launch 开销在该量级可忽略，粒度不是杠杆。

对 **H-5090**：

- 若 5090 上 `megakernel ÷ cudagraph` 的 device 倍数 **< 2.6×**：H-5090 未被否证，
  可写"融合的 device 劣势随架构收窄，机制是固定 per-step 成本被更高的带宽地摊薄"；
- 若 **≥ 2.6×**：H-5090 被否证，按 §4 的反证信号 2 处理；
- 若 cudagraph device < 0.7645 ms：**先怀疑口径**（`calibration_needed`），不要宣布 kernel 赢。

**对照的适用范围**：本页只做 5090 单机结论。**A100 一侧没有用当前 taskgraph 代码
重测**，因此 `docs/20` §9 第 1 步原文要的"A100 输 / 5090 赢 两机对照"在本页
**不成立**——本页给的是 5090 单机结果 + 归档 A100 的引用值。两机结论必须等
A100 用当前代码复测后才能写。
